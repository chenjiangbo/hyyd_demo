# 企业微信跨版本数据源排查记录与台式机测试说明

更新日期：2026-10-26  
用途：带到最初进行开源采集验证的 Windows 台式机，比较旧版企业微信的数据目录与当前采集器的读取结果。本文不包含任何聊天正文。

## 当前要回答的问题

企微窗口里能打开、能发送消息的会话，当前会话列表和消息是否已经写入本机某个企微数据目录？如果写入了，为什么当前采集结果没有显示？具体要区分：

1. 会话确实在另一个企业/账号数据目录中；
2. 会话所在目录存在，但当前版本的密钥探测或数据库解析没有读到；
3. 消息库读到了，但会话名称、联系人备注或群成员名称解析不一致；
4. 这个会话不在目前已检查的目录或数据库类型中。

现在还没有证据证明“企微没有保存这些消息”，也没有证据证明“5.0.13.6005 一定不兼容”。旧台式机的测试用于区分新旧版本表现，不是先假设新版本有问题。

## 项目背景和集成方案

产品要同时采集个人微信和企业微信。两者都通过 Windows 子进程运行各自的开源采集核心，客户端不展示开源项目自带的图形界面。采集结果转换成项目统一的消息结构，再按后台配置的全局订阅规则筛选会话并上传；订单匹配等现有业务处理不因采集来源改变。

企微链路的主要步骤如下：

1. 客户端读取企微本机配置中的当前 Profile，关联到该 Profile 的企微账号目录，再把对应的 `Data` 目录交给采集器。当前实现从 `WXWork\Profiles\setting.json` 的 `CurrentProfile` 及 Profile 的 `io_data.json` 取得目录标识。
2. 企微采集器必须在与已登录 `WXWork.exe` 相同的 Windows 登录会话中运行，才能探测该版本支持的企微进程并读取进程中的数据库密钥。通过 SSH 启动的进程属于另一个会话，不能代表桌面采集结果。
3. 采集器发现企微消息库和会话/联系人元数据数据库，建立只读快照后解析会话、消息和媒体。原始数据库不由采集器写入。
4. 会话列表通过 JSON Lines 返回给客户端。客户端以启用的订阅会话 ID 请求消息，按轮询周期读取新增消息和媒体更新。采集器不负责决定业务订阅规则。

核心实现位置：

- 开源采集核心：`packages/native-chat-collectors/wxwork/vendor/upstream/`
- 无界面采集入口：`src-tauri/src/bin/hyyd_native_collector.rs`
- Windows 数据源发现、可信进程/密钥探测和数据库快照：`crates/source-windows/`、`src-tauri/src/`。
- 企微当前账号目录识别：`packages/tray-app/src/main/wxwork-context.ts`
- 客户端子进程、会话同步和状态管理：`packages/tray-app/src/main/native-chat-collector-manager.ts`
- 会话显示名称解析已增加 `conversation_table.roomname_remark`，联系人备注解析已增加 `external_user_relation_v3` 的 `remarks`、`real_remarks`、`corp_remark`。必需的 `user.db` 或 `session.db` 无法打开时，当前代码会明确报错，不再返回不完整会话列表。

开源核心版本为 `wecom-archive 0.0.11`（MIT）。本项目增加了面向无界面子进程的入口和产品消息协议，并在上游解析层补充了当前实测数据结构所需的名称字段。完整源码在测试包内；重编译需要 Windows、Rust 1.98.1 和 MSVC x64 C++ 构建工具。台式机只做本次读取诊断时不需要 Rust，因为压缩包内附有当前 Windows 构建的采集器 EXE。

## 为什么“能读到部分会话”仍不能排除漏读

“只读到 64 或 72 个会话”不等同于“从一张完整表里只读前 64/72 行”。采集链路先定位数据目录，再探测密钥、发现指定数据库文件、建立快照、识别表结构、解析会话元数据和联系人备注。任何一层没有覆盖目标会话，都会表现为会话不在结果里。当前数据还显示至少一个消息目录因密钥失败未进入解析；而旧脚本也曾只按 `message.db` 目录扫描，忽略了只有 `account_data.db` 的目录。

代码检查没有发现会话发现查询只取前 N 行的 `LIMIT`。会话列表由已解析的会话元数据与消息库中的会话 ID 汇总而来，消息查询也没有固定的前 N 条截断。因此目前不符合“同一张表只读取前 100 行”的迹象。但这不能证明所有会话来源都已覆盖：采集器只识别指定数据库文件、依赖密钥探测成功，并按已支持的表结构解析；这些边界仍可能漏掉另一目录、另一数据库布局或新版本字段。

企微新安装、切换企业、历史登录状态和客户端版本可能影响 Profile、数据目录、数据库文件名/结构及内存密钥探测，但目前没有证据能把这次缺失归因于其中某一项。尤其不能仅凭“当前能读到一些会话”推出“同一来源下其它会话一定都能读到”。

## 台式机对比测试步骤

测试包是独立文件，不会提交或修改当前项目代码。包内有当前版本采集器 EXE、只读诊断脚本、开源核心完整源码和本说明。

1. 在台式机上把 `wecom-desktop-test-package.zip` 解压到普通目录，例如下载目录。
2. 登录并启动台式机上现有的企业微信。不要从 SSH 窗口、计划任务或其他服务会话运行诊断；PowerShell 必须在运行企微的 Windows 桌面登录会话中打开。
3. 打开普通 PowerShell，切换到解压目录，运行：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\diagnose-wecom-sources.ps1
   ```

4. 把完整输出发回。脚本会打印企微版本、发现的数据目录、每个目录是否有 `message.db` / `session.db` / `user.db` / `account_data.db`，以及读取成功的会话总数和目标名称命中项。它不会输出消息正文。
5. 如果出现 `key_probe`、`source_scan`、`unsupported` 或其他失败，保留原样发回；失败目录不算“没有会话”。不要先切换企业或重装企微，以免改变当前对比条件。

脚本对源数据库使用采集器的只读读取路径，临时快照/状态写在 Windows 临时目录，并在每个目录结束后删除。它只扫描该用户 `Documents\WXWork` 的直接数字子目录；如果台式机的企微数据实际存放在其它位置，请先把实际路径告诉我，不要自行改脚本里的路径。

## 如何解读台式机结果

- **旧版台式机能命中，5.0.13.6005 笔记本未命中**：说明版本/数据结构差异值得继续定位，但还要比较具体数据库表和字段，不能直接宣称版本过新是根因。
- **旧版台式机也能扫描，但目标只在另一个目录中命中**：说明当前企业目录识别与会话所属目录需要进一步核对。
- **旧版台式机目标会话在已成功解密目录中仍不出现**：下一步应检查采集器识别的会话表/会话 ID 与源库内容，不再把问题归结为版本新旧。
- **某些目录密钥探测失败**：这些目录仍未排除；要先获得该目录的可读扫描证据。
- **会话命中但名称不匹配**：用会话 ID、参与人字段和 `session.db` / `user.db` 元数据核对，判断是备注解析还是会话身份关联问题。

在新旧机器对比完成前，不建议为了猜测版本兼容性而先卸载或降级笔记本企微；旧台式机本身就是更有价值的对照组。
