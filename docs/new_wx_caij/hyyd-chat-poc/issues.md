## B. `download_file()` 文件附件失败：核心待修问题

### 现象

本轮通过手机向 filehelper 发送照片和 PDF。图片成功解密。PDF 消息识别为文件类，但 `MediaDownloader.download_file()` 对该样本没有返回文件路径。最初按工具解析出的名称查找没有成功。用户补充该附件已在微信本机目录，给出 `F:\\WEBCHAT_FILE\\xwechat_files\\JiangBo_Chen1978_1235\\msg\\file\\2026-10` 和实际去重后的名字后，目录中的 PDF 被定位：150,272 字节，文件头 `%PDF-` 有效。

本条附件的两个名字分别为“原始名称无 `(2)`”和“本机落盘名称有 `(2)`”。用户截图中聊天气泡宽度有限，文件名显示被截断，不能靠截图判断本地是否加了 `(2)`。本轮没有以文件名猜测替代消息记录关联。

### 根因 1：把 protobuf 二进制当 UTF-8 文件名

本机读取的 `MessageResourceDetail.packed_info` 是嵌套 length-delimited protobuf 风格数据。该样本解析结构：外层 field 1 长 181 字节；其中内层 field 1 长 87 字节，是原始文件名；内层 field 2 长 90 字节，是微信处理重名后的本地文件名。

对应源码 `sources/wechatauto-replica-main/wechatauto/media.py` 的 `_file_name()`（约 1804–1827 行）执行：

```python
name = r["packed_info"].decode("utf-8", "replace").strip()
name = re.sub(r"[\\r\\n\\x00]+", "", name)
```

这把 protobuf tag（如 `0x0A`、`0x12`）和 varint 长度（如 `0xB5 0x01`、`0x57`、`0x5A`）也解码为文字。日志/字符串表示中会看到 `\\n`、`\\x12`、`\\x01W`、`Z` 和替代字符 `�`，并且两个文件名被拼接。替代字符是 UTF-8 解码器替换非法字节的结果；控制字符来自 protobuf 二进制边界，不是微信/用户给文件名插入了控制字符。

**影响：**函数返回的既不是原始消息文件名，也不是本地落盘文件名；清理 CR/LF/NUL 不能修复 protobuf 结构。之后用该字符串匹配 `msg/file` 必然可能失败，构造输出名也不可靠。

### 根因 2：`local_type` 严格按裸 49 查询

该消息行实测 `local_type = 25769803825`，十六进制 `0x600000031`，低 8 位为文件类型 49。`download_file()` 在 `media.py` 约 1829–1838 行调用：

```python
row = self.db.get_message_row(user, local_id, local_type=49, shard=shard)
if not row or row["local_type"] != 49:
    return None
```

由于查询和比较都只接受裸值 49，实际带高位包装的本条消息可能在解析资源 metadata 之前就被过滤掉。此问题和 `packed_info` 错误解码彼此独立；任意修好其中一个，另一个仍可能使下载失败。

### 集成修复方向

1. 用 `server_id` 加分片/消息上下文关联 `MessageResourceInfo` 和 `MessageResourceDetail`，避免只按 local_id 猜。
2. 依据 protobuf schema 或经过验证的 wire-format parser 分别读取原名和本地名。对畸形长度、未知字段、截断数据、安全 basename 做处理；不对整块 bytes 直接 decode，不通过过滤控制字符做伪解析。
3. 将 `original_name`、`local_name`、`local_path` 分开保留；如果目录中两个名字都存在，依据当前消息的资源记录/可靠关联选取，不能取 `os.walk()` 遇到的第一个同名候选。
4. 先定位消息行，再依据实测的本地类型编码规则识别文件类型。此样本提示低 8 位为 49，但集成前需检查更多类型和值，不能不验证就对所有消息无差别掩码。
5. 把“复制本地已下载文件”与“触发微信下载尚未落地文件”区分开；未下载时返回明确状态，提示用户在微信点击下载后再扫描。此次只证明落地后的文件目录可读，并未证明自动触发附件下载。
6. 对调用者返回明确诊断状态，例如 `message_row_not_found`、`not_file_type`、`resource_metadata_missing`、`filename_parse_failed`、`local_file_not_found`、`ambiguous_local_file`、`copy_failed`，不要所有失败都静默返回 `None`。

**建议复测/验收：**普通名；重复名 `(2)`；两个候选文件同在目录；中文/空格/括号名；跨月路径；protobuf 截断/未知字段/非法 UTF-8；裸 49 与本条带包装值；用户尚未下载和点击下载后两种状态；按 server_id/shard 精确找到目标附件。详细清单见 `final-report.md` 第 5 节。

## G. 4.1.15.56 附件下载根因复核（确认与旧报告相同）

在用户已下载到本机的 PDF 上复查三个目标消息（message__message_2.db 中 local_id 119、92、81）：原始类型均为 25769803825 (`0x600000031`，低 32 位 49)。`get_message_row()` 不带类型过滤且指定 shard 可取到行；以 `local_type=49` 过滤则取不到。`download_file()` SQL 精确匹配 49 并再次比较 `row["local_type"] == 49`，`download_media()` 还在前置分发处判断原始值 `t == 49`。故当前样本会在附件名/路径关联之前被过滤。

进一步用无类型过滤、指定 shard 的完整行调用 `_file_name()`，三条目标行都能复现控制字符与 U+FFFD；说明绕过前置类型门槛后，旧的 protobuf 整块 UTF-8 解码错误仍会使 `f == name` 搜索失败。两个问题是串联阻塞、彼此独立，修掉一个仍不够。

## 2026-10-27 企微单聊会话目录漏项

**根因已由笔记本源库证据确认：** 三个单聊及消息存在当前企微账号的本机消息库，源会话 ID 分别为 `S:1688851245090625_1688854540251762`、`S:1688851245090625_1688857029287313`、`S:1688851245090625_1688857904312275`。其中包含三条标记消息以及“陕西金控数字化的基石-数据治理.pptx”的文件消息元数据；此次仅核对文件名/消息元数据，没有读取附件内容。

**代码根因：** 无界面采集器启动时订阅集合为空，通过 `selected_conversation_ids=Some([])` 读取导出；消息 SQL 因空集合加入 `0 = 1`，所以只从会话元数据生成目录。没有会话元数据记录的 `S:` 单聊 ID 只能从消息表发现，形成无法订阅的循环。上游完整读取能读出 100 个会话、815 条消息，独立证明目标记录在该数据源中。

**已修改：** 在企微无界面采集链路中增加独立的会话索引读取：从支持的 `messages` / `message_table` 只查询去重后的 `conversation_id`，并入会话目录；不读取这些未订阅会话的正文、发送者字段或媒体。原消息查询仍按已订阅会话 ID 与每会话源行号游标筛选。采集器每 120 秒刷新会话目录；客户端每 30 秒同步后台规则，所以首次发现目录外单聊后会在目录刷新时按可见标题匹配，命中后再订阅源 ID。群聊既有元数据目录仍保留，消息索引也覆盖其 ID。
