## 先读结论

目标场景是：用户在 Windows 登录客户端后，读取指定联系人的本机消息；用户已经打开的图片、已经下载的文件也能被产品读取。

**两边都已有真实本机证据表明场景可实现，但不是当前测试版开箱即用。**

| 客户端 | 已经实测 | 尚未完成 |
|---|---|---|
| 个人微信 4.1.15.56 | 指定会话和近期历史抽样可读；最小化时捕获到新消息；合并卡片内文字、图片子项和来源时间可解析。用户打开卡片图片后，源码副本从 Rec 缓存成功解密并生成可验证 JPEG。 | 合并卡片内嵌文件暂无样本。普通附件下载函数对已落地 PDF 仍失败。未证明从未打开/未缓存的图片可完全后台获取。源码改动尚未集成到客户产品。 |
| 企业微信 5.0.13.6005 | 新发的图片和文件合并卡片均从源数据库展开为两条文字加一个媒体子项；内部时间可读。打开/下载后，PNG 图片 MD5 与消息元数据一致，DOCX 的文件名、大小、MD5、文件头与缓存文件一致。源码副本兼容了实测的新 protobuf 格式。 | 当前 0.0.11 桌面 EXE 仍是旧程序；更新源码没有在桌面 UI 完整采集、归档、预览。现有媒体索引没有自动按内容 MD5 定位 UUID 文件名的图片；合并子项媒体尚未接入正式导出层。企微增量/常驻后台监听没有实测通过。 |

旧历史记录的附件缺失可能是本机当时没有缓存。新样本说明：用户在对应客户端打开图片、下载文件后，本机确实有可对应的媒体字节。源数据可读不等于当前 EXE 已采集显示；集成验收需要覆盖解析、定位、导出和产品 UI。

## 交给 coder 的文件

### 必须提供

1. 本文 ai-coder-handoff.md：当前结论、改动清单与验收目标。
2. wechat-test-results.md：个人微信合并消息图片成功路径、下载失败根因、边界。
3. wechat-4.1.15.56-regression.md：当前微信版本下的回归证据。
4. wecom-test-results.md：企微历史媒体基线、旧格式误分类、新合并卡片媒体实测和限制。
5. environment.md：Windows、客户端版本、构建与复现环境。
6. 两份源码副本的本轮改动。优先给 modified source override 包配原始源码 ZIP，或给 sources 下的修改版源代码目录。

### 背景与特定用例

- final-report.md：完整过程与背景，较长，按专题链接查阅。
- issues.md：历史问题根因及修复状态。
- contact-sweep-results.md：多联系人/群聊近期抽样；实现指定联系人读取时有用。
- wecom-missing-media-audit.csv：早期企微 88 个媒体引用的逐项审计；不是本次新合并图片缺失的证据。
- evidence 和 logs 是测试留档，通常无需发给 coder。

原始 ZIP 文件 wechatauto-replica.zip 和 wecom-archive.zip 是未修改的上游快照。只给原始 ZIP 会漏掉本轮修复；如果使用 ZIP，必须再叠加 ai-coder-source-overrides.zip。

## 本轮源码变更的准确清单

通过与原始 ZIP 文件哈希对照，两个源码副本各有两个已修改文件：

### 个人微信 wechatauto-replica

- wechatauto/db.py：改进登录用户可见进程发现；统一复合消息类型归一化；增加 get_merged_forward()，不改变既有 get_messages() 返回结构。
- wechatauto/media.py：媒体函数按基础类型及 shard 精确回读；避免把合并父卡片当作普通文件；增加从 Rec 本地缓存查找并解密嵌套图片，以及在清理 V2 容器页脚前校验原始载荷 MD5。
- wechatauto/records.py 是上游已有文件，本轮复用而非新增。早期报告中“新增 records.py”表述已更正。

### 企业微信 wecom-archive

- crates/parser/src/lib.rs：raw type 4 不再无条件归类为 Image，防止合并卡片生成伪图片引用。
- src-tauri/src/lib.rs：兼容此前观察到的旧结构和本次实测的新 protobuf 格式；新结构中子项 type code 2/14/15/16 分别识别为文字/图片/文件；保存子发送者、来源时间、文本与媒体元数据，并按来源时间排序。
- 对两条新样本的实测解析分别得到 3/3 子项。文件按原名找到且大小、MD5、文件头匹配；图片缓存文件名是 UUID，原文件名索引未命中，但通过媒体元数据的大小候选与 MD5 校验，确认本机 PNG 与该子项完全对应。
- 正式产品链路仍需把 raw_payload.items 内的媒体子项送入媒体导出层，并实现安全、唯一性校验的图片缓存定位。父 MessageV1 暂保留 Unsupported 以兼容当前契约；子项信息已在 raw_payload 中解析。

## 给 coder 的实现重点

1. 保留父合并卡片及子项关系。每个子项记录原始索引、类型码、发送者、来源时间、正文或媒体元数据；未知子项保留并可诊断，不静默丢弃。
2. 外层消息时间和合并记录内部时间分开保存。按源时间排序，同秒用原始索引稳定排序。微信消息键包含账号、shard、local_id，避免分片间同号冲突。
3. 媒体状态分别表示元数据已解析、本地缓存已找到、内容校验成功、需要用户下载、未找到、歧义或解码失败。文件用原名/大小/hash校验；图片校验 hash、签名和可解码性。读到 CDN 元数据不能算已经拿到媒体字节。
4. 用户已经打开图片或下载文件时，读取本机缓存；不要默认自动点击 UI。驱动客户端下载未落地附件是另一项能力，需单独实现和测试。
5. 企微 0.0.11 两次采集均为全量扫描加归档合并，没有证明增量游标或常驻监听。增量作为另一层实现：watermark、重叠窗口、幂等去重、迟到消息补扫及重启恢复。微信已有本机监听样本，但长期运行/重启恢复仍未测试。
6. 先在隔离的开发分支/工作区集成，不改动微信、企微客户端版本。先过真实样本和媒体端到端回归，再接客户产品 UI。

## 建议验收

- 指定个人/群聊读取历史、最近 N 条、分页与稳定联系人 ID 映射。
- 前台、最小化的新消息；重复消息、消息顺序、客户端或采集器重启后的补采。
- 两款客户端各自的合并记录：文字+图片+文件，验证父子关系、内部发送者/时间、文件名、媒体 hash、图片可打开、文件可读取。微信还缺一条真正含文件的合并记录样本。
- 已下载与未下载附件区分；重名文件、跨 shard 同 local_id、无缓存和多候选都返回明确状态。
- 再次采集无重复，消息数、子项数、媒体成功/缺失计数一致。
