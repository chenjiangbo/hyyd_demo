## 已下载 PDF 附件的函数回归与根因复核

升级到 4.1.15.56 后，`MediaDownloader.download_file()` 对先前已下载到本地的 PDF 样本仍未返回路径。目标发票的三条消息行位于 `message__message_2.db`，local_id 119、92、81；每行 `local_type=25769803825`，即 `0x600000031`，低 32 位是 49。当前文件仍在用户给出的 `F:\WEBCHAT_FILE\xwechat_files\JiangBo_Chen1978_1235\msg\file\2026-10` 目录；所以本次失败不是“文件尚未点击下载”的结果。

本轮按当前源码重新核验了原因，**与此前报告的两个缺陷相同，尚未修复**：

1. **类型包装导致入口提前退出。** `download_file()` 用 `get_message_row(..., local_type=49)` 做 SQL 精确过滤；本机验证同一目标行无类型过滤时能找到，过滤为裸 49 时找不到。随后源码还要求 `row["local_type"] == 49`，这也会拒绝 25769803825。自动分发入口 `download_media()` 也只判断 `t == 49`，不会把该复合值分发到文件函数。因此直接调用和自动分发都可能在检查文件名之前返回 `None`。
2. **文件名解析仍把 protobuf 二进制当 UTF-8。** 绕过类型过滤后，对目标分片的三行调用 `_file_name()`，真实返回值仍包含控制字符和 `U+FFFD` 替代字符；本机检查三行均 `parsed_name_has_control=true`、`parsed_name_has_replacement=true`。这不是微信在文件名里写入了控制字符，而是 `packed_info` 的 protobuf tag/varint 被错误解码成文本。对 `packed_info` 做 UTF-8 解码并清除 CR/LF/NUL，并没有恢复原名/本地名。
3. **local_id 必须连同 shard 使用。** 本机数据里相同 local_id 在多个消息分片重复：例如 local_id 119 在 `message__message_2.db` 和 `message__message_0.db` 都命中 `local_type=25769803825`；local_id 92 还在多个分片命中同类型但不同消息/附件。正确发票行是 `message__message_2.db` 中的那一行。若不传 `shard`，即使修复类型匹配，也可能选错同号消息。`download_media()` 已尝试将 shard 传给下载函数，但其前面的 `t == 49` 仍会挡住复合类型。

因此根因判断与旧版相同，而且本轮在 4.1.15.56 再次得到直接证据；不能归因于微信升级或文件未落地。该函数只在本地 `msg/file` 目录中找并复制已存在的文件，并不负责驱动微信点击“下载”。
