## 附件文件名与下载函数诊断摘要

本条附件对应的 `MessageResourceDetail.packed_info` 是 length-delimited protobuf 二进制。正确解析后包含两个字符串字段：

1. 消息原始文件名（无 `(2)`）。
2. 微信本机保存名称（有 `(2)`，用于同名冲突后的本地文件）。

4.1.15.56 下重新实测仍复现相同问题。`_file_name()` 把 `packed_info` 整块 `.decode("utf-8", "replace")`，目标三条 PDF 消息经无类型过滤查询后，解析结果仍同时含控制字符和 `U+FFFD`，原始名称与本地 `(2)` 名拼成一个字符串。它们来自 protobuf tag/长度字节，不是文件名本身含控制字符。

当前函数最先卡在类型过滤：原始 `local_type=25769803825`（`0x600000031`，低 32 位为 49）；指定正确 shard、无类型过滤能找到该行，SQL 按裸 49 过滤则找不到。`download_file()` 有此精确过滤和 `==49` 检查；`download_media()` 还在调用前用 `t==49` 分发，因此也会漏掉包装值。类型门槛绕过后，错误文件名仍会导致本地 `f == name` 搜索失败。此外同一 local_id 在不同 shard 有不同消息，必须传递 shard。具体证据和修复办法见 `final-report.md` 4.3–4.4。

1. Python 3.13 下安装遇到 `winsdk` 缺少轮子并需要本机 C++ 编译工具；首次依赖下载也被受限环境中断。

3. 首次 `doctor` 在 Codex 受限账户运行时报告找不到 `Weixin.exe`。交叉检查发现微信进程在登录用户 session 1，受限账户 tasklist 权限不足。用户明确同意后，在登录用户会话执行只读诊断，成功解密 24/24 个数据库并读取消息。

结论：本机能够读取多联系人及群聊的近期消息行；这仍不是所有通讯录联系人/全部历史读取证明。逐会话数据、名称和消息类型统计见 `contact-sweep-results.md`。

## 新增用例 T17：合并转发聊天记录（2026-10-24）

用户刚将一个合并转发记录发到文件传输助手。`get_messages("filehelper", limit=30)` 立即读到最新父消息：`local_id=122`、分片 `message__message_2.db`、香港时间 **2026-10-24 11:32:50**，工具类型为“文件/链接/卡片”。跨分片媒体候选的原始 local_type 为复合码（低 32 位为 49），原始 content 为 4,220 字符 XML，包含 `<recorditem>`。

只读解析该条 XML 后确认：`recorditem/recordinfo/datalist` 声明并实际包含 3 个子项：2 个文本子项（datatype 1）和 1 个图片子项（datatype 2）。3 个子项均有来源发送者及来源时间字段；文本摘要可读。图片子项包含 编码的 CDN 请求元数据/key（不是可直接请求的 HTTP URL）、MD5 与大小元数据，但不包含本地路径；按图片 MD5 在当前账号 `msg/attach` 根目录递归查找没有命中。样本中没有文件子项，因此“合并转发内嵌文件”尚未实测。

**结果：原始合并包读取 PASS；子项结构化解析由测试脚本只读 XML 确认，但库自身 NOT IMPLEMENTED；内嵌图片本机落盘 NOT FOUND；内嵌文件 NOT TESTED。** `get_messages()` 返回泛化父类型及原始 XML 字符串；源码当前没有解析 `<recorditem>` 的读取实现。对父消息调用现成 `MediaDownloader.download_media("filehelper", 122)` 实测返回 `None`。`get_message_rows_for_media()` 返回的同 local_id 候选原始类型是两个复合 49（`19<<32|49`、`6<<32|49`）及一个文本行；分发器只匹配裸 `49`，因此当前函数会漏过父卡片。即使将此父类型规范化，当前函数仍只会按普通文件消息处理，未见其递归读取合并记录内部 `dataitem` 的图片。数据中存在图片 CDN 元数据说明可继续实现/验证，但本轮未尝试远程下载。

重要结论：这个样本推翻了“合并转发可能完全没有技术上可行读取方式”的担忧——微信本地数据库中确实能读到合并 XML，文本子项和图片资源元数据也在其中。它仍证明不了当前库已把内容按产品所需完整可用地导出。

## 源码修复跟进：合并转发解析与复合类型（2026-10-24）

在登录中的微信 4.1.15.56 对真实父消息 local_id 122 / message__message_2.db 执行了只读核验：返回 3 子项，类型 text/image/text，来源时间 10:03:57、10:11:43、10:14:16 严格递增，图片 MD5 被解析；复合类型 19<<32|49 得到基础类型 49。语法编译检查通过。嵌套图下载仍返回 None：该 MD5 本机缓存未命中；父卡片不会被误当普通文件。没有运行自动化测试套件。嵌套文件 datatype 未取样，暂不声称已支持。详见综合报告“个人微信修复尝试”。

二次核查（用户点击后）发现：合并图片已写入微信专用缓存路径 msg/attach/<会话MD5>/2026-10/Rec/<记录标识>/Img/1，628,442 字节，V2 图片容器头；普通 hash.dat 缓存扫描因此漏检。源码已增加 Rec 缓存候选扫描并将以解密后 MD5 精确校验。当前解密仍未通过：图片 AES 密钥扫描未命中，db.cfg_dword 与本地 image_keys 缓存均无值；需保持图片大图在前台再捕获密钥。该文件目前只能确认是对应大小的 V2 容器，不能报告为已成功读取图片。

### 失败原因与修复点

1. 旧进程枚举先走 `tasklist`，本机实际返回访问被拒绝，导致扫描器看见 0 个微信 PID。Windows `Get-Process` 可以看见多个 `Weixin.exe`，且 `psutil` 枚举加 `OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION)` 可成功。本次源码改为优先用 `psutil.process_iter`，之后实际捕获并缓存图片 AES key；没有通过升权或改动客户端绕过这个问题。
2. 合并转发图片不在常规 `<MD5>.dat`/`_h.dat`/`_t.dat` 路径，而在微信 `msg/attach/.../2026-10/Rec/<记录标识>/Img/1`，没有扩展名。下载器之前只扫普通图片缓存，所以路径搜索漏掉了它。本次增加 Rec 目录和记录内图片序号搜索。
3. 通用 V2 图片解密器通常会先移除 24 字节容器页脚；微信子项 `fullmd5` 对应的是移除前的解密载荷，导致按旧通用流程校验必然不匹配。本次提供保留页脚的解密选项，先校验原始 fullmd5，再剥掉容器页脚输出实际图片。

### “必须先打开图片吗”与产品边界

这次打开图片的作用是触发当前客户端把合并转发子图片写入本机 `Rec` 缓存，并让当前登录进程中存在可捕获的图片密钥。它不是解析该消息正文的前提：正文、子项类型、原始时间、发送者和媒体元数据已直接从数据库内的 `recorditem` XML 读出。对产品工作流，若用户已经按业务要求在微信中点开/下载该图片，集成的读取器可以在之后扫描本机缓存、捕获/复用当前会话密钥、导出图片；本次成功证明该路径可行，不要求用户为了读取器再打开一次。

但这次实验**没有证明**一个从未在本机打开、尚未落入 `Rec` 缓存的合并转发图片可以只靠数据库字段自动获取。记录中的 `cdndataurl` 是二进制资源描述，不是 HTTP URL。要支持这种“完全未打开也后台获取”场景，需要另外实现微信 CDN/客户端媒体请求，尚未做通。密钥捕获目前实际在图片已打开的会话中验证；尚未证明登录后一次捕获即可适用于该账号以后所有图片、客户端重启后的行为或密钥轮换。
