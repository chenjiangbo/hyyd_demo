## 4. 附件文件名问题：实测数据与原因

### 4.1 用户观察与本机核验

用户给出的微信气泡截图显示一个 PDF 文件名，界面因气泡宽度截断中间部分，不能从截图判断本机去重后的后缀。此消息的原始文件名是 `dzfp_26612000001971446281_陕西轻住万禾酒店管理有限公司_20261001165146.pdf`；本地重名后的文件名是 `dzfp_26612000001971446281_陕西轻住万禾酒店管理有限公司_20261001165146(2).pdf`。用户提供了本机目录和完整文件名后，在 `F:\\WEBCHAT_FILE\\xwechat_files\\JiangBo_Chen1978_1235\\msg\\file\\2026-10` 找到带 `(2)` 的 PDF：大小 150,272 字节，开头为 `%PDF-`，是有效 PDF 文件。两个候选名（无 `(2)`、有 `(2)`）在该目录都存在；这也意味着不能仅凭“文件名相似”判断哪一个对应当前消息，必须使用消息的唯一标识/资源元数据关联。

### 4.2 `packed_info` 解析结果

`message_resource.db` 中与该消息 server ID 关联的 `MessageResourceDetail.packed_info` 是 protobuf 风格 length-delimited 二进制，不是普通 UTF-8 字符串。按其长度字段解析，本条结构为：

```text
outer field 1 (tag 0x0A), length 181
  inner field 1 (tag 0x0A), length 87: 原始文件名（无“(2)”）
  inner field 2 (tag 0x12), length 90: 本地重名文件名（带“(2)”）
```

也就是元数据分别保存了消息原始名称与本地另存名称。`0x0A`、`0x12` 是字段 tag；`0xB5 0x01`、`0x57`、`0x5A` 是 varint 长度编码。把整个二进制块直接 UTF-8 解码时，tag/长度字节会显示成 `\n`、`\x12`、`\x01`、`W`、`Z` 或替代字符 `�`。这些不是文件名中的字符，也不是 PDF 文件名真的包含控制字符。

当前源码 `_file_name()`（`sources/wechatauto-replica-main/wechatauto/media.py` 约第 1804–1827 行）对完整 `packed_info` 调用了 `.decode("utf-8", "replace")`，然后只移除 CR/LF/NUL，并把结果当成单个文件名返回。解码后的 Python `repr` 在清理前为：

```text
\n�\x01\nWdzfp_26612000001971446281_陕西轻住万禾酒店管理有限公司_20261001165146.pdf\x12Zdzfp_26612000001971446281_陕西轻住万禾酒店管理有限公司_20261001165146(2).pdf
```

经过当前代码的 `.strip()` 和 CR/LF/NUL 清理后，实际返回值可见形式为：

```text
�\x01Wdzfp_26612000001971446281_陕西轻住万禾酒店管理有限公司_20261001165146.pdf\x12Zdzfp_26612000001971446281_陕西轻住万禾酒店管理有限公司_20261001165146(2).pdf
```

因此它既不是正确的原名，也不是正确的本地名。`�` 是解码器替换非法 UTF-8 字节的显示符号。报告中的转义写法用于展示不可见控制字节；底层字符串不是反斜杠字母 `\\x12`，而是对应控制码字符。

### 4.3 4.1.15.56 回归：确认与此前相同根因

本轮复核不是只根据旧报告推断：读取目标消息原始行后，确认在 4.1.15.56 上仍是 `local_type=25769803825`（`0x600000031`，低 32 位 49）。对目标 `shard=message__message_2.db`，`get_message_row(..., shard=...)` 不带类型过滤能命中，传 `local_type=49` 则返回空。`_file_name()`（`media.py:1804`）在绕过这一入口限制后仍返回包含控制字符和 `U+FFFD` 的拼接字符串。三个 PDF 消息 local_id 119、92、81 均复现这些现象；这与此前观察一致。`download_file()`（`media.py:1829`）的 SQL 类型过滤和随后严格相等检查是首个阻塞点；`get_message_row()`（`db.py:2039`）按原始整数精确比较。

还有一个需在集成实现中保留的分片条件：local_id 不是全局唯一。实测 local_id 119 在 `message__message_0.db` 和 `message__message_2.db` 都有复合类型 25769803825 的消息，local_id 92 也在多个分片对应不同附件。因此必须从消息枚举结果携带 `(username, shard, local_id)` 到下载层；不能修好类型后再只靠 local_id 选行。当前 `download_media()`（`media.py:2245`）有传 shard 的意图，但它先按 `t == 49` 分发，复合类型在此处就被漏掉。数据库已有 `_msg_type_name()`（`db.py:2604`）能识别复合码显示名；媒体路由应复用/抽取同一类型归一化规则，而不要各处自行做裸值比较。

此 PDF 已经在用户本机文件目录中。函数源码只扫描 `account_dir\msg\file` 并复制匹配文件，不会触发微信端下载；本次失败应诊断为“消息行/缓存文件关联实现失败”，而不是文件未下载。

### 4.4 修复建议（未修改上游源码）

1. **统一消息类型识别。** 将 `db._msg_type_name()` 已用的复合码规则抽成共享的数值归一化 helper：对已知复合码取低 32 位，仅当结果是受支持的类型码时采用；`download_media()` 分发、`download_file()` 行校验和其它媒体函数统一使用。按 shard 先读取原始行，再校验归一化类型，不能先在 SQL 中用裸 `local_type=49` 把行筛掉。本样本须映射 `0x600000031` → 49；同时覆盖图片、语音、视频和未知包装值，避免误分类。不要简单地对所有值无条件 `& 0xff`。
2. **按 protobuf wire format 解析 `packed_info`。** 逐字段读取外层消息和内层名称字段，分别返回 `original_name` 与 `local_name`；遇到未知字段要跳过、长度越界/截断要显式报错。不能整块 `.decode("utf-8", "replace")`，也不能靠删除控制码掩盖格式错误。
3. **强制传递分片身份。** 媒体查询先取得全部原始候选，利用规范化类型分类，并以指定 `shard` 回读完整消息；接口层尽可能要求 `(username, shard, local_id)`，无法确定时返回歧义诊断，不静默拿最新同号记录。
4. **名称与本地文件关联分开处理。** 用 `local_name` 搜索对应月份缓存目录；保留 `original_name` 作消息展示。如果原名和本地重名名都存在，不得任选第一个。对匹配多个文件的情况，使用资源 ID/时间/大小或内容指纹进一步关联，无法唯一关联时返回 `ambiguous_local_file`。
5. **返回明确失败状态。** 区分 `message_row_not_found`、`not_file_type`、`resource_metadata_missing`、`filename_parse_failed`、`local_file_not_found`、`ambiguous_local_file`、`copy_failed`。已落地文件复制成功才返回路径；尚未落地时明确提示需用户在微信中点击下载。
6. **回归验收本机失败样本。** 用上述 3 条发票记录逐条核验：复合类型归一化、指定 shard 命中、原名/`(2)` 本地名解析、在 `F:\WEBCHAT_FILE\...\2026-10` 精确定位正确 PDF、输出路径可读且内容与本地源文件一致。同时使用其他分片同 local_id 的干扰行确保不串附件。

以上是对源码的修改建议，不是已执行修复；本轮按用户要求只分析并更新报告，没有改 `wechatauto-replica` 或寰宇医道项目代码。

## 5. 给集成开发 AI coder 的实现要求

以下是基于本轮发现建议的实现方向，不是已完成的代码修改。集成时应先围绕清晰的数据模型实现，再接入客户 Windows 客户端；本轮没有改寰宇医道项目。

### 5.1 文件消息解析/数据模型

- 以消息的 `server_id`（以及所属分片/会话信息）关联 `MessageResourceInfo` / `MessageResourceDetail`，避免只按本地 local_id 模糊命中。
- 按 protobuf wire format 读取 `packed_info`，逐层解析 length-delimited 字段和 varint 长度；不要把整块 bytes 当 UTF-8，也不要通过删除控制字符“修复”。优先使用已验证的 schema/协议定义；若项目没有 schema，应实现边界检查严格的 parser 并覆盖空字段、未知字段、截断长度、非法 UTF-8 等情况。
- 将原始文件名、微信本地保存名、已解析本地路径分开存储，例如 `original_name`、`local_name`、`local_path`。不要将两个候选名拼接为一个 `filename`。
- 文件名使用安全的 basename 规则，拒绝路径穿越和盘符/UNC 注入；解析失败应返回可诊断错误，不得把原始二进制生成的字符串拼到输出路径。

### 5.2 `local_type` 与消息行匹配

- 先用 local_id、shard 等定位消息行；再按实际数据库编码解读类型字段。该样本 `25769803825` 的低 8 位为 49，说明当前只按裸值 49 精确匹配不适用此行。
- 不要未经验证地对所有类型无差别 `& 0xff`：先确认高位在支持的微信版本/表结构中代表什么，至少记录原始值和归一化值；用消息资源记录交叉确认它是文件类型。
- 查询和返回错误应区分 `message_row_not_found`、`not_file_type`、`resource_metadata_missing`、`filename_parse_failed`、`local_file_not_found`、`copy_failed`，方便诊断而不是一律返回 `None`。

### 5.3 缓存关联与“下载”语义

- 对已经由用户在微信中下载到本机的文件，先在账户的 `msg/file/YYYY-MM` 缓存树中按本条资源记录查找；保留微信本地文件名（包括 `(2)`），并返回真实路径或复制后的路径。
- 原始名称用于 UI 展示；本地名称用于缓存查找。不能仅凭气泡显示名推断缓存名，也不能在多个重名候选都存在时随意选第一个。应优先依据本条消息资源记录、时间/文件指纹等稳定关联；若仍有多个匹配，返回歧义列表/诊断状态。
- “从缓存复制已下载文件”和“驱动微信下载尚未落地的大文件”应区分成两个操作/状态。当前本轮只证明了用户已经下载后的本地路径读取可行；没有证明内置函数能触发微信下载，也没有测试大文件下载流程。
- 若附件并未落地，清楚返回 `not_downloaded_locally` 或“需要用户在微信中点击下载”，并保留可再次扫描的路径；不要伪报下载成功。

### 5.4 建议验收用例

1. 同一文件名无冲突、已有缓存：返回正确消息的文件路径，文件内容与原文件一致。
2. 本地文件名冲突，元数据中原名与本地 `(2)` 名不同：原名、本地名分别解析；按当前消息返回正确的 `(2)` 文件。
3. 同一目录存在两个候选名：必须由消息资源关联到正确文件，不能只选 `os.walk()` 第一个结果。
4. `packed_info` 含未知字段、空值、截断 varint、越界长度、无效 UTF-8：安全失败并返回具体诊断，不崩溃、不生成带控制字符的路径。
5. `local_type` 为裸 49 及带高位包装的 `25769803825`：都能按明确验证的类型规则识别；非文件类型不得误收。
6. 已下载与未下载附件：已下载时返回本地路径；未下载时给出需用户操作的状态，用户点击下载后再次扫描可找到文件。
7. 覆盖 PDF、TXT、中文名、括号/空格、同名重复、不同月份目录；确保按 server ID/shard 关联而非只按文件名。

## 6. 企业微信测试结论

用户手动执行本机采集后，`wecom-archive` 0.0.11 在当前企业微信 **5.0.13.6005** 上完成一批 `windows-local-v1` 采集，状态为 `completed`。独立测试副本、loopback 服务和归档库均正常；SQLite `integrity_check=ok`。两次采集后归档 **2,958 条消息、117 个会话、196 个参与者、88 项媒体引用**，消息时间范围为 2025-03-21 10:23 至 2026-10-24 10:35（香港时间）。所有消息都有时间和发送者字段，117/117 个会话摘要的最新时间与归档消息最大时间一致。这证明本机现有缓存历史可读，不证明云端或任意联系人完整历史。

媒体能力为部分通过：88 项引用中 38 个本地文件通过大小与 SHA-256 校验，包括 33 张可完整解码的 JPEG/PNG 图片；3 个 ZIP/container 和 2 个 PDF 只检查了签名和完整性。其余 50 项（40 图片、10 文件）被标记 `not_found_in_authorized_media_roots`；另有 2 个媒体原名为空。界面/媒体表计数为 88，但批次 `media_count=0`。已读源码确认根因：`archive-store/src/ingest.rs` 批次 INSERT/完成 UPDATE 均未写该列，schema 默认值 0 留下；这是批次统计字段漏写，不代表媒体索引为 0。

时间字段与会话摘要一致性通过；用户截图中的一个会话片段时间递减且界面顺序合理，但未逐条与企微原生窗口校准。第二次手动全量重扫捕获了用户新发的合成消息，审计结果 `inserted=1, unchanged=2951, revised=6`，归档总数增加 1 且无重复累加；这不是 PC 最小化后台监听或游标增量验证。正文中有 1,190 条含 `[敏感数据已脱敏]`，其中 5 条完全被占位符替换、1,185 条部分替换；用户的“测试测试，不用理会”以完整正文入库。源码确认采集脱敏默认开启，且在入库前改写正文和 raw payload；需下一次取消脱敏重新采集才能恢复源值。

因此当前结论是：**历史本机缓存读取通过，手动重扫捕获新增并合并通过，时间顺序部分验证，图片/文件部分可用；最小化后台监听及媒体完整性未证实。** 完整数字、失败原因和下一轮操作见 [企业微信测试结果](wecom-test-results.md)。

## 10. 企业微信集成可行性（给集成开发 AI coder）

### 结论

**源码已取得且按 MIT License 开放；客户产品不需要启动或展示 `WeComArchive.exe`。** 该 EXE 只是本轮从源码构建出的测试应用。当前实测证明采集核心能在 Windows 企业微信 5.0.13.6005 上读出本机已缓存的 2,958 条消息/117 个会话；手动再次全量扫描时新增 1、未变 2,951、修订 6，归档行数没有重复累加。媒体目前 38/88 项验证可用、50 项缺失；默认脱敏又会在写入归档前替换敏感内容。以上表示源码可作为集成起点，进入产品前仍需抽取采集编排并补齐媒体定位、脱敏策略和同步模型。

### 可复用边界与集成方式

- 仓库为 Rust workspace，按 MIT License 授权；复用或改编时需保留版权和许可证文本。主要 crate 已分层：`source-windows`（Windows 数据源发现、只读快照/相关能力）、`message-parser`（消息归一化）、`archive-domain`（契约）、`archive-store`（归档存储）、`media-store`（媒体存储）、`archive-transfer`（导入/导出及脱敏）、`apps/server`（本机 API）。
- 本机完整源码位于 `outputs/hyyd-chat-poc/sources/wecom-archive-main`，仓库内含 `LICENSE`（MIT）；`outputs/hyyd-chat-poc/wecom-test-run/WeComArchive.exe` 是从这份源码构建的独立测试产物，不是唯一可用交付形式。客户可以只使用集成进自家产品的后台能力和自家 UI，不必看到或操作该测试 EXE。
- 实际收集编排和 `redact_sensitive_export` 目前位于 `src-tauri/src/lib.rs`；关键收集函数是应用内部私有函数，不是稳定公共 API。Tauri UI 不必复用，但需要把收集编排抽成产品内 Rust library/worker，并定义稳定输入输出、进度、取消和结构化错误。
- 如果客户 Windows 客户端本身基于 Rust/Tauri，可优先把成熟 crate 和抽出的 orchestration 纳入产品 native backend；如果产品是 C#/.NET、Qt 或其他栈，可将 Rust collector 做成版本化本地 worker，通过受限的 JSON/命名管道协议传递结果，再由产品层保存和展示。直接依赖 `WeComArchive.exe` 的 UI 自动化不适合作为正式集成接口。
- 推荐数据流：用户选择授权的数据根目录 → 发现登录账户对应的数据源 → 一致性只读快照 → 解密和消息解析 → 文件/图片定位与 SHA-256 校验 → 输出标准化消息及媒体状态 → 产品归档层合并、去重、保留修订。不要把本机绝对路径作为消息身份；以稳定 source/conversation/message ID 建键。

### 集成前必须补的能力

1. **脱敏策略：**本次库内 1,190/2,958 条含占位符，其中 5 条完全替换、1,185 条部分替换。默认脱敏值为 true，处理发生在导入前且覆盖正文/raw payload。若产品需求是完整原文，应按产品授权明确配置默认值，并让用户知道切换只影响新采集；对现有已脱敏记录做一次未脱敏重采集，实测 `revised` 更新后是否能恢复。
2. **媒体定位：**当前 88 项引用中 50 项不在授权媒体根目录；要用用户确认已在客户端打开/下载的一张图片和一份 PDF/TXT做前后对照，核对数据根目录、媒体根目录发现、原名、hash、missing 状态，再实现可诊断的“未下载/根目录未授权/缓存不存在/解析失败”。
3. **增量模型：**本次两个批次都是 `cursor_before=null` 并全量扫描；审计证明合并可避免重复行，但不是后台实时监听或水位增量。产品若要后台同步，需设计游标/水位、重叠窗口、稳定 ID 幂等和退出/重启恢复，再测试客户端最小化期间新增。
4. **消息完整性：**362 条消息被归为 `unsupported`。逐个盘点 raw type，决定产品需要的图片/语音/视频/撤回/小程序/红包/系统卡片映射；未解析消息需在 UI 明确展示原始类型/占位状态，不能误当文本丢弃。
5. **时间线：**本机时间字段完整，117/117 摘要匹配最新消息；用两条有明确先后关系的测试消息，对照企微原生窗口验证同秒/跨秒排序及显示时区。

### 缺失媒体逐条核查（2026-10-24）

已对 `archive.db` 中 50 个 `integrity=missing` 媒体引用逐条关联消息，完整清单见 [wecom-missing-media-audit.csv](wecom-missing-media-audit.csv)。样本时间为香港时间 **2025-04-02 至 2025-07-24**：40 条归档类型为 image、10 条为 file。用户检查后确认这些 file 的附件本机均未下载，因此这 10 条 missing 与本机无文件相符；仅 2 条 file 引用保留大小，分别约 262 MB 与 479 MB，其余 8 条没有大小字段。其余 40 条不能直接视为 40 张真实缺图：用户已针对清单第 33 条核对会话并提供截图，企微页面中没有相应图片。

有明显的元数据质量风险：部分归档为 image 的记录名是 `default-connect-logo.jpg`、`0`、`pdf.png`，也有 image 记录名带 `.xlsx` 或 `.mov`；这些值未必是企微界面显示的原始附件名。第 33 条具体记录为 `raw_type=4`、归档类型 image、资源名 `0`、无大小、无路径；会话截图未显示对应图片。源码 `crates/parser/src/lib.rs` 将 raw type `4` 无条件归为 image；`src-tauri/src/lib.rs` 对该类型走通用 metadata 文本路径，并可能把普通文本中的候选串补成 `media_path` 和 `name`。此证据说明第 33 条是**疑似错误分类/伪媒体引用**，不应记作“图片已从磁盘删除”。进一步核对全部媒体行发现，40 条 missing image 全部是 `raw_type=4`；而 33 条本机已验证的 image 全部是 `raw_type=14`。该强烈模式使这 40 项的类型映射/解析错误成为优先怀疑项，但第 33 条截图只能直接确认一个样本，尚不能据此断言另外 39 条都不是图片。集成修复应按真实消息结构识别图片，并要求有效的图片资源字段、可验证的本地路径或媒体哈希后才创建媒体引用；否则保留原始消息类型并标为未识别，不凭普通文本造图片附件。

源码实现先从已发现的企微候选数据源取得有限媒体根目录，再把数据账号根目录作为受限回退，递归建立本地文件索引；只用消息路径、名称、MD5/查找提示或消息 ID 匹配唯一文件。找不到时统一记为 `not_found_in_authorized_media_roots`。对于用户已确认本机未下载的文件，原因已清楚；第 33 条则是不同问题，说明图片计数中至少混入一条假媒体引用。剩余图片引用仍需抽查，才能区分本机缓存缺失和解析/分类问题。后续选择一张企微页面确实存在的图片，点击打开/下载并采集对比即可，不必手工核查全部 50 条。

### 合并转发聊天记录风险（2026-10-24）

用户提供了“李苏南和杨洋的历史消息”合并转发卡片截图。第 33 条 `raw_type=4` 记录解析出的内部文本与卡片预览内容高度吻合，但归档却把它保存为 `message_type=image`，`name=0`，且没有可定位媒体。由此更像是把合并转发卡片/其内部记录误当图片，而非真实图片下载失败。需要保留一个时间线疑点：该归档行时间为 **2025-05-27 15:56:12 HKT**，截图显示卡片附近时间为 **2025-05-26 15:45**；内容对应关系强，但尚未解释这一时间差，不应据截图声称消息 ID 与界面卡片已严格一一确认。

目前企微归档里该记录的 `body_text` 为空；若干内部文本只在 `raw_payload.text` 中出现，未转换为带各自发送者、时间、类型的子消息，也没有提取出合并记录内部的图片/文件结构。因此只能说有部分文本被解码到原始载荷，**不能证明合并转发内容被完整读取**。源码仓库搜索未发现对合并转发记录进行递归展开的实现；这是企微集成的明确待验收项。建议产品后端把此类记录建模为父级卡片 + 有序子消息（发送者、原发送时间、正文、附件引用），解析失败时保留原始卡片而不要伪造 image。

### 个人微信合并转发实测（2026-10-24）

用户将一条合并转发记录发到文件传输助手后，`wechatauto-replica` 读取到最新父消息 `local_id=122`、分片 `message__message_2.db`、香港时间 **2026-10-24 11:32:50**，类型显示为“文件/链接/卡片”。媒体 API 的候选原始 local_type 为复合码（低 32 位为 49）。消息 `content` 是 4,220 字符 XML，包含 `<recorditem>`。对该 XML 作只读结构解析发现 3 条子项：2 条文本（datatype 1）和 1 张图片（datatype 2）；每项都包含发送者和来源时间字段，图片项包含 编码的 CDN 请求元数据/key（不是可直接请求的 HTTP URL）、MD5、大小元数据。父消息本机 `msg/attach` 目录未找到按该图片 MD5 命名的文件。该样本没有文件子项。

### 两套源码的合并转发修复可行性（2026-10-24）

**结论（本节较早，当前状态见后文 2026-10-24 最新复测）：个人微信与企微的合并消息都已在本机真实样本中证明可解析。微信一条合并卡片内的图片在用户打开后已从本机 Rec 缓存解密导出；企微最新两条卡片均解析出文字和附件，本机图片与文件也按元数据核验成功。注意：企微采集/归档/UI 的完整媒体链路尚未接通，当前 0.0.11 EXE 未包含源码修改；微信内嵌合并文件尚无样本。

#### 个人微信 wechatauto-replica

修复入口与证据：

1. [wechatauto/db.py](sources/wechatauto-replica-main/wechatauto/db.py) 的 get_messages()/_export_row() 已把消息 content 原样交给调用方；本次在微信 4.1.15.56 的真实数据库中读到父卡片完整 <recorditem> XML，说明不需要再从 UI OCR 或凭空恢复内部正文。其 recordinfo/datalist 下的 3 个子项已经实测为 2 条文字和 1 条图片，且子项带来源发送者、时间；图片有 CDN 资源字段、MD5、大小。
2. 同一文件的 _msg_type_name() 已能把 4.x 包装类型取低 32 位显示为实际类型，但 [wechatauto/media.py](sources/wechatauto-replica-main/wechatauto/media.py) 的 download_media() 仍用 t == 49 裸值分发。本次候选类型 19<<32|49、6<<32|49 因而漏过。这是一个独立且明确的修复点：媒体路由和 SQL/行校验复用统一类型归一化函数，并携带 shard。
3. 仅修复类型判断仍不够：当前下载器把父卡片当作普通文件/链接处理，源码没有递归解析 <recorditem>/dataitem 的实现。应增加一个纯解析层，把父消息保留为“合并转发卡片”，按 XML 顺序输出有父 ID 关联的子消息（来源时间、发送者、文本/媒体类型、文件名/资源元数据）；嵌套媒体再走各自解析器。子消息原始时间用于记录内部排序，父卡片时间仍保留为外层消息时间，避免把两种时间混在一起。
4. 图片处理建议先按 MD5 查本机微信缓存，再对样本中的 CDN 字段实现单独的受控下载/解码适配；目前只证实这些字段存在，未证实本机缓存存在或 CDN 资源可成功下载。文件子项需要另取一个确实含文件的合并转发样本，确定 dataitem 的文件名、大小、MD5、下载 URL/本机路径字段；现阶段不应假设图片逻辑可直接复用到文件。

**个人微信可行性判断：高。** XML 原始包和内部文本/图片元数据已在本机真实样本中证实，主要工作是增加结构化解析、复合类型归一化和嵌套媒体解析。图片字节可获取性为“有线索、未验证”；嵌套文件为“未取样、未知”。

#### 企业微信 wecom-archive

当前采集器在 [src-tauri/src/lib.rs](sources/wecom-archive-main/src-tauri/src/lib.rs) 从源 message_table 读取 raw_type、content 与 local_extra_content 字节，然后调用 readable_message_payload()，再交给 parser 归一化。这是合适的源码修复边界：在原始字节还在手上时识别合并卡片并解析，而不是等通用解码把它压成普通 text/媒体字段后再猜。当前代码对 raw type 14/29 图片和 type 20 文件有专用解码，对 type 4 没有合并记录专用处理。

[crates/parser/src/lib.rs](sources/wecom-archive-main/crates/parser/src/lib.rs) 将 "4" 无条件分类为 Image；实测疑似卡片行因此产生 image/name=0。应先依据真实原始字节的结构签名区分“合并转发/历史记录卡片”与图片，不能只把 raw type 4 改成另一种固定类型，否则可能误伤真正的媒体类型。解码层应产出明确的 merged_forward 结构（父卡片 + 有序子项），必要时在 domain schema 中增加 message type/child message 表达；对未识别 payload 保留原始信息并归为 unsupported，禁止从普通文本猜造图片路径。

现有归档行第 33 条的内部文字与用户截图卡片预览相符，但归档时间与截图时间相差约一天；归档 DB 保存的是已转换的 raw_payload，不能单独证明当时的源 protobuf/二进制字段形状。因此企微的下一步不是盲写解析器：先从仍可访问的本机源 DB 只读提取这条原始行（至少保留 raw_type、content 长度/字段边界、local_extra 结构；不得把远程访问密钥写进报告），与一条真实图片 raw type 14 对照，再按字节结构编写 fixture 和解析。若源 DB 中原始卡片仅有链接或摘要，也应如实确定其可读边界。

**企业微信当前判断（更新于本报告末尾的真实复测）：** 两种合并卡片编码已经在本机源数据库中直接解析；新样本文字、图片、文件元数据和内部时间均读到，图片/文件缓存字节也核验成功。源码解析层有修复；媒体正式导出和桌面 UI 端到端仍待完成。

#### 建议的修复顺序与验收

1. 先各自实现“原始记录识别 + 有序子项解析”，暂不改下载流程。一个共同 fixture 至少覆盖文本、图片、文件、空/损坏子项和父子时间不同；断言子项数量、顺序、发送者、原时间、原文件名与资源元数据。
2. 先修微信复合 local_type 路由，再做本机图片缓存解析和嵌套文件解析；分别记录“元数据解析成功”与“媒体字节落地成功”，不能把前者当成后者。
3. 修企微 raw type 4 的结构识别与归档 schema，再拿真实客户端卡片逐条和 UI 对照；在解决样本时间偏差前，不以归档时间排序通过作为验收。
4. 最终两边都用含 text + image + file 的合并记录做端到端核验：卡片父子关系、内部时间顺序、原名、媒体 hash/大小、图片可打开、文件可读取，以及再次采集不重复。只靠源代码单元用例不足以证明当前客户端数据兼容。

这段记录的是修复开始前的阶段状态。后续已在两份本机源码副本内实施并验证修复尝试；没有修改上游/客户项目仓库，没有升级或降级客户端。当前状态和准确的源码文件清单见本报告末尾及 `ai-coder-handoff.md`。

### 个人微信修复尝试（2026-10-24，源码副本）

按实际样本实现了第一阶段的源码改动，文件仅位于 sources/wechatauto-replica-main：

**真实客户端核验：**在当前微信登录会话上调用新方法读取 parent local_id 122、shard message__message_2.db，成功返回 3 个子项，类型顺序 text/image/text，来源时间为 2026-10-23 10:03:57、10:11:43、10:14:16，按时间递增；内嵌图片 MD5 字段存在。4.x 复合类型 (19<<32)|49 归一化为 49。通用 download_media() 对父卡片返回 None（不会误走普通文件路径）；download_merged_forward_image() 也返回 None，证实该图片 MD5 对应档位当前不在本机可用缓存中。代码语法编译检查通过。未运行上游自动化测试套件，未改微信客户端/版本或客户项目。

**本阶段结论：**消息卡片及子项结构化读取已在本机样本通过；来源时间排序与复合类型识别通过；子项图片二进制仍未取到，本机缓存路径失败属“资源当前不存在/未缓存”，不是 XML 解析失败；合并记录内嵌文件还没有样本，尚未实现其 datatype 语义。下一步需一条确实含文件的合并转发样本，并对图片尝试先在微信里打开该转发卡片中的图片后再读本机缓存；若仍无缓存，再研究 CDN 取图或微信界面路径。

**媒体引用补充核验：**不能把 recorditem 的 cdndataurl/cdnthumburl 当作可直接访问的 HTTP URL。真实样本字段是 194 个十六进制字符，解码为 97 字节的二进制结构；其中没有可直接传给普通 HTTP downloader 的 URL。所以上述源码新增接口当前只检查本地加密缓存，不尝试 CDN 网络请求。将来若要补齐未缓存图片，需先逆向/实现微信图片资源请求结构或让微信客户端自身加载该卡片图片；不能把现有 CDN 元字段直接 GET。


### 合并记录图片缓存二次检查（用户点击图片后）

用户在微信中打开并点击了合并记录图片后，再次只读扫描发现微信确实写入了本机文件：位于该会话附件目录的 2026-10/Rec/<记录标识>/Img/1，无扩展名，大小 628,442 字节；记录子项声明 datasize 为 628,411 字节，文件头为微信 V2 图片容器格式。普通图片缓存查找器只搜 MD5.dat/_h.dat/_t.dat，因此漏掉了这个 Rec 专用目录与序号文件名。源码副本已扩展嵌套图片导出路径：搜索对应会话 Rec 缓存，解密后要求 MD5 匹配才落盘，避免把同序号的其它记录图片认错。

### 发现的开源解析缺口及本次修改

这两条新记录证明，当前企微客户端写入的合并转发格式与先前那批样本并不完全相同。旧解析逻辑把每个子项都当成 `field 101 → 内层字段 1 → 类型/正文` 结构；一旦子项是图片或文件，结构不符就会使整张合并卡片解析失败。这正是此前截图中“一张卡片被误当成图片/缺少内部内容”的具体原因之一，而不是客户端里没有消息。

本次在开源源码副本 `sources/wecom-archive-main/src-tauri/src/lib.rs` 中扩展了解析器，同时保留旧格式：

- 识别新观察到的子项 `field 5` 类型码：`2` 文字、`14` 图片、`15/16` 文件；文字正文在 `field 101`，媒体描述在 `field 103`。
- 输出每个子项的发送者、原始消息时间、类型和文字；合并卡片保持为一条外层消息，并按子项原始时间排序。
- 文件项读取文件名、大小和 MD5；图片项读取本次观察到的缓存查找 MD5、字节数和图像宽高，不把图片加密/远端访问材料放进报告或归档。

源码直接对本机最新两条数据库记录进行了实时解析，均得到 3/3 子项，文字和附件类型正确。子项时间也能正确保留：图片卡片为 2025-04-24 15:39:56、15:40:01 和 2025-04-27 09:38:20；文件卡片为 2025-04-24 15:24:27、15:26:51 和 16:56:22（香港时间）。
