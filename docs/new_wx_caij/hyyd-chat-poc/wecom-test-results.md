## 合并转发卡片补充核查（2026-10-24）

用户提供“李苏南和杨洋的历史消息”卡片截图。此前逐条媒体清单第 33 项来自会话 `鑫联智胜（北京）&共达地`，归档 row `source_message_id=1563`、香港时间 `2025-05-27 15:56:12`，原始类型 `4`，归档类型 `image`，资源名 `0`，大小/本地路径为空。raw payload 内解码出的聊天文字与截图卡片预览高度吻合，但卡片附近截图时间为 `2025-05-26 15:45`，因此仍有时间映射疑点。

源码会把 raw type `4` 无条件分类为图片，且该路径使用通用 metadata 文本解码/候选值猜路径。结合用户确认企微会话中未显示图片，该行很可能是合并转发/历史记录卡片被误判为图片，而不是一张未下载图片。40 条 missing image 全部 raw type 4，33 条 verified image 全部 raw type 14，其他 39 条 raw type 4 尚未逐项确认。企微版本的工具只在父消息 raw payload 留下部分文字，没有解析成带发送者、原始时间、正文、附件的嵌套子消息列表；合并卡片内部图片/文件读取未通过验证。

后续集成应把合并记录识别为父卡片并解析子记录，检查真实子消息类型后再创建附件引用；不应将任意 raw type 4 文本猜成图片。

## 企业微信合并转发修复实测（2026-10-24）

### 本轮结论

在企业微信客户端 **5.0.13.6005** 的当前登录数据上，已经从真实加密源数据库读取到 raw type `4` 的合并记录，并在 WeComArchive 源码副本实现了结构化展开。真实样本解析通过：历史子消息可以从一个父卡片内展开并按子消息 epoch 时间排序。原版本把该父卡片错误分类为图片，并为乱码字段生成了虚假的文件名 `0`/本地路径；改后父卡片不再生成图片媒体引用。

图片/文件的端到端读取目前**不能判为通过**：当前 11 条合并记录共 221 个子项中，有 1 个子项的类型码为 `3`，新解析器按现有顶层类型映射将它标为 image，但该子项只解出 4 字节资源字段 `[OK]`；父消息的本地附件元数据中找不到匹配路径，因此没有图片字节可导出。本批样本没有文件类型子项，文件原名、媒体路径和文件字节均未验证。当前用户界面也未用新代码运行核对，因此本轮通过的是数据库解密与源码解析链路，不能表述成已通过新版 GUI 展示或媒体下载。

### 原始样本和真实时间

- 客户端进程版本：`5.0.13.6005`（本机运行进程路径确认）。
- 使用 WeComArchive 自己的只读发现、一次性密钥探测、源数据库快照和只读解密路径；探测到当前会话的 5 个 WXWork 进程，获得 1 个可验证候选密钥。加密数据库必须经此路径打开，直接把源 `message.db` 当 SQLite 读会报 `file is not a database`，这属于加密格式，不是数据库损坏。
- 真实群会话样本 `source_message_id=1563`，会话与之前误报为图片的截图样本吻合；外层消息时间为 2025-05-27 15:56:12（香港时间），raw type `4`，原始 content 3,674 字节，SHA-256 `5eed1b66a37c384811aed084bbd7502430d85131519290a947433f2b4ea6f436`。
- 新解析器展开出 11 个子消息，子类型码均为 `0`（当前确认映射为文字）；内部时间从 2025-05-26 14:52:09 到 15:31:42（香港时间），严格非递减。生成的文本摘要长 823 字符。外层卡片时间与内层历史消息时间保存在各自字段，没有互相覆盖。
- 对当前数据库全部 11 条 raw type `4` 记录进行的只读扫描累计得到 221 个子项：220 个 code `0`，1 个 code `3`。唯一 code `3` 位于 `source_message_id=947` 的第 19 个原序位置，内部时间为 2025-04-24 14:05:01（香港时间）。其资源负载解出为 `[OK]`，按 raw type 映射标记为图片；从父消息本地附件索引未找到可访问媒体路径（命中数 0），所以没有证明图片内容可读。
- 221 个子项中没有观测到文件子项。不能据此宣称合并记录文件已支持或不支持；必须补一条实际含文件的企微合并记录才能确定编码和落盘路径。

### 源码副本中的修改

仅修改 `outputs/hyyd-chat-poc/sources/wecom-archive-main`：

1. `crates/parser/src/lib.rs` 不再把 raw type `4` 无条件分类为 Image。它保留 `Unsupported` 兼容状态，且不再从 `name/media_path` 误生成媒体引用；原始 payload 字段仍保留。
2. `src-tauri/src/lib.rs` 从原始 protobuf 中识别 raw type `4` 合并卡片：其 field 1 的重复记录项包含子发送者、子 epoch 时间和嵌套内容；识别到该结构后生成 `raw_payload.kind=merged_forward`、有序 `items`、原序号、sender id/name、来源时间、嵌套 type code 和文字内容。当前只确认 code `0`=text、code `3` 按现有顶层映射标记为 image；其余码保持 `unknown`，不臆断成文件。
3. `src-tauri/src/lib.rs` 的本地媒体路径扫描也不再把父卡片 raw type `4` 当普通媒体搜索，避免为父卡片创建错误的 `0` 文件引用。
4. 没有新增 schema enum；父级 `MessageV1.message_type` 保持 `unsupported` 以兼容现有 `message.v1`，子消息结构位于 `raw_payload.items`。集成端需要从这段结构读取子项；当前桌面 UI 是否渲染它尚未验证。
