## 时间字段与顺序的实测诊断

源码中的 `get_messages()` 明确按 `sort_seq` 降序合并分片，而不是按 `create_time` 排序。一个样本中，数据库 `sort_seq` 顺序内部有两对相邻消息的 `create_time` 相差 1 秒且方向相反：

- `local_id` 518：10:27:56，`sort_seq` 1792722477001；下一条 `local_id` 519：10:27:57，`sort_seq` 1792722477000。
- `local_id` 512：07:40:59，`sort_seq` 1792712460001；下一条 `local_id` 511：07:41:00，`sort_seq` 1792712460000。

用户已在微信界面核对 **2026-10-23 10:27:56–10:27:57** 与 **07:40:59–07:41:00** 附近消息，确认实际先后无误。因此本项按用户场景判为 **PASS**：工具返回顺序与微信实际顺序一致。秒级 `create_time` 在这两对相邻消息上差 1 秒且非单调，是时间字段粒度/记录值与 `sort_seq` 不完全一致；本轮没有发现用户可见顺序错误。集成应保留原始 `sort_seq` 与 `create_time`，以 `sort_seq` 维护消息先后，并把 `create_time` 用作显示时间；不应仅按秒级时间戳重排消息。

本轮时间核对结论依据用户在客户端的实际观察；报告记录了消息 ID 和时间，不包含这几条消息正文。
