# 设计：订单 AI 滚动简报（prompt + 输出结构）

> 状态：已实现并按 2026-06-22 讨论改为**全量重算 + 三触发（转写完成/静默5分钟/攒够10条微信企微消息）**。
> 目的：把"调 AI"的两个目的用**一份滚动简报、一次调用**同时办了：
>   1) 给寰宇员工有用的东西——**现状摘要 / 当前阶段 / 下一步 / 风险**；
>   2) 给系统回填——**结构化关键信息**（意向医院/科室/医生/就诊时间/主诉…）。
> 简报挂到订单生命周期轴上的合适位置（前端展示形态另议）。

---

## 1. 输入（喂给 AI 的东西）

一份简报 = 针对**一个订单**，综合它名下的全部沟通：

| 来源 | 表/字段 | 说明 |
|---|---|---|
| 微信/企微消息 | `Message`：`channel / senderName / contentText / capturedAt`（按 `orderId`） | 已由 sidecar+后端结构化、去重累积的对话流水 |
| **通话记录** | `Call`：`direction(in/out) / callStatus / durationSec / startedAt`（按 `orderId`） | 谁打的、接没接、多久、什么时候 |
| **通话录音转写** | `Call`：`asrText`（必要时 `asrResultJson` 的分段/说话人） | Fun-ASR 转写文本，是通话内容的主体 |
| 订单上下文 | `Order`：`customerName / hospital / dept / doctor / status / orderState` + `rawJson.serviceType / itemName`（**业务类型**：住院/护工/检查加急/门诊/接送/挂号/会诊…） | 已知信息，供 AI 参考、**不要照搬**；`serviceType` 让 AI 按业务类型正确理解"办理中"等通用阶段 |

> 通话和消息**统一按 `capturedAt`/`startedAt` 时间排成一条时间线**喂进去，让 AI 看到"先电话后微信"这种真实交付节奏。

### 全量重算（不做增量喂）
- **每次都把该订单全部的微信/企微消息 + 通话/录音转写 + 手工补录一起喂给 LLM**，重新产出整份简报。
  不做"只喂水位之后的新内容"那种增量喂——单个订单的信息量不大，全量更准，也不会出现"只总结了新增那几条"的问题。
- 仍给每个订单存一个**记号**（`briefLastMsgId / briefLastCallId / briefLastMaterialId` = 上次跑到的最新 id），
  但它**只用来判断"自上次以来有没有新内容"**（让扫描器避免对同一状态重复跑），**不参与裁剪喂给 LLM 的范围**。

> 两处展示同源：右侧「AI 关键信息」（`keyInfo` 等结构化字段）和需求沟通里的「AI 沟通总结」（`summary`）
> 是**同一份简报、同一次 LLM 调用**的两个视图，触发逻辑共用本节这套。

---

## 2. 触发策略（基线，已认可）

按"一段对话/通话有实质进展"让 LLM 跑一次全量总结，**不按帧、不死等、不重复**。满足任一即跑：

- **通话录音转写完成**：转写一完成就**立即**跑一次（电话信息量大，值得马上重做总结）。
  实现在 `asr/transcribeScheduler.ts` 转写 `done` 分支直接 `refreshOrderBrief(force)`，不靠定时扫描器。
- **静默 N 分钟**：该订单最后一条消息/通话过了 N 分钟没更新 → 跑一次。（**N=5**）
  跑完后记号推进到最新，没有新内容进来就不会再被选中 → **天然不重复**。
- **消息阈值 K**：自上次跑以来攒够 K 条**有内容的微信/企微消息** → 跑一次。（**K=10**）
  只数有内容的微信/企微消息——纯时间戳/系统提示/空消息**不计入** K。
- **手动按钮**：员工在订单详情点"刷新" → 立即跑（`force`）。
- **便宜预过滤**：自上次以来的新增若只有时间戳/系统提示/空转写 → **不调 LLM**，只把记号推进到最新（省钱、防重复）。

实现：一个后端定时扫描器（`jobs/orderBriefScheduler.ts`，参照 `asr/transcribeScheduler.ts`），每 ~1 分钟扫
"自上次以来有新内容 + 满足静默/阈值"的订单 → 调简报服务（全量重算）。手动按钮 + 转写完成走同一个 `refreshOrderBrief`。

## 3. 输出结构（固定 JSON，键不变）

```jsonc
{
  "summary": "一句话现状：客户为父亲(63岁)办住院护工，已约到周三入住并电话通知，待客户确认陪护班次",
  "stage": "已安排已通知",                  // 见 §5（6 个通用阶段之一）
  "stageEvidence": "6/12 通话告知已排周三床位+护工；客户未明确答复班次",  // 判此阶段的依据（可追溯）
  "hasOpenIssue": false,                    // 客户是否有未解决的问题/异议（横切，见 §5）
  "nextActions": ["确认客户接受的陪护班次", "若周三不便，重排床位"],
  "risks": ["客户两次催进度，情绪略急"],   // 风险/需关注；无则 []
  "keyInfo": {                              // ← 回填字段（目的1），通用集；没有填 null，禁止编造
    "目标医院": "北京天坛医院",
    "科室或病种": "神经内科 / 脑血管",
    "意向专家": null,
    "期望时间": "本周",
    "客户诉求": "为父亲安排住院期间护工陪护，希望尽快",
    "服务具体需求": "住院护工，男性父亲，需24小时陪护",  // 各业务的具体要求(护工班次/接送地址/会诊资料…)
    "病情或资料补充": "父亲63岁，曾抽烟已戒",
    "特殊要求": "希望快",
    "沟通偏好": "电话为主"
  },
  "updatedFrom": { "lastMessageId": 1234, "lastCallId": 56 }  // 本次处理到的水位（系统写，便于核对）
}
```

字段说明：
- `summary`：给员工看的一句话现状，**最重要**，必须人话、具体、含关键事实。
- `stage` / `stageEvidence`：当前阶段 + 依据。阶段变化即"明显阶段性成果"，可驱动 UI 高亮/通知。
- `hasOpenIssue`：客户是否有未解决问题（横切，见 §5）。
- `nextActions` / `risks`：给员工的行动项与提醒；无则空数组。
- `keyInfo`：回填字段，键固定（见下），没有填 `null`，**绝不编造**。
- 早期已确认的事实，新一轮**不得无依据地清空**（增量合并，只在有新证据时修正）。

`keyInfo` 固定键（**改为业务通用集**，不再是挂号专用；可再调）：
`目标医院 / 科室或病种 / 意向专家 / 期望时间 / 客户诉求 / 服务具体需求 / 病情或资料补充 / 特殊要求 / 沟通偏好`。
> 其中 `服务具体需求` 是通用兜底位：护工→班次/性别要求、接送→地址/时间、会诊→需哪些科室/资料、住院→床位/陪护…
> （旧的 `keyInfoService.FIELD_KEYS` 偏挂号，本简报取代它；若仍要单独的纯回填接口，键应同步成这套。）
>
> ⚠️ **这套键是占位**：真正"回填进系统"的字段由每种订单的**泰康/寰宇自有系统(ABI)回填接口**决定，
> 目前那块还没接。等接入时再把 `keyInfo` 的键对齐到各业务的真实回填字段；现在 AI 抽哪些不影响架构。

## 4. Prompt 设计

**System：**
```
你是寰宇医疗绿色通道服务的"订单助理"。下面是某订单的服务专员与客户之间的沟通记录，
来自三个渠道：微信/企业微信消息、电话通话记录、通话录音的转写文字。

注意：
- 文字来自屏幕 OCR 和语音转写，可能有错别字或个别识别错误，请按语义合理理解，不要被个别错字带偏。
- 说话人标注：消息里 [专员]=我方服务专员，[客户]=客户/群成员，[系统]=时间/系统提示；
  通话里 [去电]/[来电] 表示方向，转写文字未必分得清谁说的，按上下文判断。

你的任务：基于"上一版简报"和"本次新增的沟通"，**更新**这份订单简报，产出一个 JSON。
要求：
- 只输出一个 JSON 对象，不要解释、不要 Markdown、不要代码块标记。
- 给员工的部分（summary/stage/nextActions/risks）要具体、可执行，用中文短句。
- stage 只能取下面固定集合之一：<阶段枚举>。
- keyInfo 的键固定如下，没有的填 null，绝不编造：<字段键列表>。
- 增量更新：保留上一版里已确认的信息，只在有新证据时修正或补充；不要无依据地清空已知字段。
- JSON 结构如下（键固定）：<输出结构 schema>
```

**User：**
```
【已知订单信息（参考，不要照搬）】客户=…，业务类型=住院护工，医院=…，科室=…，医生=…，当前状态=…

【上一版简报（首次为空）】<上一版 JSON 或 "（无）">

【本次新增沟通（按时间先后）】
[2026-06-12 10:03 去电 时长2分钟] 转写：喂你好，是张先生吗…（asrText）
[2026-06-12 10:30 专员] 王医生周三的号约上了
[2026-06-12 10:31 客户] 好的我看看时间
[2026-06-12 14:00 系统] 14:00
…
```

> 实现要点：把 `Message` 与 `Call` 合并成上面这种**带角色 + 时间**的行；通话用 `direction`→去电/来电、`startedAt`、`durationSec`，正文用 `asrText`。

## 5. 阶段枚举（粗粒度、跨所有业务类型通用）

> 背景：库里绿通订单 304 单，业务类型很多——住院、住院护工、检查加急、全程门诊、就医接送、
> 挂号协助、MDT会诊、电话问诊、出院陪护…（挂号只占少数）。所以阶段**不能按"挂号"设计**，
> 要抽一套**所有业务通用**的"服务交付生命周期"，粗一点。各业务的差异交给 AI 看 `serviceType`
> 自己理解（比如"办理中"对挂号=约号、对护工=派护工、对接送=排车）。

**6 个主阶段（任何绿通业务都走这条线）：**
1. `待跟进` —— 已接单，尚未实质联系客户
2. `沟通中` —— 了解需求/病情、收集资料、确认服务内容（对应"需求沟通清楚"的过程）
3. `办理中` —— 我方协调资源/安排服务（约号/排床/约专家/派护工/排接送…，**各业务通用的"我方在办"**）
4. `已安排已通知` —— 已安排妥并通知客户，等客户确认或等到执行日（对应"挂号完成并通知客户"）
5. `服务执行中` —— 实际服务进行中（就诊/住院/护工在岗/接送中/会诊中…）
6. `已完成` —— 服务交付完成

**横切标记（不占主阶段，任何阶段都可能）：**
- `hasOpenIssue`（布尔）：客户反馈了**尚未解决**的问题/异议/投诉。处理并获客户认可后置回 false。
  —— 这样"客户反馈问题→已处理→认可"不用为每种业务塞一堆问题阶段，正好简化。

> 要不要这套 6 阶段 + 问题 flag？可再合并（如把 4、5 合成"执行中"）。定了我写进 prompt 和类型。

## 6. 存储与接口

**存储**（建议）：给 `Order` 加 `aiBriefJson Json?`（存整份简报）+ `briefUpdatedAt` + 水位 `briefLastMsgId / briefLastCallId`。
（现有 `AiSummary` 表是"一次性文本摘要"，结构化滚动简报用 `Order.aiBriefJson` 更合适；二者不冲突。）

**接口**：
- `POST /api/v1/orders/:id/brief/refresh` —— 手动按钮用：取该订单累积对话+通话 → 调简报服务 → 写回。
- 定时扫描器内部直接调简报服务（不走 HTTP）。
- `GET` 订单详情时把 `aiBriefJson` 一起返回，前端挂到生命周期轴。

**服务**：新增 `src/llm/orderBriefService.ts`：`buildBrief(order, prevBrief, newMessages, newCalls) → Brief`，内部拼时间线 + 调 `chat()`（百炼，复用 `gatewayClient`）。说话人/结构化已在上游做好，这里同 `keyInfoService` 一样**只做文本理解**，不碰 VLM。

## 7. 成本与边界
- 四道闸（增量喂 + 阈值 K + 静默 N + 预过滤）→ 实际"每段对话有实质进展时调一次"，不是每帧、不是死等。
- 通话转写（asrText）可能很长 → 喂之前可对**超长单通**做截断/分段（保留首尾 + 关键段），后续按需。
- LLM 只在后端调（铁律），tray-app/sidecar 不碰。
