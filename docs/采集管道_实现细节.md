# 采集管道 · 当前实现细节

> 更新时间：2026-06-16
>
> 本文档只描述**当前代码已实现**的正式链路，不保留旧方案和“目标设计”措辞。

## 一、进程与职责

| 名称 | 代码位置 | 职责 |
|---|---|---|
| sidecar | `packages/capture-sidecar` | 截图、OCR、聊天区分区、气泡扫描、消息结构化 |
| tray-app 主进程 | `packages/tray-app/src/main` | 接收 sidecar 帧、写本地 SQLite、上报后端 |
| 后端 | `packages/backend` | 订单关联、消息入 PostgreSQL |

当前正式链路：

```text
微信 / 企微窗口激活
  -> sidecar 截图
  -> sidecar OCR
  -> sidecar 分区 + 标题识别 + 气泡扫描 + 结构化
  -> tray-app 主进程接收 frame JSON
  -> 本地 SQLite 入库
  -> 后端做订单关联并存库
```

后端**不再做消息结构化**。结构化成品由 sidecar 直接产出。

## 二、sidecar 触发与截图

入口：`CaptureCollector.cs`

触发源：

- 前台窗口切换 `foreground`
- 键盘 Enter `key-enter`
- 鼠标左键松开 `click`
- 鼠标滚轮 `wheel`
- 定时兜底 `interval`

约束：

- 600ms 尾沿防抖
- 1 秒最小截图间隔
- `interval` 触发时，最近 2500ms 仍在打字则跳过

窗口识别：`WindowInspector.cs`

- 只认 `Weixin.exe` / `WeChat.exe` / `WXWork.exe`
- 过滤 owner 窗口、tool window、小弹窗
- `GetWindowText` 不再参与会话标题判断

截图：`WindowCapture.cs`

- 用 `Graphics.CopyFromScreen`
- 落盘目录：

```text
%LOCALAPPDATA%\HyydCaptureSidecar\frames\{yyyy-MM-dd}\{timestamp}-{channel}-{hash}.png
```

## 三、OCR

入口：`RapidOcrEngine.cs`

当前正式 OCR：

- `RapidOcrNet`
- ONNX Runtime
- PP-OCRv5 中文模型

模型文件：

- `models/v5/ch_PP-OCRv5_det_mobile.onnx`
- `models/v5/ch_PP-LCNet_x0_25_textline_ori_cls_mobile.onnx`
- `models/v5/ch_PP-OCRv5_rec_mobile.onnx`
- `models/v5/ppocrv5_dict.txt`

构建前由 `scripts/ensure-sidecar-ocr-models.js` 保证存在并校验 SHA256。

当前 RapidOCR 输出已经是**行级框**。因此 sidecar 不再把多个 OCR 块重新拼成一行，当前实现里**每个 OCR 块直接视为一行文本**。

## 四、聊天区分区

入口：`MessageStructurer.DetectChatXRange`

### 4.1 左界 `chatX0`

思路：利用联系人列表右边界的重复值，而不是依赖“大空白列”。

步骤：

1. 先取窗口左侧 OCR 块，排除最左图标栏。
2. 由于 OCR 已是行级框，每个 OCR 块直接当作一行。
3. 统计这些行的右端 `MaxX`。
4. 从最大 `MaxX` 开始向下找，至少出现 2 次的值视为联系人列表右边界。
5. `chatX0 = contactRight + HYYD_CHAT_LEFT_PADDING`，默认 `15px`。

如果找不到可复用的联系人右界，直接报错，不做兜底猜测。

### 4.2 右界 `chatX1`

- 微信 `wechat`
  - `chatX1 = windowWidth`
- 企微 `wxwork`
  - 如果 OCR 识别到“群成员”，取该文字起始 X 为 `chatX1`
  - 否则 `chatX1 = windowWidth`

当前不对企微右侧成员区做二级推断。

## 五、标题与客户会话判断

入口：`MessageStructurer.Build`

步骤：

1. 先切出聊天区内 OCR 行。
2. 跳过窗口顶部系统按钮区域后，`MinY` 最小的那一行就是标题。

标题用途：

- 作为 `FramePayload.title`
- 作为客户会话判断依据
- 作为单聊订单号候选提取来源

客户会话判断规则：

- 标题含 `就医服务群` -> `conversationKind = "group"`
- 标题命中订单号正则 -> `conversationKind = "single"`，并抽 `orderNo`
- 两者都不命中 -> 非客户会话

订单号只在标题找，不在消息正文里找。

## 六、气泡扫描

入口：`MessageStructurer.DetectBubbleRegions`

这是当前结构化链路的核心。

### 6.1 扫描范围

扫描只在聊天区内进行：

- `x = [chatX0, chatX1)`
- `y = [scanY0, scanY1)`

其中：

- `scanY0 = 标题行下方`
- `scanY1`
  - 优先取“发送”按钮行的上方
  - 没识别到“发送”时，取窗口高度的一个保守下界

### 6.2 颜色桶

当前按渠道分两套：

#### 微信 `wechat`

- 左侧灰气泡：接近 `RGB(238,238,239/240)` 的中性浅灰
- 右侧 self 气泡：接近 `RGB(157,242,159)` 的浅绿

#### 企微 `wxwork`

- 当前样本中 self 气泡是浅蓝，大致范围：
  - `R 188~215`
  - `G 220~240`
  - `B 248~255`

当前正式实现里，企微气泡扫描主要针对这类浅蓝消息气泡。

### 6.3 连通域流程

对命中颜色的像素：

1. 膨胀 `radius = 3`
2. 腐蚀 `radius = 2`
3. 4 邻域 BFS 连通域
4. 计算包围盒
5. 统计每一行像素数量
6. 用“实心行阈值”裁掉上下抗锯齿毛边

### 6.4 几何过滤

入口：`IsLikelyBubbleRegion`

当前会过滤掉这些明显不是气泡的区域：

- 过小块：`w <= 45 && h <= 45`
- 很扁的小横条：时间旁浅灰抗锯齿条
- 很细长的竖条：输入框两侧白边
- 紧贴聊天区左右边缘、同时又很窄的竖向碎片
- 聊天区底部的细长竖条

当前这些过滤只基于**连通域几何形状**，不参与分区和标题判断。

## 七、正式消息结构化

入口：`MessageStructurer.Build`

正式链路：

1. 分区，得到聊天区
2. 取聊天区 OCR 行
3. 找标题
4. 找“发送”按钮行
5. 过滤“发送”同行及其下方 OCR
6. 调 `DetectBubbleRegions` 得到气泡区域
7. 把 OCR 行按“中心点是否落在气泡包围盒内”归到气泡
8. 根据气泡位置判 `self / other`
9. 对 `other` 再找发送人
10. 剩余没进气泡、且相对居中的 OCR 行判 `system`

### 7.1 OCR 行是否属于气泡正文

规则：`LineInsideRegion`

判据很简单：

- OCR 行中心点 `CenterX / CenterY`
- 落在气泡框内（带少量 padding）

这一步之后：

- 在气泡里的 OCR 行 = 正文候选
- 不在任何气泡里的 OCR 行 = 非正文候选

### 7.2 说话人 `speaker`

当前正式实现只看气泡位置，不再用颜色样本或 HSV 辅助。

规则：

- `region.CenterX >= midX` -> `self`
- `region.CenterX < midX` -> `other`

### 7.3 发送人 `name`

只对 `other` 气泡做。

第一步：找气泡外上方的候选行 `FindSenderNameForRegion`

约束：

- 在当前气泡上方
- 到气泡顶部距离不超过约 `2.4 * lineH`
- 在聊天区左半边
- `MinX` 与当前气泡左界接近
- 文本短
- 非系统、非时间、非链接

第二步：如果没找到，再看 OCR 是否把发送人压进了气泡顶部

入口：`PromoteOverlappingSenderName`

规则：

- 气泡至少有 2 行正文
- 第一行非常贴近气泡顶部
- 第一行文本满足“像发送人”的基本条件

满足则：

- `sender = firstLine.Text`
- 并把这行从正文里移除

### 7.4 system

入口：`IsCenteredSystemLine`

system 只从**没进任何气泡**的 OCR 行里产生。

条件：

- 相对聊天区中心足够近
- 行宽不能太宽

再细分：

- 命中 `TimeLine` -> `system:time`
- 命中 `SystemKeyword` -> `system:notice`
- 否则 -> `system:other`

## 八、输入区

当前输入区不再走旧的“切线算法”。

正式链路只保留一条轻规则：

- 如果 OCR 识别出“发送”按钮，则“发送”这一行以及其下方 OCR 视为输入区噪声，不参与正文。

输入区的其它误检，靠：

- `scanY1`
- `IsLikelyBubbleRegion`

来压制。

## 九、sidecar 输出

sidecar 通过 stdout 输出 `FramePayload` JSON。

关键字段：

- `title`
- `conversationKind`
- `orderNo`
- `messages`
- `ocr.blocks`
- `chatX0`
- `chatX1`
- `droppedBlockCount`

说明：

- `messages` 是正式结构化结果
- `ocr.blocks` 保留给调试页画框
- `InputCutY / InputCut` 目前正式链路不再使用，当前返回仍保留字段，但值为 `null`

## 十、tray-app 主进程

入口：`capture-sidecar-client.ts`

当前职责：

1. 接收 sidecar frame
2. 存调试环形缓冲
3. 写本地 SQLite
4. 逐条上报新消息给后端

当前不再调用后端 `/api/v1/capture/structure` 做二次结构化。

## 十一、tray-app 采集调试页

入口：`packages/tray-app/src/renderer/src/v2/pages/SidecarDebugPage.tsx`

采集调试页的「OCR 识别」标签用于验证 sidecar 结构化结果，不参与正式数据处理。

当前展示内容：

- 原始 OCR 行列表：展示 `ocr.blocks` 的文本、坐标、尺寸和置信度，便于复制给 AI 分析。
- 分区线：展示 `chatX0 / chatX1`，用于确认聊天区是否切准。
- 气泡框：来自 sidecar `messages[].box`，按 `self / other / system` 用不同颜色标识。
- 正文归属：OCR 行中心点落入某个 `message.box` 时，在调试页视为该消息正文。
- 发送人标识：调试页按 sidecar 的 `sender` 字段，在对应 other 气泡上方寻找匹配 OCR 行并标紫色框。
- system 标识：sidecar 输出的 `system:time / system:notice / system:other` 会以系统消息样式展示。

说明：

- 调试页只渲染 sidecar 的结果，不重新判定消息。
- 如果调试页显示错误，优先回到 sidecar 的分区、气泡扫描、sender 识别逻辑排查。
- `InputCutY / InputCut` 旧输入区切线字段仍可能存在于类型里，但当前正式链路不依赖它。

## 十二、后端

入口：`packages/backend/src/routes/api.ts`

后端当前职责：

- 认证员工
- 根据 `orderNo` / `conversationName` 做订单关联
- 消息入 PostgreSQL

后端不再负责：

- 分区
- 气泡扫描
- sender 判定
- system 判定

## 十三、当前实现的关键结论

1. RapidOCR 已经是行级结果，sidecar 不再做复杂“拼行”。
2. 结构化链路现在是“先找气泡，再判消息/发送人/system”。
3. `self / other` 由气泡位置决定，不再依赖颜色样本辅助。
4. 真正需要持续调的核心只剩两块：
   - 聊天区分区
   - 气泡扫描与几何过滤
