# 采集管道 · 当前实现细节

> 更新时间：2026-06-16
>
> 本文档只描述**当前代码已实现**的正式链路，不保留旧方案和“目标设计”措辞。

## 一、进程与职责

| 名称 | 代码位置 | 职责 |
|---|---|---|
| sidecar | `packages/capture-sidecar` | 截图、OCR、聊天区分区、气泡扫描、消息结构化 |
| tray-app 主进程 | `packages/tray-app/src/main` | 接收 sidecar 帧、写本地 SQLite、上报后端 |
| 后端 | `packages/backend` | 订单关联、消息入 PostgreSQL |

当前正式链路：

```text
微信 / 企微窗口激活
  -> sidecar 截图
  -> sidecar OCR
  -> sidecar 分区 + 标题识别 + 气泡扫描 + 结构化
  -> tray-app 主进程接收 frame JSON
  -> 本地 SQLite 入库
  -> 后端做订单关联并存库
```

后端**不再做消息结构化**。结构化成品由 sidecar 直接产出。

## 二、sidecar 触发与截图

入口：`CaptureCollector.cs`

触发源：

- 前台窗口切换 `foreground`
- 键盘 Enter `key-enter`
- 鼠标左键松开 `click`
- 鼠标滚轮 `wheel`
- 定时兜底 `interval`

约束：

- 600ms 尾沿防抖
- 1 秒最小截图间隔
- `interval` 触发时，最近 2500ms 仍在打字则跳过

窗口识别：`WindowInspector.cs`

- 只认 `Weixin.exe` / `WeChat.exe` / `WXWork.exe`
- 过滤 owner 窗口、tool window、小弹窗
- `GetWindowText` 不再参与会话标题判断

截图：`WindowCapture.cs`

- 用 `Graphics.CopyFromScreen`
- 落盘目录：

```text
%LOCALAPPDATA%\HyydCaptureSidecar\frames\{yyyy-MM-dd}\{timestamp}-{channel}-{hash}.png
```

## 三、OCR

入口：`RapidOcrEngine.cs`

当前正式 OCR：

- `RapidOcrNet`
- ONNX Runtime
- PP-OCRv5 中文模型

模型文件：

- `models/v5/ch_PP-OCRv5_det_mobile.onnx`
- `models/v5/ch_PP-LCNet_x0_25_textline_ori_cls_mobile.onnx`
- `models/v5/ch_PP-OCRv5_rec_mobile.onnx`
- `models/v5/ppocrv5_dict.txt`

构建前由 `scripts/ensure-sidecar-ocr-models.js` 保证存在并校验 SHA256。

当前 RapidOCR 输出已经是**行级框**。因此 sidecar 不再把多个 OCR 块重新拼成一行，当前实现里**每个 OCR 块直接视为一行文本**。

## 四、聊天区分区

入口：`MessageStructurer.DetectChatXRange`

### 4.1 左界 `chatX0`

思路：利用联系人列表右边界的重复值，而不是依赖“大空白列”。

步骤：

1. 先取窗口左侧 OCR 块，排除最左图标栏。
2. 由于 OCR 已是行级框，每个 OCR 块直接当作一行。
3. 统计这些行的右端 `MaxX`。
4. 把 `MaxX` 排序后做**相邻聚类**：相差 ≤ `HYYD_CONTACT_RIGHT_TOLERANCE`（默认 `2px`）的归为同一条右边界。取**支持行数最多**（≥ `HYYD_CONTACT_RIGHT_MIN_SUPPORT`，默认 2）的那一簇作为联系人右界——联系人列表每行右侧有右对齐的时间戳，十几行对齐成一条线，行数远多于聊天区里偶尔凑齐的两三条；**不取"最靠右"那簇**，否则聊天区短消息的巧合对齐会被误选、把 `chatX0` 推进聊天区。同分行数时取更靠右者，`contactRight` = 该簇里最大的真实 `MaxX`。
5. `chatX0 = contactRight + HYYD_CHAT_LEFT_PADDING`，默认 `15px`。

如果找不到达标的桶，抛异常——但**不再吞掉整帧**：异常被上层捕获，原图+OCR 仍输出给调试页，异常堆栈随帧带到调试页右侧（见 §十一）。

### 4.2 右界 `chatX1`

- 微信 `wechat`
  - `chatX1 = windowWidth`
- 企微 `wxwork`
  - 取右侧成员区里“发送企业名片”按钮的“**企业名片**”几个字定位（真实企微没有“群成员”字样）；命中行里最靠左的 X = 成员区左界 = `chatX1`。关键词可用 `HYYD_WXWORK_MEMBER_KEYWORD` 覆盖。
  - 否则 `chatX1 = windowWidth`

当前不对企微右侧成员区做二级推断。

## 五、标题与客户会话判断

入口：`MessageStructurer.Build` 出标题，`CaptureCollector.ClassifyTitle` 做客户会话判断。

步骤：

1. 先切出聊天区内 OCR 行。
2. 跳过窗口顶部系统按钮区域后，`MinY` 最小的那一行就是标题。

标题用途：

- 作为 `FramePayload.title`
- 作为客户会话判断依据
- 作为订单号候选提取来源

客户会话判断规则（`ClassifyTitle`，匹配前先把标题里所有空白删掉——OCR 常在字符间塞空格）：

- **群聊关键词**：标题含 `就医服务群`（可用 `HYYD_CAPTURE_TITLE_KEYWORDS` 覆盖，逗号分隔）→ `conversationKind = "group"`。
- **订单号正则**：不分群聊单聊，都跑同一条正则抽订单号（IgnoreCase 容忍大小写）：
  - 高客：`fwyy` + 6~24 位 `[0-9a-z|]`
  - 普客：`CCOD` / `COD` / `OD` + 12~18 位 `[0-9a-z|]`
  - 没命中群关键词、但抽到订单号 → `conversationKind = "single"`。
- `isCustomer = 含群关键词 或 抽到订单号`。两者都不命中（含标题为空）→ 非客户会话，丢弃。

注意：

- **群聊和单聊都带订单号**，"就医服务群"关键词只决定 `kind`，不决定有没有订单号。
- 订单号只在标题找，不在消息正文里找。
- 这里抽出的是**含 OCR 噪声的订单号候选**（`fwyy1` 可能读成 `fwyyl`、hex 位认成字母）。sidecar / tray-app **不做订单匹配**，只把候选随消息上报；**由后端负责归一 + 误差（编辑距离）匹配到真实订单**（见 §十二）。

## 六、气泡扫描

入口：`MessageStructurer.DetectBubbleRegions`

这是当前结构化链路的核心。

### 6.1 扫描范围

扫描只在聊天区内进行：

- `x = [chatX0, chatX1)`
- `y = [scanY0, scanY1)`

其中：

- `scanY0 = 标题行下方`
- `scanY1`
  - 优先取“发送”按钮行的上方
  - 没识别到“发送”时，取窗口高度的一个保守下界

### 6.2 颜色桶

当前按渠道分两套：

#### 微信 `wechat`

- 左侧灰气泡：接近 `RGB(238,238,239/240)` 的中性浅灰
- 右侧 self 气泡：接近 `RGB(157,242,159)` 的浅绿

#### 企微 `wxwork`

- 当前样本中 self 气泡是浅蓝，大致范围：
  - `R 188~215`
  - `G 220~240`
  - `B 248~255`

当前正式实现里，企微气泡扫描主要针对这类浅蓝消息气泡。

### 6.3 连通域流程

对命中颜色的像素：

1. 膨胀 `radius = 3`
2. 腐蚀 `radius = 2`
3. 4 邻域 BFS 连通域
4. 计算包围盒
5. 统计每一行像素数量
6. 用“实心行阈值”裁掉上下抗锯齿毛边

### 6.4 几何过滤

入口：`IsLikelyBubbleRegion`

当前会过滤掉这些明显不是气泡的区域：

- 过小块：`w <= 45 && h <= 45`
- 很扁的小横条：时间旁浅灰抗锯齿条
- 很细长的竖条：输入框两侧白边
- 紧贴聊天区左右边缘、同时又很窄的竖向碎片
- 聊天区底部的细长竖条

当前这些过滤只基于**连通域几何形状**，不参与分区和标题判断。

## 七、正式消息结构化

入口：`MessageStructurer.Build`

正式链路：

1. 分区，得到聊天区
2. 取聊天区 OCR 行
3. 找标题
4. 找“发送”按钮行
5. 过滤“发送”同行及其下方 OCR
6. 调 `DetectBubbleRegions` 得到气泡区域
7. 把 OCR 行按“中心点是否落在气泡包围盒内”归到气泡
8. 根据**气泡颜色**判 `self / other`（self/other 分色各扫连通域，不看位置——见 §7.2）
9. 对 `other` 再找发送人
10. 剩余没进气泡、且相对居中的 OCR 行判 `system`

### 7.1 OCR 行是否属于气泡正文

规则：`LineInsideRegion`

判据很简单：

- OCR 行中心点 `CenterX / CenterY`
- 落在气泡框内（带少量 padding）

这一步之后：

- 在气泡里的 OCR 行 = 正文候选
- 不在任何气泡里的 OCR 行 = 非正文候选

### 7.2 说话人 `speaker`

**按气泡颜色判定，不看位置**（位置/中心点判定试过多次都不稳：长消息会越过中线、合并的连通域中心无意义）。

做法：self 和 other 各用自己的基准色**分别**做连通域（互不合并），气泡来自哪种颜色就是谁说的：

- 命中 self 色（企微浅蓝 `#C9E7FF` / 微信浅绿 `#9DF29F`）-> `self`
- 命中 other 色（企微浅灰 `#E4E7EB` / 微信浅灰 `#EEEEF0`）-> `other`

分开扫的关键作用：一条左边的灰 other 气泡和一条右边的蓝 self 气泡，再挨着也不会被膨胀粘成一个跨整宽的大块（旧实现就是因为蓝灰同一张 mask 被粘起来、中心落在左侧而把 self 误判成 other）。色值带容差兼容显示器色差（见 §6.2）。

### 7.3 发送人 `name`

只对 `other` 气泡做。

第一步：找气泡外上方的候选行 `FindSenderNameForRegion`

约束：

- 在当前气泡上方
- 到气泡顶部距离不超过约 `2.4 * lineH`
- 在聊天区左半边
- `MinX` 与当前气泡左界接近
- 文本短
- 非系统、非时间、非链接

第二步：如果没找到，再看 OCR 是否把发送人压进了气泡顶部

入口：`PromoteOverlappingSenderName`

规则：

- 气泡至少有 2 行正文
- 第一行非常贴近气泡顶部
- 第一行文本满足“像发送人”的基本条件

满足则：

- `sender = firstLine.Text`
- 并把这行从正文里移除

### 7.4 system

入口：`IsCenteredSystemLine`

system 只从**没进任何气泡**的 OCR 行里产生。

条件：

- 相对聊天区中心足够近
- 行宽不能太宽

再细分：

- 命中 `TimeLine` -> `system:time`
- 命中 `SystemKeyword` -> `system:notice`
- 否则 -> `system:other`

## 八、输入区

当前输入区不再走旧的“切线算法”。

正式链路只保留一条轻规则：

- 如果 OCR 识别出“发送”按钮，则“发送”这一行以及其下方 OCR 视为输入区噪声，不参与正文。

输入区的其它误检，靠：

- `scanY1`
- `IsLikelyBubbleRegion`

来压制。

## 九、sidecar 输出

sidecar 通过 stdout 输出 `FramePayload` JSON。

关键字段：

- `title`
- `conversationKind`
- `orderNo`
- `messages`
- `ocr.blocks`
- `chatX0`
- `chatX1`
- `droppedBlockCount`
- `structureError`

说明：

- `messages` 是正式结构化结果
- `ocr.blocks` 保留给调试页画框
- `InputCutY / InputCut` 目前正式链路不再使用，当前返回仍保留字段，但值为 `null`
- `structureError`：分区/气泡检测抛异常时的异常文本（含堆栈）。非空时该帧 `messages` 为空、`title=null`（会落到非客户路径），但仍输出，保留原图+OCR 供调试。正常帧为 `null`。**结构化失败不再整帧丢弃**，避免最该排查的样本反而看不到。

## 十、tray-app 主进程

入口：`capture-sidecar-client.ts`

当前职责：

1. 接收 sidecar frame
2. 存调试环形缓冲
3. 写本地 SQLite（含去重）
4. 逐条上报新消息给后端

当前不再调用后端 `/api/v1/capture/structure` 做二次结构化。

### 10.1 本地去重（`capture-store.ts`）

入口：`CaptureStore.insertFrame`。两道关：

**第一道·同屏判重** `isDuplicateFrame`
- 取同一会话（同渠道+进程+标题）的**上一帧**，比 `chat_text_hash`。
- `chat_text_hash` = 这一屏结构化消息按 `说话人:归一内容` 拼起来的哈希（`hashChatMessages`）。
- 一致 → 同一屏 → 整帧标 `skipped_duplicate`，不拆消息、不上报。
- 注意：**不再用整图字节哈希 `image_hash`**——时钟跳一分钟/光标闪一下字节就变，判不出同屏。结构化消息为空（结构化失败/空会话）时不在这里判重，交给后续逻辑。

**第二道·单条消息去重** `insertMessageBlock`
- 去重键 `dedupe_key = 线程id : 说话人 : 内容哈希`（哈希前删空白、中文标点转英文）。
- 同一会话里已存过同键消息 → 不新增，只 `seen_count+1`、续 `last_seen_at`、记录来源帧；**不进上报队列**。
- 没存过 → INSERT，进 `newMessages` 上报后端。
- **不卡时间窗**：只看"会话+说话人+内容"。代价是客户隔很久又发一字不差的同一句会被合并，可接受。

self / other / system 三类都入本地库、都参与去重。当前上报后端时 `system`（时间戳/撤回提示等）被跳过，只传 self / other。

## 十一、tray-app 采集调试页

入口：`packages/tray-app/src/renderer/src/v2/pages/SidecarDebugPage.tsx`

采集调试页的「OCR 识别」标签用于验证 sidecar 结构化结果，不参与正式数据处理。

当前展示内容：

- 原始 OCR 行列表：展示 `ocr.blocks` 的文本、坐标、尺寸和置信度，便于复制给 AI 分析。
- 分区线：展示 `chatX0 / chatX1`，用于确认聊天区是否切准。
- 气泡框：来自 sidecar `messages[].box`，按 `self / other / system` 用不同颜色标识。
- 正文归属：OCR 行中心点落入某个 `message.box` 时，在调试页视为该消息正文。
- 发送人标识：调试页按 sidecar 的 `sender` 字段，在对应 other 气泡上方寻找匹配 OCR 行并标紫色框。
- system 标识：sidecar 输出的 `system:time / system:notice / system:other` 会以系统消息样式展示。
- 结构化失败提示：`structureError` 非空时，摘要栏下方显示红色「结构化失败」面板，内含异常堆栈，可一键复制发给开发排查；原图+OCR 仍在下方正常展示。

说明：

- 调试页只渲染 sidecar 的结果，不重新判定消息。
- 如果调试页显示错误，优先回到 sidecar 的分区、气泡扫描、sender 识别逻辑排查。
- `InputCutY / InputCut` 旧输入区切线字段仍可能存在于类型里，但当前正式链路不依赖它。

## 十二、后端

入口：`packages/backend/src/routes/api.ts`

后端当前职责：

- 认证员工
- **订单关联（权威）**：tray-app 上报时带 `orderNoCandidate`（标题里抽的含噪订单号）。后端对候选做**归一 + 编辑距离误差匹配**，并对**靠容差(距离≥1)匹配上的**再用"订单客户名是否出现在标题里"做一道校验（距离=0 直接信）；匹配不到/并列/名字对不上 → 存 `UnmatchedOrderRef` 待人工确认（铃铛通知）。sidecar / tray-app **不判订单归属**，只转发候选。
- **跨帧单消息去重 + 时间链还原**（新链路，见下）
- 消息入 PostgreSQL

后端不再负责：分区 / 气泡扫描 / sender 判定 / system 判定（这些在 sidecar）。

### 12.1 跨帧处理（新链路）

架构分工：**sidecar 出每帧结构化（含 system）→ tray-app 逐帧原样转发 → 后端做跨帧去重 + 时间链**。跨帧逻辑放后端是因为后端在本机、改完热重载，迭代快（不必每次都走 VM 部署）。

入口：`POST /api/v1/capture/frame`，body：`{ channel, conversationName, orderNoCandidate?, screenshotOssKey?, capturedAt, messages:[{speaker, name?, text, kind?}] }`（messages 是屏幕从上到下的顺序，含 system）。

- **单消息去重**：去重键 `dedupeKey = sha256(员工 | 会话名 | 说话人 | 归一内容)`（`Message.dedupeKey` 唯一）。命中 → 只 `seenCount+1`、刷新 `lastSeenAt`、订单/时间后补；未命中 → 插入。
- **时间链还原** `chatTime`（`lib/chatTimeParser.ts`）：messages 自上而下扫，遇到 `system:time` 锚点就更新当前 anchor，其下方消息 `chatTime = 最近 anchor`（解析中文锚点：`HH:mm`、`上午/下午/晚上/凌晨/中午`、`今天/昨天/前天`、`星期X/周X`、`M月D日`、`YYYY年M月D日`，以 `capturedAt` 当天为基准、按北京时区 UTC+8 换算）。算不出 → `chatTime=null`。
- **时间线排序**：消息按 `[chatTime asc nulls last, capturedAt asc]`——往上翻看的历史消息靠 `chatTime` 排回真实位置，没锚点的近期消息(null)排在最后、按截图时刻。

> 过渡期：旧的逐条 `POST /api/v1/messages` 仍在（当前 tray-app 还在用），与 `/capture/frame` 并存；tray 切到新接口后废弃旧的。`Message` 新增字段：`senderType / kind / chatTime / contentHash / dedupeKey / seenCount / firstSeenAt / lastSeenAt`。

## 十三、当前实现的关键结论

1. RapidOCR 已经是行级结果，sidecar 不再做复杂“拼行”。
2. 结构化链路现在是“先找气泡，再判消息/发送人/system”。
3. `self / other` 由**气泡颜色**决定（self、other 各用自己的基准色分别扫连通域、互不合并），不再用位置/中心点。
4. 真正需要持续调的核心只剩两块：
   - 聊天区分区
   - 气泡扫描与几何过滤
