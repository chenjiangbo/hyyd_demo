# 采集客户会话识别规则

> 更新时间：2026-06-25。范围：`packages/capture-sidecar/CaptureCollector.cs` 的客户会话准入判断，以及后端 `packages/backend/src/lib/orderNoMatch.ts` 的订单号候选解析。

## 1. 识别发生在哪里

sidecar 截图并 OCR 后，会先用结构化逻辑切出聊天区，再取聊天区顶部标题行作为 `title`。

客户会话判断只看这个标题行，不再扫全屏 OCR。这样可以避免左侧联系人列表里出现客户群名时误保留当前非客户会话。

核心入口：

- `CaptureCollector.ClassifyTitle(title)`
- `MessageStructurer.Build(...)` 负责生成 `structure.Title`

## 2. 客户会话准入规则

当前是“命中任一条件即保留”，不是同时满足。

标题行满足以下任一条件，就认为是客户会话：

1. 包含客户群关键词，默认是 `就医服务群`
2. 包含完整订单号候选：
   - `fwyy...`
   - `COD...`
   - `CCOD...`
   - `OD...`
   - `SO...`
   - `LT...`
3. 包含短备注尾号：`#订单尾8位` 或 `＃订单尾8位`

因此：

- 企微群名含 `就医服务群`，即使没有订单号，也会保留。
- 企微群名不含 `就医服务群`，但含 `fwyy...`，会保留。
- 企微群名不含 `就医服务群`，但含 `OD...`，也会保留。
- 单聊备注如 `王五家属#12345678`、`wwm#12345678`，会保留。

## 3. 群聊与单聊分类

`conversationKind` 目前只用于标记类型：

- 标题含 `就医服务群` → `group`
- 标题不含 `就医服务群`，但命中订单号或 `#尾8位` → `single`

注意：如果一个企微群标题不含 `就医服务群`、但含 `OD...`，当前会被保留，但 `conversationKind` 会是 `single`。这不影响订单关联；如果后续 UI 必须区分群/单聊，需要单独增强群聊识别，不应改订单匹配逻辑。

## 4. 订单号候选格式

sidecar 和后端都认以下候选：

```text
fwyy[0-9a-z|]{6,24}
(CCOD|COD|OD)[0-9a-z|]{12,18}
(SO|LT)[0-9oqislzg|]{14,24}
[#＃][0-9a-z|]{8}
```

`#尾8位` 允许英文和数字，不能是中文；并且必须正好 8 位，不会把 `#123456789` 截成 `#12345678`。

## 5. 后端关联规则

完整订单号：

- 做 OCR 易混字符归一
- 用编辑距离 `<= 2` 在当前员工订单集合中匹配
- 唯一最近命中则关联
- 多个并列或无法命中则写入 `unmatched_order_refs`

`#尾8位`：

- 先做 OCR 易混字符归一
- 与当前员工订单号的后 8 位比较，允许编辑距离 `<= 2`
- 唯一命中则关联
- 多个命中时，才使用 `#` 前的名称做弱破平
- 名称破平只处理一个特殊词：去掉 `家属`
- 仍不能唯一确定或找不到订单，则写入 `unmatched_order_refs`，由 tray-app 右上角铃铛提示

## 6. 典型例子

| 标题 | 是否保留 | 说明 |
|---|---:|---|
| `20260610辽宁李德恒先生就医服务群` | 是 | 命中 `就医服务群` |
| `20260610辽宁李德恒先生就医服务群fwyy1514012829958197248` | 是 | 同时命中群关键词和 `fwyy`，但不是必须同时命中 |
| `20260610辽宁李德恒先生就医服务群ODabcdef1234567890` | 是 | 同时命中群关键词和 `OD` |
| `李德恒ODabcdef1234567890` | 是 | 不含群关键词，但命中 `OD` |
| `李德恒家属#12345678` | 是 | 命中 `#尾8位` |
| `wwm#12345678` | 是 | 命中 `#尾8位`，`#` 前不要求中文 |
| `普通同事群` | 否 | 没有群关键词、订单号或尾号 |

## 7. 调试页矛盾提示排查

如果采集调试页看到类似：

```text
标题行：20260604北京钻石车凤莲女士就医服务群fwyy1512135181178949632X
非客户会话 — 标题未含"就医服务群"，也未匹配 COD/fwyy 订单号
```

按当前源码规则，这个标题不应该被判为非客户会话，因为它同时命中：

- `就医服务群`
- `fwyy1512135181178949632X`（`fwyy` 后允许英文/数字，候选存在不代表数据库里必须存在）

出现这种矛盾通常不是“订单号不存在”导致的。订单号不存在只会影响后端订单关联，应该进入待确认，不应该影响 sidecar 的客户会话准入。

优先排查：

1. **员工机运行的 sidecar 不是最新版本**  
   当前源码已支持 `fwyy...`、`OD...`、`#尾8位` 任一命中保留；员工机如果没重新 deploy/build，仍可能跑旧规则。

2. **调试页文案是旧的硬编码文案**  
   采集调试页的“未匹配 COD/fwyy”提示是前端按 `filtered` 状态展示的固定文字，不是 sidecar 返回的精确失败原因。以后要排查应看 sidecar 原始日志里的“客户会话识别：...”和“非客户会话...标题=...”。 

3. **`HYYD_CAPTURE_TITLE_KEYWORDS` 覆盖了默认关键词**  
   默认关键词是 `就医服务群`。如果运行环境设置了 `HYYD_CAPTURE_TITLE_KEYWORDS` 且不包含 `就医服务群`，则群关键词不会命中，只剩订单号规则。

4. **OCR 显示看起来相同，但实际字符不同**  
   例如某个汉字被 OCR 成形近字，或标题中混入不可见字符。sidecar 会先去空白再匹配，但不会做中文形近字纠错。

结论：`fwyy...X` 是否存在于订单库，不影响客户会话准入；它只影响后端能否自动关联订单。关联不到时应写入 `unmatched_order_refs`，由 tray-app 右上角铃铛提示。
