# 挂号凭证浮动精灵需求说明与设计方案

## 1. 文档目的

本方案用于实现一个常驻桌面的浮动精灵。寰宇员工可以把微信、文件夹或其他窗口中的图片直接拖到精灵上，客户端识别图片是否为挂号凭证，并尝试将其关联到正确的订单。

本功能不再依赖微信或企业微信的大图窗口，也不要求员工在特定会话中打开图片。图片归属以图片内容和订单匹配结果为准。

## 2. 已确认的需求

### 2.1 员工操作

1. 客户发送挂号凭证图片后，员工将图片拖到浮动精灵。
2. 精灵接收图片并立即给出处理状态。
3. 客户端先判断图片是否像挂号凭证。
4. 如果是挂号凭证，系统提取患者、医院、科室、时间等信息并寻找订单。
5. 找到订单后，精灵直接把图片上传到该订单的素材中。
6. 如果不是目标订单，员工可以重新选择订单；重新选择后上传到正确订单。

### 2.2 不在本期范围内

- 不再自动发现微信大图窗口。
- 不再依赖微信窗口标题、句柄或 ClassName。
- 不要求员工必须在客户会话中打开图片。
- 不使用“另存为”获取原图，仍然以拖入图片作为输入。
- 不把整张订单详情或几十个订单字段发送给 AI。

## 3. 现有代码能力

当前已有视觉模型调用能力：

- `packages/backend/src/llm/imageUnderstandService.ts`
- `packages/backend/src/llm/gatewayClient.ts`

`imageUnderstandService` 不是未实现接口。它已经能够把图片发送给视觉模型，并返回图片分类和识别文本。当前默认视觉模型是 `qwen-vl-max`，默认通过阿里云百炼 DashScope 的 OpenAI 兼容接口调用；如果配置了 `HYYD_VLM_BASE_URL`、`HYYD_VLM_API_KEY` 或 `HYYD_VLM_MODEL`，则使用对应配置。

当前实现的调用位置是订单简报任务：图片已经绑定订单并上传后，后台再对图片做“聊天截图/单据/短信/其他”的分类和文字提取。因此，它可以作为本功能的基础，但需要扩展识别结果和调用时机，不能直接解决拖入图片后的订单匹配。

现有订单素材上传接口是：

```text
POST /api/v1/orders/:id/materials
```

该接口要求先有 `orderId`。因此拖入图片后必须先完成识别和订单匹配，再调用这个接口。上传成功后，图片通过现有 `Material.orderId -> Order.id` 关系进入订单素材，不需要新增一套图片归属关系。

当前数据模型已经存在：

- `Order` 模型对应数据库表 `orders`，主键为 `id`，包含订单号、患者、手机号、医院、科室、医生、状态等字段；
- `Material` 模型对应数据库表 `materials`，通过 `orderId` 关联 `Order`，图片本体存放在 MinIO 的 `materials` bucket；
- `Material.employeeId` 记录上传员工；
- 现有管理端和订单详情已经能够读取订单素材。

## 4. 样例分析

当前样例目录：

```text
debug/挂号凭证
```

样例包含以下形态：

- 医院公众号或小程序的预约成功页面；
- 医院挂号详情页面；
- 短信形式的预约成功通知；
- 手机拍摄的屏幕照片；
- 包含二维码、挂号号、医院、科室和患者信息的凭证；
- 长文本形式的挂号或预约通知。

这些图片的版式、颜色、字段名称和脱敏方式都不一致，不能采用固定坐标或单一模板。共同特征是：

- 存在“挂号成功”“预约成功”“预约信息”“挂号详情”等语义；
- 通常能识别到医院、科室、就诊人、就诊时间中的部分信息；
- 可能存在挂号号、订单号、就诊号或二维码；
- 患者姓名、身份证号和手机号可能是脱敏的；
- 只要能证明这是一次医院挂号或预约成功凭证，就应当允许进入后续订单匹配。

## 5. 挂号凭证识别方案

### 5.1 识别原则

视觉模型需要采用宽松的业务判断，不要求识别出全部字段。

判断重点不是“是否符合某一种模板”，而是：

1. 是否表达了挂号或预约已经成功；
2. 是否包含医院或医疗机构相关信息；
3. 是否包含科室、医生、就诊时间或就诊人等医疗预约信息；
4. 是否只是普通聊天、广告、缴费、检查报告或其他非挂号图片。

“有挂号/预约语义 + 有医院或科室信息”即可作为较强的挂号凭证候选。模型看不清字段时不得猜测，应返回空值或“不确定”。

### 5.2 视觉模型输出

现有的 `kind + text` 结果需要扩展为结构化结果，建议至少包含：

```json
{
  "isRegistrationProof": true,
  "confidence": 0.92,
  "proofType": "mini_program|sms|hospital_page|photo|other",
  "patientName": "张*伟",
  "patientNameSuffix": "伟",
  "idCardSuffix": "1234",
  "phoneSuffix": "5678",
  "hospital": "北京大学第三医院",
  "department": "消化内科",
  "doctor": "王某某",
  "appointmentDate": "2026-10-27",
  "appointmentTime": "08:30-09:00",
  "registrationNumber": "11021182",
  "rawText": "模型读到的主要文字",
  "evidence": [
    "预约成功",
    "就诊医院",
    "就诊科室",
    "就诊人信息"
  ]
}
```

字段不要求全部存在。模型必须区分：

- 图片中明确看见的内容；
- 根据版式或语义推断的内容；
- 无法确认的内容。

无法确认的字段应为空，不得补造。

### 5.3 提示词方向

提示词应以当前样例归纳出的共同业务含义为主，而不是写死医院模板。提示词应明确：

- 图片可能是小程序、短信、网页、聊天转发图或手机拍摄图；
- “预约成功”“挂号成功”“挂号详情”等表达都应识别；
- 医院、科室、医生、患者、时间、挂号号是重点字段；
- 脱敏姓名、身份证后四位、手机号后四位仍应提取可见部分；
- 不要求所有字段齐全；
- 不确定时返回空值；
- 只判断是否像挂号成功凭证，不把普通缴费单、检查报告、病历或聊天截图误判为挂号凭证。

提示词需要在样例验证过程中持续调整，不能因为当前样例数量有限就把规则收紧成固定模板。

## 6. 订单候选匹配方案

### 6.1 第一阶段：程序匹配

第一阶段由后端程序完成，不调用 AI 搜索订单。

程序根据视觉模型提取出的字段查询订单，并保留每一条匹配依据。优先级建议如下：

1. 挂号号、申请号、订单号等强标识；
2. 身份证后四位；
3. 手机号后四位；
4. 患者姓名可见部分；
5. 医院；
6. 科室；
7. 医生；
8. 就诊日期和时间。

身份证后四位、姓名最后一个字等信息不能单独作为唯一匹配条件，必须和医院、科室、时间等信息组合判断。

程序匹配必须返回：

- 候选订单 ID；
- 订单号；
- 患者姓名；
- 医院、科室、医生；
- 就诊时间；
- 命中的凭证字段；
- 未命中的关键字段；
- 匹配状态：唯一、多个、无结果。

不能只返回一个没有解释的分数。

### 6.2 AI 候选范围

程序匹配阶段暂时不限制员工订单范围，搜索全部订单。这样可以避免订单归属、状态或分配字段不完整时漏掉真实订单。

搜索全部订单不等于把全部订单发送给 AI。程序查询必须完整执行，不能通过只取前 N 条来代替完整搜索；订单较多时使用数据库条件查询、分页或分批处理，并记录实际查询范围和结果数量。

当前实现中，程序匹配会读取完整 `Order` 集合并计算候选；如果没有唯一程序匹配，AI 候选只从 `assignedEmployeeId` 等于当前登录员工的订单中生成。AI 返回的建议会排在候选列表第一项，但不会绕过员工选择直接上传。候选数量和匹配依据由后端返回给精灵，当前没有单独的后台诊断页面展示完整模型请求。

AI 辅助匹配必须使用受限候选范围。建议候选范围由程序根据图片识别出的信息生成：

- 医院一致或医院名称标准化后相近；
- 科室一致或属于同一医院的相近科室；
- 就诊日期相同或处于明确的业务时间范围；
- 患者姓名可见部分、身份证后四位或手机号后四位至少命中一项；
- 挂号号、申请号或订单号出现部分可检索信息。

这些条件按医院、时间、患者信息、科室等字段组合查询，取满足有效锚点的完整候选集合，再把候选订单摘要发给 AI。没有任何有效锚点时，不应把全量订单发送给 AI，而应提示员工通过订单号、患者或医院重新选择。

候选范围的订单数量需要在接口日志和界面中可见。不得静默截断；如果数量过大，应继续分页查询或提示员工缩小范围。

### 6.3 第二阶段：程序无唯一结果时调用 AI

如果程序没有找到唯一订单，可以进入 AI 辅助匹配，但只把上一节生成的受限候选订单摘要发送给 AI。

流程为：

1. 程序根据医院、科室、时间、患者可见信息等锚点查询候选订单；
2. 每个候选订单只保留必要字段：订单 ID、订单号、患者姓名、手机号后四位、身份证后四位、医院、科室、医生、就诊时间和状态；
3. 将挂号凭证的结构化识别结果和候选订单摘要发送给 AI；
4. AI 返回最可能的订单、置信度、命中的字段和排除其他订单的理由；
5. AI 结果只能作为候选建议，不能在低置信度或有竞争候选时自动覆盖程序结果；
6. AI 给出可用候选并完成必要选择后，浮动精灵直接上传到该订单，并提供“不是该订单？重新选择订单”入口。

建议 AI 返回：

```json
{
  "candidateOrderId": 123,
  "confidence": 0.86,
  "matchedFields": ["hospital", "department", "appointmentDate"],
  "reason": "医院、科室和就诊日期一致，患者姓名仅保留末字，无法单独确认",
  "alternativeOrderIds": [456]
}
```

如果 AI 置信度不足或存在明显竞争候选，必须进入人工选择，不得自动上传。

## 7. 浮动精灵交互

### 7.1 常态

- 精灵常驻桌面并置顶；
- 支持拖入图片文件、微信图片或其他可拖拽图片；
- 不遮挡主要工作窗口；
- 通过图标、颜色和短文字显示当前状态。

### 7.1.2 当前 Electron 实现

浮动精灵不是独立程序，而是 tray-app 内的第二个 Electron `BrowserWindow`：

- 主进程文件：`packages/tray-app/src/main/index.ts`；
- 页面入口：`packages/tray-app/src/renderer/pet.html`；
- React 组件：`packages/tray-app/src/pet/main.tsx`；
- 角色 SVG 视觉组件：`packages/tray-app/src/pet/PetAvatar.tsx` 与 `PetAvatar.css`；
- 气泡内容组件：`packages/tray-app/src/pet/PetBubble.tsx` 与 `PetBubble.css`；
- 动画样式：`packages/tray-app/src/pet/styles.css`；
- 拖拽后的文件处理：`packages/tray-app/src/main/pet-intake-service.ts`。

正式角色视觉参考图保存在 `packages/tray-app/resources/寰宇医道_像素精灵原图参考.png`，只作为绘制依据，不作为运行时角色贴图。角色默认显示尺寸约为 `64 x 70`，通过 SVG 图层实现待机、拖拽接收、处理中和完成说话等状态。

窗口属性为透明、无边框、置顶、不显示在任务栏、不可调整大小。空闲和拖拽悬停时窗口为 `96 x 96`，只显示小尺寸精灵；真正放下文件、处理中、候选选择或结果提示时窗口动态扩展到约 `300 x 260`，根据精灵所在屏幕位置把气泡放在精灵左侧或右侧。表单或长内容会在屏幕约束内继续按实际气泡尺寸扩展。页面根节点必须使用：

```css
-webkit-app-region: no-drag;
```

这是拖拽接收的必要条件。若把根节点设为 Electron 的 `drag` 区域，Windows 会把从微信拖入的动作当作移动窗口，显示禁止拖拽光标，并且页面收不到 `drop` 事件。当前精灵不提供通过拖拽移动窗口的功能，位置由主进程设置。

精灵本体不显示关闭按钮。隐藏精灵属于系统操作，由右键菜单处理，不退出客户端。精灵窗口右键由主进程的 `webContents` `context-menu` 事件处理，菜单为：

```text
隐藏浮动精灵
显示工作台
退出客户端
```

“退出客户端”执行完整 Electron 退出流程，会同时结束托盘客户端、采集 sidecar 和素材同步 worker。托盘菜单中的退出与它使用相同的退出逻辑。

当前消息展示不是底部单行状态栏，而是精灵旁边按需出现的对话气泡：空闲和拖拽悬停状态隐藏气泡，消息状态使用较大的中文字体和多行换行，气泡按内容自然增高，不使用省略号截断。精灵靠近屏幕右侧时气泡出现在左侧，靠近左侧时气泡出现在右侧。成功或异常提示展示一段时间后自动收回到 `96 x 96`；候选订单状态保持展开，候选项使用可换行的按钮展示患者、医院、科室和订单号。窗口和气泡采用紧凑尺寸，避免遮挡过宽的桌面区域。

移动端心跳不能证明 App 在前台还是后台运行，因此精灵不显示“前台运行”或“后台运行”状态。工作台已有 `/api/v1/me/presence` 轮询，渲染层把移动端状态通过 IPC 同步给精灵：最近有可靠心跳时显示绿色呼吸点，心跳过期时显示橙色静态点，没有可靠状态时不显示状态点。后端产生 `needs_open` 时，继续使用现有右下角提醒窗口，同时向精灵发送一次气泡提醒；精灵不自行重复判断或周期性重复弹出。

气泡内容通过 `PetPanel` 联合类型驱动，不把业务表单写死在精灵组件中。表单面板支持标题、说明、字段分组、文本框、多行文本、数字、日期、下拉、单选和复选框；字段可以声明必填、只读、提示、校验错误和选项。操作按钮独立于字段区，表单字段区在内容超过屏幕可用高度时滚动，操作区保持可见。气泡渲染后通过 `ResizeObserver` 把实际尺寸报告给主进程，主进程按气泡内容和当前屏幕边界重新调整浮动窗口，不使用固定的单一气泡尺寸。

### 7.1.3 当前拖拽接收链路

页面收到 `drop` 后按以下顺序取得路径：

1. 从 `DataTransfer.files` 读取文件，并调用 Electron `webUtils.getPathForFile(file)`；
2. 如果微信没有提供标准文件对象，再读取 `text/uri-list`；
3. 最后读取 `text/plain` 中的 `file://` 路径；
4. 主进程再次使用 `existsSync`、`statSync` 校验路径确实是文件，并检查扩展名；
5. 通过 `pet:drop-files` IPC 进入图片暂存、视觉识别、订单匹配和上传流程。

当前支持的扩展名为 `png`、`jpg`、`jpeg`、`webp`、`bmp`、`gif`。微信拖拽是否能成功，取决于微信版本和当前拖拽来源是否向 Electron 暴露真实文件路径。Windows 调试时必须记录 `DataTransfer.types`、`files.length`、`getPathForFile` 返回值和最终 IPC 入参，不能只根据光标样式判断失败位置。

### 7.1.4 当前动画状态

当前使用 HTML/CSS 绘制角色，没有外部图片素材或独立动画运行时。React 状态和 CSS class 的对应关系如下：

| 状态 | 触发条件 | 当前动画 |
| --- | --- | --- |
| `idle` | 常态 | 身体呼吸、脚下光圈轻微变化 |
| `dragover` | 文件进入精灵区域 | 双手抬起、身体弹跳、屏幕高亮 |
| `working` | 识别或上传中 | 身体摆动、天线摆动 |
| `pet-speaking` | 状态文案变化后约 1.8 秒 | 屏幕缩放变化、天线灯闪烁 |
| `done` | 上传成功 | 身体跳跃，屏幕显示 `OK` |
| `unknown` | 文件不支持或处理失败 | 身体摇头，屏幕显示警示色 |
| `candidates` | 等待员工选择订单 | 屏幕显示候选状态，候选列表可点击 |

“说话”目前是视觉状态，不是语音播报。业务状态由主进程通过 `pet:status` IPC 推送，页面再切换动画 class。

### 7.1.1 登录和启动方式

- 第一次启动或本地没有有效登录信息时，显示现有登录窗口；
- 登录成功后保存登录会话；
- 后续启动默认不显示工作台和登录页，只显示托盘图标和浮动精灵；
- 用户从托盘菜单主动打开工作台时，才显示完整工作台；
- 会话失效时，浮动精灵提示需要重新登录，并打开登录窗口；
- 用户主动退出登录后，关闭精灵的业务处理能力并重新显示登录窗口。

现有 v2 客户端已经有登录会话保存、登录页和托盘生命周期，需要将启动显示策略从“创建主窗口”调整为“托盘 + 浮动精灵”，而不是重新设计登录机制。

```text
正在保存到对应订单…

```

程序已经得到唯一订单后直接调用订单素材上传接口，不再显示“确认上传”。如果员工判断订单不对，可以通过“不是该订单？重新选择订单”进入改绑流程。改绑必须由后端明确处理原素材和新订单的关系，不能静默创建重复素材或覆盖原记录。

### 7.4 AI 找到候选订单

```text
可能是张*伟的挂号凭证
北京大学第三医院 · 消化内科
匹配依据：医院、科室、就诊日期
识别置信度：较高

正在保存到对应订单…

[不是该订单？重新选择订单]
```

AI 找到候选后直接上传，但文案必须明确是“可能是”，不能显示成已确认。低置信度或多个竞争候选时，应先显示候选选择列表，选定后再上传。

当前实现采用更保守的交互：AI 建议只作为候选列表的第一项，员工点击订单后才调用素材上传接口。也就是说，当前不会因为 AI 返回了一个 `orderId` 就自动上传。

### 7.5 多个候选订单

显示候选订单列表，每项展示：

- 患者姓名；
- 医院和科室；
- 就诊时间；
- 匹配依据；
- 订单号。

员工选择后直接上传图片，不再增加“确认上传”按钮。

当前实现的候选列表显示患者姓名、医院、科室和订单号；候选项点击后直接上传。设计中的“重新选择订单”入口尚未连接到独立的订单搜索/改绑页面，Windows 调试时需要重点验证候选列表是否足够覆盖实际选择场景。

### 7.6 无法处理的文件

```text
嗯…这好像不是我现在能处理的文件呢
你可以先把挂号凭证拖给我，其他文件类型我们还在学习中
[重新处理] [删除]
```

后续浮动精灵还会支持 Excel 等其他文件类型，因此不能把所有非挂号图片都称为“错误”。当前无法识别的文件统一进入“未知文件 / 暂不支持处理”状态，不能静默丢弃。

### 7.7 Windows 调试重点

当前代码已经完成 macOS 下的类型检查和 Electron 构建，但浮动窗口、微信拖拽和透明窗口命中区域必须在 Windows 手工确认。调试顺序如下：

1. 先确认精灵窗口显示尺寸、位置和置顶状态；
2. 右键精灵，确认“隐藏浮动精灵”“显示工作台”“退出客户端”均可出现；
3. 右键选择“隐藏浮动精灵”，确认只隐藏精灵，托盘和采集仍然运行；
4. 从 Windows 文件管理器拖入一张本地 PNG，确认出现 `dragover` 状态并进入 `pet:drop-files`；
5. 从微信聊天窗口拖入图片，分别检查 `DataTransfer.files`、`DataTransfer.types`、URI 数据和 `getPathForFile`；
6. 确认主进程日志中的文件路径存在，并且没有被误判为窗口移动；
7. 再检查视觉模型请求、订单候选返回和素材上传结果。

现阶段需要重点排查的边界包括：

- 微信拖拽的是临时文件、虚拟文件还是仅有自定义剪贴板数据；
- 微信拖拽时是否触发页面 `dragover`/`drop`，还是在进入透明窗口前就被 Windows 拒绝；
- 多显示器、缩放比例变化后精灵窗口的可见区域和实际命中区域是否一致；
- 候选列表弹出后，按钮区域是否仍然是 `no-drag` 并能正常点击；
- 视觉模型失败、订单查询失败和上传失败时，精灵是否显示明确错误而不是停留在 `working`。

Windows 调试修复必须先记录实际事件、路径和主进程错误，再修改对应层级：拖拽事件问题改 renderer 或窗口属性，路径校验问题改 preload 或主进程，识别和匹配问题改 backend，不能通过静默重试或伪造成功状态掩盖问题。

## 8. 图片生命周期和失败处理

1. 拖入后先保存到客户端待处理目录。
2. AI 识别失败，保留图片并记录错误。
3. 不是挂号凭证，保留结果，等待员工删除或重新处理。
4. 找不到订单，保留图片，允许重新选择或重新匹配。
5. 程序匹配到订单或员工重新选择订单后，调用现有素材上传接口。
6. 上传成功后删除客户端待处理图片。
7. 上传失败则保留图片和错误信息，不能删除。
8. 不允许因为模型响应异常、订单查询异常或上传异常而静默跳过。

### 8.1 当前实现与目标的差异

- 图片分析和上传失败时，客户端暂存文件会保留，主进程输出 `[pet]` 错误日志；
- 当前判断为“不是挂号凭证”后会删除本次暂存副本，原始拖拽文件不受影响；这与“保留结果、等待员工删除”的目标设计仍有差异；
- 当前待选择订单只保存在 tray-app 进程内存中，客户端重启后不能恢复未完成选择；
- 当前没有独立的“手动搜索订单并重新绑定”窗口；
- 当前精灵动画使用 CSS，不依赖图片素材，动画是否在 Windows 透明窗口上流畅需要实机确认。

这些差异属于待调试或待补齐项，不能在验收记录中标记为已完成。

## 9. 开发顺序

### 第一步：实现浮动精灵窗口

- 先实现现有 tray-app 内的 Windows 置顶浮动窗口，不新增独立程序；
- 支持拖入文件并显示接收状态；
- 支持精灵的隐藏、托盘恢复和客户端退出；精灵当前不通过拖动移动位置，因为整个窗口需要作为文件接收区域；
- 第一版使用程序绘制的 HTML/CSS 动态角色，不依赖现成图片素材；
- 拖入时改变表情、大小、颜色或姿态，给出“接住文件”“正在处理”“处理完成”“暂时不会处理”的反馈。

没有现成精灵素材不是阻塞条件。第一版可以使用 CSS/HTML 绘制简单角色并做动画，例如身体呼吸、眼睛眨动、拖入时张开双手、处理时旋转或跳动。后续如果需要更有品牌感，再替换为透明 PNG/WebP 动画帧或 Lottie/Rive 资源，窗口交互接口不变。

### 第二步：整理现有视觉模型接口

- 确认视觉模型配置、模型名称、调用地址和错误日志；
- 保留现有 `imageUnderstandService` 的通用能力；
- 增加结构化挂号凭证识别结果；
- 先不接订单上传。

### 第三步：使用样例验证挂号凭证识别

- 对 `debug/挂号凭证` 下的全部图片逐张测试；
- 记录是否识别为挂号凭证；
- 记录医院、科室、患者、时间和挂号号的提取结果；
- 发现模型完全无法识别时，先调整提示词和输出校验，再决定是否调整方案；
- 不用样例数量限制来伪造验证通过。

### 第四步：实现订单候选查询和程序匹配

- 明确全量订单查询的字段、分页和结果记录方式；
- 建立字段标准化和脱敏字段比较规则；
- 实现完整候选查询；
- 返回候选订单和可解释匹配依据；
- 用真实订单和样例凭证验证唯一、多个、无结果三种情况。

### 第五步：实现受限候选集和 AI 辅助匹配

- 只在程序没有唯一结果时触发；
- 只发送必要订单字段；
- 完整记录发送的候选数量、模型结果、置信度和理由；
- AI 只能提供有范围的候选建议；低置信度或多个候选时由员工选择后直接上传。

### 第六步：接入现有素材上传

- 程序匹配到唯一订单或 AI 得到可用候选并完成必要选择后，直接调用现有 `POST /api/v1/orders/:id/materials`；
- 上传成功删除客户端待处理文件；
- 上传失败保留文件并显示失败状态；
- 验证订单详情和后台管理端能够看到图片。

### 第七步：调整启动和登录体验

- 首次登录显示现有登录窗口；
- 登录成功后保存会话；
- 后续启动只显示托盘和浮动精灵；
- 托盘菜单可以打开完整工作台；
- 会话失效、退出登录和重新登录路径必须可验证。

### 第八步：端到端验收

至少验证：

- 小程序截图；
- 短信截图；
- 医院页面截图；
- 手机拍摄图片；
- 有脱敏姓名的凭证；
- 有身份证后四位的凭证；
- 有多个候选订单；
- 程序无结果、AI 找到候选；
- AI 也无法确定；
- 非挂号图片；
- AI 服务失败；
- 订单查询失败；
- 上传失败和重试。

任何一种样例如果识别结果与实际业务明显不符，应先记录根因和影响范围，再调整提示词、字段解析或匹配方案，不能用静默跳过或默认绑定掩盖问题。

## 10. 预期结果

最终员工不需要判断图片来自微信、企微、文件传输助手还是其他位置，只需要把图片拖给浮动精灵。系统负责识别、查找订单并直接将图片保存到订单素材中；如果不是目标订单，员工可以重新选择订单。

该流程的核心原则是：

```text
视觉模型负责理解图片
程序负责查询和匹配订单
程序负责确定或提供候选订单，员工负责必要时重新选择归属
现有素材接口负责上传和保存
```
