# 「订单号待确认」功能 · 后端交接说明（给做 UI 的 AI）

> 后端已实现：从微信/企微聊天截图标题里抽到的订单号候选，自动模糊关联到订单；
> **关联不上时存起来，等员工/客户确认绑定**。本文说明数据表与接口，UI 由你来做。
> 写作时间：2026-06-12。涉及文件：`packages/backend/src/lib/orderNoMatch.ts`、`src/routes/api.ts`、`prisma/schema.prisma`。

## 一、背景与整体流程

寰宇专员用微信/企微跟客户沟通。会话标题（群名 / 单聊备注名）里通常带**订单号**：
- 普客（普通客户）：`COD…/CCOD…/OD…`（16 位 hex，**就是订单库里现有的号**）
- 高客（VIP）：`fwyy` + 长数字（**目前订单库里还没有这套号**，待补）
- 群（仅企微）：`<日期><省份><级别><姓名>就医服务群<订单号>`

采集截图经 OCR 得到标题文本，上报到后端 `POST /api/v1/messages`（字段 `conversationName` = 标题）。后端按下面的优先级关联订单：

1. **抽订单号候选** → 在该员工订单里**模糊解析**（OCR 易混字符归一 + 编辑距离 ≤2，取唯一最近）
   - 唯一命中 → 直接关联（`message.orderId`）。**普客即使 OCR 错 1-2 位也能自动关联，不会进待确认。**
   - 找不到（`none`）/ 多单并列（`ambiguous`）→ **写入 `unmatched_order_refs` 表，待确认**（你做的 UI 来处理）
2. 没抽到订单号 → 退回按客户姓名模糊匹配

> 因此当前**高客 fwyy 的会话基本都会进待确认表**（库里暂无 fwyy，匹配不到）。等后端补了 fwyy→订单映射后，这部分会自动减少。

## 二、数据表 `unmatched_order_refs`（Prisma model `UnmatchedOrderRef`）

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `employeeId` | 所属员工 |
| `channel` | `wechat` / `wxwork` |
| `conversationName` | OCR 到的会话标题原文（可能含 OCR 噪声） |
| `candidate` | 从标题抽到的订单号候选（去空白后，可能错几位/带尾部粘连） |
| `candidateKind` | `fwyy` / `cod` / `ccod` / `od` / `unknown` |
| `reason` | `no_match`（找不到） / `ambiguous`（多单并列） |
| `bestDist` | 最近编辑距离（排查用） |
| `candidateOrderIds` | `ambiguous` 时并列的订单 id 列表（JSON 数组） |
| `screenshotOssKey` | 截图在 MinIO 的 key（可换签名 URL 展示，复用 `/api/v1/messages/:id/screenshot-url` 同款逻辑） |
| `capturedAt` | 截图时间 |
| `seenCount` | 同一候选重复出现次数（去重计数） |
| `status` | `pending` / `confirmed` / `rejected` |
| `resolvedOrderId` | 确认后绑定的订单 id |
| `createdAt` / `updatedAt` | 时间戳 |

- **去重**：同一 `employeeId + candidate` 只存一行，重复出现 `seenCount+1` 并刷新截图/时间（`@@unique([employeeId, candidate])`）。

## 三、接口（都用 `X-Employee-Code` 头鉴权，员工自己确认自己的）

### 1) 列出待确认
```
GET /api/v1/unmatched-order-refs?status=pending
→ { data: UnmatchedOrderRef[] }   // 按 updatedAt 倒序
```
`status` 可传 `pending`(默认) / `confirmed` / `rejected`。

### 2) 确认绑定到某订单
```
POST /api/v1/unmatched-order-refs/:id/confirm
body: { "orderId": 123 }
→ { data: { ok: true, backfilledMessages: N } }
```
- 把该记录标 `confirmed`、记 `resolvedOrderId`；
- 并**回填**：该员工、同 `conversationName`、还没关联订单的历史消息（截图）一并挂到这张订单上（返回回填条数）。

### 3) 忽略（不是客户会话 / 不需要绑定）
```
POST /api/v1/unmatched-order-refs/:id/reject
→ { data: { ok: true } }
```

## 四、UI 建议（你来实现）

1. 一个「**待确认会话**」列表：展示 `conversationName`、`candidate`(高亮抽到的号)、`candidateKind`、`reason`、`seenCount`、`capturedAt`、截图缩略图。
2. 每条提供：
   - **确认**：让员工选/搜一张订单（可用现有 `GET /api/v1/orders` 列表，按客户名/订单号搜），点确认 → 调接口 2。
   - **忽略**：调接口 3。
   - `ambiguous` 时，把 `candidateOrderIds` 对应的几张订单直接列出来让员工二选一，体验最好。
3. 截图展示：用 `screenshotOssKey` 换签名 URL（参考后端 `/api/v1/messages/:id/screenshot-url` 的实现，或让后端再加一个按 ossKey 换 URL 的小接口——需要的话告诉后端同学）。
