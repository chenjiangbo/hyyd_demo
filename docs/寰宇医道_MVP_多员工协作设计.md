# 寰宇医道 MVP - 多员工协作设计

> 本文档是对 `寰宇医道_MVP_技术设计.md` 的补充。主文档默认场景是"一个员工的一天"，没有覆盖多员工同时使用时的协作问题，本文档专门处理这块。

---

## 一、背景：从"一个员工"到"多员工同时使用"

主 MVP 技术设计文档（"剧本"在第 1 节）只描述了**单一员工**的端到端流程：他打开泰康、看到候选池、申领、打电话、发微信、看汇总。

但寰宇真实场景是 5-20 个员工**同时**在岗、各自登录自己的泰康账号、各自处理一部分订单。当我们把单员工架构直接乘以 N 时，会出现一些非平凡的协作问题。

---

## 二、泰康业务的核心可见性约束

通过实际观察泰康追踪池（`https://ccm.taikang.com/#/register/trackIngPoolList`）的行为，我们确认了如下事实：

| 订单阶段 | 在泰康里的可见性 | 谁能继续操作 |
|---|---|---|
| **候选池**（未申领） | 所有泰康账号登录后看到的是**完全相同**的列表 | 任何一个员工都可以"申领"，先到先得 |
| **已申领** | 仅申领该订单的那个泰康账号能看到此订单 | 仅那个账号能操作，包括后续回填、跟进 |

这两条性质共同决定了：
- 每个员工都必须装我们的 Chrome 插件，因为他申领的那批订单只在他的浏览器里可见，回填、点详情、修改字段都得在他这边发生。
- 候选池的扫描不需要每个人都做，因为大家看到的是一样的。如果每人都扫，就是 N 倍重复劳动。

## 三、核心问题清单

| # | 问题 | 影响 |
|---|---|---|
| 1 | 多员工同时扫候选池，N 倍重复上报 | 带宽浪费 / 后端 CPU 浪费 / 可能触发泰康风控 |
| 2 | 员工的泰康标签页关掉了，但 Tray App 不知道 → 申领指令被静默丢弃 | 员工以为申领成功，实际什么都没发生 |
| 3 | 单台机器扫描时也要避免重复上报（哪怕只有自己） | 后端 upsert 能去重但浪费传输 |
| 4 | 谁是"指定读取者"挂了，候选池就停止更新了 | 申领台数据陈旧 |
| 5 | 多 Tray App 实例同时连同一员工 token | 指令路由不确定 |

本 MVP **只解决 1 和 2**。其他问题在最后一节统一列出。

---

## 四、方案对比

围绕"谁负责扫候选池"这一核心问题，我们考虑过四个方案：

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **A. 指定读取者** | 团队里选定 1 台机器 / 1 个泰康账号当"池读取者"，只有它的插件去扫候选池并上报。其他员工的插件**只接申领/回填指令**，不扫池 | 简单、无竞态、流量小 | 那台机器掉线整体候选池就不更新（人工介入即可） |
| **B. 后端发租约** | 每个插件向后端申请"我能扫吗"，后端给第一个发 5 分钟租约，过期自动转给下一个 | 自动容错 | 实现复杂、租约边界容易出 bug、不利于审计 |
| **C. 全部扫 + 后端去重** | 所有插件都扫，后端按 `(source, source_order_no)` upsert 去重 | 不需要协调机制 | 5× 带宽和 CPU、可能触发风控、对泰康不友好 |
| **D. 专设 Bot 账号** | 单独搞一个泰康"专用账号" + 一台机器只干扫描 | 不干扰真实员工 | 多一个账号成本、可能违反泰康使用条款 |

**选定方案 A。** 理由：
- MVP 阶段员工数量小（5-20），方案 A 的"单点"风险可控
- 即便读取者掉线，影响只是"候选池数据陈旧"，员工已申领的那些订单都不受影响
- 实现成本最低，未来若需要可向 B 平滑演进

## 五、方案 A 详细设计

### 5.1 插件运行模式

Chrome 插件引入 `mode` 配置，存于 `chrome.storage.local`：

| mode 值 | 行为 |
|---|---|
| `pool_reader` | 扫泰康追踪池 + 上报订单 + 接收并执行指令 |
| `worker`（默认） | **不扫池**、不上报订单，但仍接收并执行指令（申领、回填等） |

**默认 worker**：避免插件装好就立刻全员开扫。运维只在指定的那台机器上手动切到 `pool_reader`。

### 5.2 插件 Popup 配置 UI

点击浏览器工具栏的插件图标弹出 popup：

```
┌────────────────────────────────────────┐
│ 寰宇医道探针  v1.x                       │
│                                          │
│ 后端：✅ 已连接 (192.168.202.1:13000)    │
│ 员工：罗璨清                              │
│                                          │
│ ☐ 本机为候选池读取者                       │
│   （勾选后会扫描泰康追踪池并上报订单。       │
│    整个团队应当只在一台机器上勾选）            │
│                                          │
│ 当前状态：Worker 模式                      │
└────────────────────────────────────────┘
```

切换勾选 → 写入 `chrome.storage.local.mode` → content script 重新加载逻辑。

### 5.3 增量上报（同时解决问题 3）

无论是 pool_reader 还是潜在的多读者场景，单次扫描可能拿到 100+ 条订单。完整全量上报浪费带宽。

**简单做法**：
- content script 维护一个内存集合 `lastReportedOrderIds: Set<string>`
- 每次扫描后只把"新增的 / 状态变更的"订单上报
- 后端依然 upsert（兜底防止丢失）

**注意**：刷新页面或重启插件后 `Set` 会清空，会有一次"全量上报"，这是可接受代价。

### 5.4 Presence 心跳（解决问题 2）

每个员工的插件（不论模式）定期向后端发心跳：

```json
{
  "type": "PRESENCE",
  "taikangTabOpen": true,
  "trackingPoolPageActive": false,
  "mode": "worker"
}
```

频率：每 10s。  
发现机制：`chrome.tabs.query({ url: 'https://ccm.taikang.com/*' })` 判断有无泰康标签。

后端维护一个 in-memory `presence: Map<employeeId, PresenceInfo>`。

Tray App 启动后：
- 通过 `GET /api/v1/me/presence` 周期性（5s）拉取自己的 presence 状态
- 如果 `!taikangTabOpen`，工作台顶部显示醒目红色 banner：
  > ⚠️ 未检测到泰康标签页。申领指令将无法执行。请先打开 https://ccm.taikang.com 并登录。

### 5.5 运维 SOP

```
新员工入职 / 新机器部署：
  1. 在 Windows 机器上装 Chrome 插件，指向 dist/
  2. 在 Tray App 首次启动时填员工 Token
  3. 默认插件是 worker 模式 → 不要勾"池读取者"
  4. 让员工自己打开泰康并保持登录

指定一台为读取者：
  1. 在某台已装好插件的电脑上点插件图标
  2. 勾选"本机为候选池读取者"
  3. 确认控制台日志出现 "Pool Reader 模式启动"
  4. 在 Tray App 申领台能看到泰康真实订单流入

读取者掉线（候选池数据停止更新）：
  1. 联系当事员工恢复 Chrome
  2. 或临时让另一台机器勾选当读取者
  3. 注意：旧读取者恢复后请取消勾选，避免双读
```

## 七、MVP 阶段已知但暂不实现的问题

我们刻意把以下问题留到 MVP 之后处理，记录在此以免遗忘：

### 协作类

1. **多人误勾选了 pool_reader**  
   现状：N 个人扫都会 upsert 到后端，后端按 `(source, sourceOrderNo)` 去重，不会出数据错乱，但会浪费流量。  
   未来：后端记录 `last_reader_employee_id` 和 `last_reader_at`，若发现 30s 内有多个 reader 在上报，向所有 Tray App 推警告，让运维人工介入；或后端给每个上报源打"质量分"，只保留分数最高的那份。

2. **Pool Reader 长时间掉线无人接手**  
   现状：候选池数据陈旧，所有人 Tray App 上的申领台不再更新。  
   未来：监控读取者最近 30 分钟无心跳 → 通知运维 / 自动从 worker 中挑选一个临时升级 / 引入轮值表。

3. **PRESENCE 心跳频率与精度的平衡**  
   现状：固定 10s 一次。  
   未来：根据是否真在用做指数退避（活跃 5s、空闲 60s）。

### 数据类

4. **候选池增量算法太粗**  
   现状：客户端用内存 Set 去重，重启后会全量上报一次。  
   未来：对扫到的订单做 hash（按时间+订单号+状态），客户端持久化到 `chrome.storage.local`，跨重启保留。

5. **跨机器看不到对方的客户和录音**  
   现状：员工 A 的所有数据只在自己机器上采集；员工 B 看不到 A 的客户对话历史。这本身**是设计目的**——隐私分隔。  
   未来：如果业务方明确要"团队共享某些视图"，需要新增字段 `shareScope` 并补 UI。

### 路由类

6. **同一员工的多个 Tray / 多个 Chrome 实例**  
   现状：后端 `activeConnections.set(employeeId, ...)` 后写覆盖先写，新连接顶替旧连接。  
   未来：要么改为 `Set<Socket>` 广播给所有连接、要么明确"同一 token 只允许单连接"并拒绝后来者。

7. **网络抖动后状态同步**  
   现状：重连即可；不做差量补偿。可能漏一次申领指令。  
   未来：指令存数据库后由插件主动拉一次 `/api/v1/commands?status=pending&target=ext`，确保没漏。

### 业务类

8. **指定读者的泰康账号本身能不能也申领**  
   现状：可以，读者用自己账号扫到的池里也能点申领；和其他员工一样平等。  
   未来：如果业务方希望"读者只读不接业务"，加一个 `read_only_account` 标识。

9. **泰康账号统一登录 / SSO 失效**  
   现状：每个员工各自手动登录，掉线就掉线。  
   未来：Tray App 检测到 Chrome 登录失效后弹提示，引导员工重登；或者通过浏览器自动登录（业务方红线，**不会做**）。
