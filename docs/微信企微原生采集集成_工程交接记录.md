# 微信与企业微信原生消息采集集成：工程交接记录

更新日期：2026-10-25
用途：记录需求决策、已验证事实、当前代码状态和未完成事项，便于后续开发者或 AI coder 接手。本文描述的是进行中的集成工作，不代表已完成客户版发布。

## 1. 项目目标与已确认决策

客户使用 Windows，在微信和企业微信桌面端与客户沟通。寰宇医道客户端在后台周期性读取本机消息；允许有一定延迟，不要求实时。业务只需要采集指定业务会话，例如护工、医疗协助群等，不需要把全部个人消息送入业务系统。

已确认的产品和技术决策：

1. 不使用开源工具自带的图形界面，只保留消息读取、媒体读取等核心代码。
2. 微信与企微采集器分别作为 Windows 子进程运行。寰宇医道主进程负责会话规则、后端通信、持久化确认和附件上传。
3. 采集器发现会话目录；后台配置决定哪些会话订阅消息。未订阅的会话不读取消息正文。这样后台可调整会话范围，不必把业务关键词写死在客户端。
4. 两个平台的原始消息类型不同，但通过共享消息信封表达共同字段（会话、来源 ID、方向、发送者、规范类型、时间、原始类型码、来源元数据、附件）；平台差异保留在 `sourceTypeCode` 和 `sourceMetadata`。未知类型必须保留并显式诊断，不能静默丢弃。
5. 新消息使用独立的原生采集数据结构和入库链路，不要求兼容截图时代 sidecar 的消息格式。sidecar 暂时仍在安装包配置中；未来可以弃用，也可以按需适配新结构。
6. 企业微信采集使用当前 profile 对应的数据目录。运行中检测到当前 profile/目录变化时，暂停企微采集；本轮决定不支持客户端运行中切换，切换企业后重启寰宇医道客户端。选择正确的数据目录不需要额外读取企业显示名称。
7. 当前会话采集规则由后台管理端配置，不采用客户端内置的群名关键词或单聊标题规则作为最终配置。
8. 本机旧开发数据库数据已按用户要求清空；本地开发库按当前 Prisma schema 重建用于验证。正式环境 migration 链仍需单独处理，不能把本地 `db push` 当成生产迁移方案。

### 协议与可靠性约定

- 子进程 stdout 只能输出逐行 JSON 协议；stderr 只用于诊断，不写消息正文或凭据。
- 采集器按父进程提供的订阅列表读取消息；空列表不读取消息正文。企微仍可刷新会话目录以便后台配置新会话。
- 消息批次携带 `cursorAfter`。Electron 收到后先提交后端消息，再处理附件上传；所有必要持久化成功后写本地游标并 ACK。发生失败不推进游标，子进程可重发，服务端按来源 ID 幂等。
- 企微增量游标为源表 `message_table.rowid`，不是消息时间；新写入的旧时间消息也会被读取。最近 5 分钟消息仍会重查，用于发现附件状态变化。企微扫描间隔为 2 分钟，实际耗时和客户端到端延迟仍待 Windows 测量。
- 现阶段附件状态回查窗口是 5 分钟；旧消息若在更晚时间才下载附件，当前逻辑不保证重新发现。先用 Windows 客户数据测量下载/落盘行为，再确定是否需要持久化待补附件列表。
- 成功同步后台规则后，本机保存当时选中的会话；后台不可用或客户端重启时继续按本机最后保存的订阅采集。规则恢复在线后再重新同步。
- 会话身份使用平台、账号、来源会话 ID；消息保留平台原始类型码及元数据。媒体元数据与媒体字节状态分开表达。

## 4. 企业微信当前企业识别：决策与证据

问题背景：测试机先后切换过企微企业。此前通过固定旧目录读到了旧企业的 65 个会话。用户要求客户端要知道启动时当前登录的企业及其对应数据目录；如果运行中切换不能可靠支持，就暂停采集并要求重启客户端。

当前识别方案：

1. 读取当前 Windows 用户下企微注册表 `HKCU\\Software\\Tencent\\WXWork` 的存储设置。若设置了自定义路径，使用该路径；若为空且 `DataLocation=0`，使用 Windows 文档目录下 `WXWork`。其它未验证存储模式显式报错，不猜测目录。
2. 读取 `<WXWorkRoot>\\Profiles\\setting.json` 的 `CurrentProfile`。
3. 读取该 profile 的 `io_data.json`，解析 protobuf 风格 `user_info` 的字段 1，得到账号目录编号。
4. 解析到 `<WXWorkRoot>\\<账号目录编号>\\Data` 并要求 `message.db` 存在。
5. Electron 启动企微子进程时传入明确的 `--source-root` 和 `--account-directory-id`，企微读取不再自行寻找“第一个能打开的旧数据库”。每 30 秒校验当前 profile；一旦身份变化或无法验证，停止企微子进程、清理该运行会话中的企微发现状态并锁定到客户端重启。微信采集可独立运行。
6. 企微子进程只读取 Electron 明确传入的数据目录，不单独解析企业显示名称；当前目录与 profile 的绑定由 Electron 侧完成。

已确认的 Windows 观察：手动切换企业前后，`CurrentProfile` 和 `user_info` 字段 1 都变化，字段 1 对应不同的账号数据目录编号；旧 profile 与新 profile 各自落到各自数据目录。这证明“当前 profile -> 账号目录”链条在测试机上成立。实际运行时切换后，验证前读到的 65 个会话属于旧 profile；之后识别到新 profile 的方向是正确的。

企业显示名称不是消息采集和企业切换检测的必要条件，因此已移除单独读取它的步骤。上游解析器仍可在正常采集时读取用户/组织元数据，但产品不再为显示名称额外触发密钥探测。

前面提到的“Windows 计划任务”只是尝试把短诊断放在交互桌面会话运行的远程执行手段，执行超时，没有成功取得企业名称；不是产品架构，也没有留下常驻任务。之后用交互会话再次尝试仍因扫描耗时而停止。Windows 上 Broker Python 进程保持运行，企微进程也保持运行；本轮诊断临时文件和 PsExec 工具已清理。

**给接手者的约束：** 高负载探测的根因是新增的企业名称解析单独调用了上游密钥探测，实际采集又会再次调用；这一步现已删除。正常消息采集仍需要密钥探测来解密企微数据库。采集器周期性扫描会重复进入上游采集入口，后续需观察 Windows 实际运行成本，再决定是否复用运行中已取得的解密上下文。不得为了企业显示名称额外执行密钥探测。

## 7. 主要已知风险

- **企微上下文：** 客户端用当前 profile 和账号目录编号选择并监控数据目录；企业显示名不参与采集判定。切换前后的映射已在 Windows 上验证，仍需用最终产品包做端到端确认。
- **环境差异：** 上游功能在 Windows 实测，开发主机是 macOS。真实微信/企微数据库、Windows 注册表、MSVC 编译和 Windows 子进程生命周期都必须在 Windows 验收；macOS 只能做 TypeScript、代码审查和可用的非平台特定构建检查。
- **企微版本/数据库格式：** 企业微信版本更新可能改变数据结构或密钥探测方式；解析失败要明确报错，不能扫描旧目录、换数据库或返回部分成功。
- **消息和媒体可靠性：** 图文、文件、合并消息应分别校验父子消息、来源时间、媒体字节/哈希和最终对象存储。只验证入库数量非零不足以通过。
- **授权和隐私：** 当前采集范围由后台规则控制；不能因为采集器可发现所有会话就把所有正文订阅上传。诊断日志不得包含消息正文、解密密钥或附件内容。
- **工作树状态：** 本仓库同时存在大量其他未提交改动和新增文件。交接者不要 reset、checkout 覆盖或清理整个工作区；开始前先检查 `git status --short`，只修改本任务明确文件。
