# 订单字段与服务步骤分析：现有实现说明

> 本文记录当前代码中的真实处理流程，不是新方案。提示词、输入模板和字段白名单以 packages/backend/src/llm/orderAiExtraction.ts 为准；本地代码提示词版本：order-fields-v7-native-message-evidence。
>
> 生产案例只读查询日期：2026-10-29。案例中的申领号、寰宇订单号及沟通正文已脱敏。生产数据库保存模型输出和水位，不保存当时完整模型输入，所以案例展示的是按现有代码可组装出的输入形状，不冒充历史请求原文。

## 1. 结论

当前主要业务 AI 调用是 extractOrderServiceFields。每次针对一张泰康 B 端订单调用一次文本模型；这一轮同时要求 AI 完成三类工作：

1. **服务信息归属**：阅读申领号下的沟通，结合程序提供的寰宇服务单候选，为每条字段候选和每个服务事件选择寰宇服务单号。
2. **字段提取**：从动态字段白名单中提取新增、确认、变更或需确认的信息。
3. **服务事件识别**：根据明确的完成或确认事实输出 workflow_events，后台再按工作流配置更新服务步骤状态。

这三类工作目前在同一个模型请求中，不是三次调用。但需要准确区分：提示词要求按时间线理解和分段，模型输出也会给字段候选及服务事件标注寰宇服务单号；它**没有输出逐条消息的“消息 ID → 订单”归属表**，也没有直接输出各服务步骤的完整状态或“当前阶段”。

触发水位目前只用于判断是否有新内容；一旦触发，代码仍重新读取并发送可查询到的整段历史沟通。因此当前实现没有复用已完成的消息归属，旧内容可能在每一轮中再次由 AI 判断。这是本轮讨论发现的核心问题之一，详见第 10 节。第 10 节中的增量复用内容是后续设计方向，不代表已实现。

申领号下的沟通会被带入每张待分析订单的输入，但同一申领号下每张 B 端订单仍分别触发一轮分析；当前订单服务类型和字段白名单随之变化。

模型没有收到申领号下每张 B 端订单的完整数据库记录。它收到的是：当前 B 端订单 ID、申领号、服务类型、寰宇服务单候选及服务类型、当前订单少量已保存值、当前 B 端表单已保存值，以及申领号下的沟通时间线。

## 2. 触发逻辑

后台启动时执行一次扫描，随后每 30 秒检查一次。检查到待分析订单后，实际分析入口是 triggerOrderAiAnalysis，最终调用 analyzeOrderFields。

| 来源 | 触发条件 | 处理范围 |
|---|---|---|
| 电话录音 ASR | ASR 转写成功落库后立即触发；若后台在落库与触发之间重启，30 秒扫描会找回已完成且水位未消费的转写 | 通话已关联的订单；若有申领号，同时分析该申领号下各订单 |
| 微信/企微 | 后台每 30 秒检查；新消息后达到后台配置的静默分钟数才触发，当前默认 5 分钟 | 该申领号下有新素材的订单逐单分析 |
| 手工补录文字/图片 | 新素材静默 3 分钟后触发 | 素材所属订单 |
| 订单页手动重跑 | POST /api/v1/orders/:id/ai-fields/reanalyze | 指定订单，强制重跑 |

静默时间只控制何时入队，不裁剪模型读取的历史内容。每次分析都会重新读取该申领号下可查询到的整段微信/企微消息和通话记录，再按时间组成时间线。

同一订单正在分析时再次触发，不会并行调用同一订单：本次结束后会补跑一轮并读取最新素材。不同订单仍分别分析。

### 静默水位与模型时间的区别

- 旧消息表触发水位使用消息 ID；静默判断看 captured_at。
- 原生采集消息的模型时间使用准确的 occurred_at；静默/变更水位看 observed_at、附件 updated_at 和会话关联时间。
- 模型时间线不显示系统采集/观察时间；原生消息显示发生时间。旧消息表使用 sort_time ?? chat_time ?? captured_at。
- 系统观察时间会影响“何时触发”，但不会作为原生消息的模型发生时间。

## 3. 一次分析如何组装资料

入口：packages/backend/src/jobs/orderBriefRunner.ts 的 analyzeOrderFields。

### 3.1 当前订单与申领号

1. 按 orderId 读取当前订单。
2. 从 orders.raw_json.crmApplyNo 读取申领号。
3. 若有申领号，读取该申领号关联的全部 orders；没有申领号时只以当前订单为范围。
4. 对每张 B 端订单，根据泰康订单号尝试发现寰宇服务单号并保存映射；远端发现失败会记录警告，并继续使用本地已关联服务单号。
5. 给模型的寰宇服务候选仅包含 {orderNo, serviceType}。B 端来源订单号 bOrderNo 用于服务端编排，不放进模型输入。

### 3.2 订单字段白名单

系统把当前订单 serviceType 与申领号下已关联寰宇服务单的 serviceType 合并去重，然后按这些服务类型挑选字段白名单：

- 字段没有 services 限制时，对所有服务类型可用。
- 字段有 services 限制时，只在本次候选服务类型包含于该列表时可用。
- 只有本次白名单字段可以返回。完整 70 项定义见本文第 7 节。

### 3.3 当前已保存值

模型收到以下当前订单字段，用于判断“新增/确认”还是“变更”，提示词要求不得照搬：

- hospital：订单当前医院。
- department：订单当前科室。
- doctor：订单当前医生。
- serviceRemark：raw_json.comments ?? raw_json.comment。
- bFormSaved：当前订单未作废的 B 端正式表单值，按表单页签整理。

bFormSaved 每个页签取最近更新的一份有效表单数据，只取字符串且非空、长度不超过 200 字符的字段值。当前实现读取失败时记录警告并使用空对象继续分析。

这不是整张订单快照。模型不会因此拿到患者姓名、联系电话、完整 raw_json、全部泰康字段、负责人等所有订单资料。

### 3.4 旧消息表

查询条件是“application_no 等于当前申领号，或 order_id 等于当前订单”，按消息 ID 升序读取。送给模型的字段为：

- 消息 ID；
- channel；
- senderName；
- 正文 contentText；
- 消息时间 sortTime ?? chatTime ?? capturedAt。

旧消息表的映射没有把 senderType、kind 或新的原始类型码传入本次分析，所以旧表消息在时间线上主要显示渠道、发送人名称和正文。

### 3.5 微信/企微原生消息及附件

loadNativeChatAiBatch 只读取已匹配到申领号的会话：

    conversation.applicationNo = 当前申领号
    conversation.applicationLinkStatus = matched

消息按发生时间、合并消息序号、数据库 ID 排序。每条原生消息组装为：

- 原生消息引用 ID：原生消息#<id>；
- 渠道；
- 发送人名称；
- 准确发生时间 occurredAt；
- 方向：incoming / outgoing / system / unknown；
- 标准化消息类型 kind；
- 原始来源类型码 sourceTypeCode；
- 合并消息序号 sourceItemIndex；
- 消息文本；
- 附件证据：类型、文件名、MIME 类型、大小、处理状态，以及已完成的图片识别信息。

已完成的图片识别信息会整理成文本，包括图片类型、简述、可见文字、识别字段；若有挂号匹配结果，也会附申领号/订单候选、匹配说明、经理确认情况。图片二进制本身不会放进本次文本提取请求。

普通文件目前传文件名、格式、大小、状态等元数据；本链路没有提取普通 PDF、Word、TXT 正文。原始 XML/source metadata 本身不传给模型，只整理面向人的业务证据。

如果某条原生消息没有文本和附件证据，会传入“（无文本或附件内容）”。未关联到申领号的原生会话不会由该适配器读入当前订单分析。

### 3.6 手工补录素材（这部分目前取消了，没有手工补录的地方了）

只读取当前订单的 materials，不跨申领号合并其他订单的补录素材。

- 文字素材：发送人标为“专员文字补录”，正文使用 textContent。
- 图片素材：若尚未识别且有 MinIO 对象，先调用图片视觉模型做“分类 + OCR/提取”，结果存入 aiImageKind、aiImageText；进入订单字段分析时间线的是这两项整理后的文字，不是图片二进制。
- 空正文/空识别文字的补录素材不会进入文本时间线。
- 为避免和数据库正数消息 ID 冲突，补录素材映射到负数 message ID；模型证据引用可能显示为“消息#-<素材ID>”。

这条手工补录图片识别调用目前不检查“图片 AI 分析”总开关；总开关默认关闭不代表这里不会识别补录图片。图片识别失败会记警告，字段分析继续运行。

#### 手工补录图片预处理的独立视觉模型输入

未处理的手工补录图片会先通过 visionChat 单独调用视觉模型；之后文本字段提取模型才会收到缓存下来的图片类型和文字。视觉请求使用 HYYD_VLM_MODEL，未配置时 gui-plus，temperature=0。system prompt 原文如下，user 文本固定为“请按要求识别这张图片，只输出 JSON。”，并附图片 base64 data URL：

    你是医疗绿色通道服务的图片理解助手。员工会粘贴各种截图作为订单补充材料。
    请判断图片类型，并提取其中的文字与关键信息。
    类型只能取其一：聊天截图（微信/企业微信对话）、单据（挂号单/缴费单/检查单/病历等）、短信、其他。
    提取要求：
    - 聊天截图：按“谁说了什么”的顺序整理对话文字（分得清就标注说话人）。
    - 单据：提取关键字段（医院、科室、医生、就诊时间、项目、金额、单号等）。
    - 短信：照录短信正文与发件方。
    - 看不清的字不要编造，照实留空或标注[不清晰]。
    严格只输出一个 JSON：{"kind":"聊天截图|单据|短信|其他","text":"提取到的文字与关键信息"}。
    不要解释、不要 Markdown、不要代码块标记。

### 3.7 电话记录

查询范围同旧消息：申领号下的通话，或当前订单的通话。传入字段是通话 ID、方向、ASR 文本、通话开始时间。时间线只包含非空 ASR 文本；原始录音二进制不进入订单字段提取模型。

## 4. 真实模型请求长什么样

### 4.1 System 消息

当前 system 消息由三部分拼接：

1. 本文第 6 节逐字列出的 ORDER_AI_PROMPT_RULES。
2. 固定 JSON 输出结构说明。
3. 动态白名单字段与本次可用的寰宇订单号（事件编码取 WORKFLOW_EVENT_CODES）。

文本模型经 gatewayClient 调用百炼兼容 Chat Completions。模型为 HYYD_LLM_MODEL，未配置时 qwen-plus；temperature=0、maxTokens=10000。

JSON schema 文本会动态包含本轮允许的寰宇服务单和字段白名单，核心形状如下。实际 system prompt 用 JSON.stringify 输出对象：

### 4.2 User 消息模板

下面是代码实际组装的五段输入。花括号内是运行时数据：

    【当前订单】订单ID={orderId}；申请号={applicationNo或无}；服务类型={当前服务类型}

    【允许归属的寰宇服务订单】{[{orderNo, serviceType}, ...]}。每条字段候选和服务事件都必须填写 huanyu_order_no。

    【本单允许提取字段】{字段 code（中文标签）；...}

    【当前已保存正式值，仅用于判断变更，不得照搬】{hospital, department, doctor, serviceRemark, bFormSaved}

    【申请号下沟通时间线】
    {按时间排序的消息、电话转写及补录材料}

### 4.3 时间线每行模板

    [{消息#ID 或 原生消息#ID} {北京时间 YYYY-MM-DD HH:mm} {渠道；方向；类型；来源类型码；合并序号；发送人}] {正文/附件元数据/图片识别摘要}
    [通话#ID {北京时间 YYYY-MM-DD HH:mm} {去电或来电}] {ASR 转写正文}

对旧消息，方向/类型/来源类型码/合并序号可能为空；对原生消息，按采集到的方向、类型、类型码和序号传入。时间线只展示消息发生时间，不展示系统观察时间。

## 5. 模型输出、校验与后续动作

模型只返回 JSON，主体形状如下：

    {
      "field_candidates": [
        {
          "huanyu_order_no": "候选寰宇服务单号",
          "field_code": "白名单字段编码",
          "value": "候选值",
          "normalized_value": "可选标准值或结构化数据",
          "candidate_type": "new_or_confirmed | change_candidate | ambiguous",
          "confidence": 0.0,
          "requires_confirmation": false,
          "evidence": [{ "source_id": "消息#123 或 原生消息#123 或 通话#456" }]
        }
      ],
      "workflow_events": [
        { "huanyu_order_no": "候选寰宇服务单号", "code": "允许的事件编码", "evidence": "明确事实" }
      ]
    }

服务端会再校验：

- huanyu_order_no 必须在本次候选集合中；field_code 必须在本订单动态白名单中。
- 字段必须有非空值和至少一个 source_id；占位词（如“未知”“待确认”“无”）会被丢弃；证据最多留 5 个，值最多 2000 字。
- escort_records、recommended_schemes 会做 JSON 结构校验/规范化；陪诊单值与列表之间有兼容转换。
- workflow event 的订单号和事件 code 必须在候选集合、事件白名单中。

成功结果写入 b_order_ai_analysis_runs 与 b_order_ai_field_candidates。本轮完整历史重算后，旧的 pending 字段候选会标为 superseded。候选字段不会自动覆盖正式订单字段，员工确认/采用后才进入业务表单。服务事件会写入 b_order_ai_service_events；只有该寰宇服务单配置 workflow_enabled=true 时才尝试推进工作流。

模型调用或 JSON 解析失败时，运行记录标为 failed 并记错误。自动触发不立即重试同一批已消费水位；有新素材后再触发。手动重跑可以强制再次分析。事件落库/推进失败单独写日志，不会把失败说成模型成功。

    【服务取消事件(service_cancelled)识别铁律（极其严谨）】：
    1. 必须有双方明确达成一致确认取消就医服务、退单或服务终止解散群聊的确凿事实证据，才能输出 service_cancelled 事件！

    【医院、科室、医生提取与缺失规范（极其重要）】：

    1. 适用状态枚举仅限：已完成、待跟进、待预约、待交付、预约完成待支付、已取消。
    2. “已完成”识别要求（极其严谨，必须有确凿事实证据）：
       - 必须有沟通记录或通话录音明确证实本次就医全流程履约已彻底结束（例如：陪诊/门诊已完成且患者已顺利就医返程，服务人员发送了就诊结束总结/回访/感谢确认，或双方明确确认“本次服务已全部完成/结束”）；

       - 必须 requires_confirmation=true，并引用证明服务彻底结束的具体消息或通话原文作为 evidence。
    【时区基准】：沟通时间线中的所有消息和通话时间均为中国东八区北京时间，提取的时间字段务必保持一致。

## 10. 本轮讨论：一次调用做多项工作，以及增量归属复用

本节记录这轮关于未来改造的讨论。第 1 至第 9 节描述当前代码；本节的“建议方向”尚未实施。

### 10.1 背景与疑问

最初的改造目标是改善“订单字段提取”，希望先把业务背景和规则讲清楚，让 AI 在了解医疗服务业务的情况下提取字段。讨论代码后发现，当前一次 extractOrderServiceFields 调用同时还承担服务单归属和 workflow_events 识别。由于三个目标共用同一条申领号沟通时间线，原本只想改字段提取提示词的改造，会触及这三个任务的输入、输出和相互关系。

本轮确认的疑问包括：

- 是否应该将订单归属、字段提取、服务事件识别拆成多次模型调用？
- 归属已有结果能否复用，避免每次新消息到达后重新让 AI 判断旧消息属于哪个服务单？
- 新消息可能依赖前文，如何让 AI 使用必要历史上下文，同时只处理新消息？
- 服务环节描述是否仍有用途？

### 10.2 当前代码对“复用”的实际支持

当前不是按“仅将新增消息送入模型”的方式工作：

1. `fieldAiLastMsgId`、`fieldAiLastCallId`、`fieldAiLastMaterialId` 和原生消息水位主要用于判断是否有新内容、避免没有变化时无意义调用。
2. 发现新内容后，`analyzeOrderFields` 仍查询申领号下可见的消息和通话，并将完整时间线传入 `extractOrderServiceFields`。
3. 结果保存的是字段候选、模型原始输出、分析水位和服务事件；当前没有独立持久化每条消息到一个或多个寰宇服务单的归属结果。
4. 因而现有水位提供的是“增量触发”，不是“增量输入”或“归属结果复用”。

这解释了为什么“希望 AI 不要每次重复区分旧沟通”与当前实现不一致：现在每轮分析仍可能重新理解旧时间线。

### 10.3 建议方向：职责分清，先不增加模型调用次数

当前建议是保留每批新素材一次模型调用，但把三类任务的输入输出边界写清楚；“逻辑上拆分任务”不等于“物理上增加到三次模型调用”。三项任务面对同一批沟通，且字段和事件都需要使用订单归属判断，继续在一个请求中处理可避免多次调用间发生归属不一致。

后续每批分析建议按以下约束设计：

1. **新素材只做一次归属判断**：仅对尚未归属的新消息或新素材提出归属任务。AI 为产生的字段候选、事件和相关内容片段选择一个或多个程序提供的寰宇服务单；程序保存归属结果，以稳定的原生消息引用 ID、消息 ID 或素材 ID 关联。不得把“字段/事件带有服务单号”误认为已保存逐条消息归属。
2. **已归属历史不再重复分类**：后续调用读取已保存的归属结果。必要的旧消息可以作为理解上下文提供，但必须明确标记为已归属、只供理解，不要求 AI 再次输出归属。对无法确定的内容保留待判状态，不强行分配。
3. **允许一条消息涉及多个服务单**：同一条消息可能讨论多个订单，应按其中实际表达的内容分别关联；不能假设每条消息只能归属一个服务单。若无法确定具体内容片段对应哪张服务单，保留不确定状态。
4. **新内容继续做字段与事件判断**：AI 对新内容生成字段候选和 workflow_events，并使用已保存的订单归属、当前字段值以及必要业务上下文消解“刚才说的方案”“再次复诊”等指代。输出仍是候选和事件，不直接写正式字段或直接改步骤状态。
5. **保留跨批次未完成判断所需的信息**：若事件需要多轮对话共同证明（例如先提出取消、后续才确认），后台需要保留尚未闭合的待判断上下文，供新一批消息判断；不能因上一批结束就丢掉，也不应因此重扫全部历史。
6. **纠错要有明确重判路径**：当经理或运营人员纠正既有订单归属，或明确要求重分析时，才对受影响的历史内容重新判定，并保留可追溯的修订记录。常规新增消息不自动触发全历史重新归属。

图片原始内容的视觉理解仍是独立图片 AI 流程；其识别结果作为新素材或消息的证据进入订单 AI 分析，不应和“订单字段与服务步骤分析”的文本模型调用混为一谈。

### 10.4 服务环节配置与 workflow_events 的关系

后台工作流配置和 AI 的业务说明不是同一个配置：

- **实际工作流配置**定义系统步骤、步骤状态、激活关系、重复性及事件如何推进步骤。它是后台更新状态和提醒读取状态的依据，仍然有用。
- **提供给 AI 的服务环节业务说明**解释某个事件何时能从沟通证据中成立、哪些情况不能判为完成。即使不要求 AI 输出“当前阶段”，这些说明仍能帮助 AI 判断是否应输出 workflow_events。

当前代码中，工作流事件提示词主要是固定规则和事件编码；此前 AI Skill 配置页保存的服务类型/服务环节描述尚未接入 `extractOrderServiceFields` 的 system prompt。因此该配置当前不会改变模型判断。后续若要让实施人员配置业务说明，需要明确把它作为 AI 判断规则输入；后台工作流本身仍负责事件落地及提醒状态。

### 10.5 本轮结论及尚未实施的事项

- 当前一次订单 AI 调用做归属、字段提取、workflow_events 三类工作；当前没有逐消息归属表。
- 当前水位只增量触发，模型输入仍是整段历史；归属结果未被独立复用。
- 建议先保持每批素材一次模型调用，明确任务边界，并实现消息/素材归属的持久化和增量输入；不因逻辑拆分而默认改成三次调用。
- 当前只完成方案讨论和本文档更新；尚未改动模型提示词、数据库结构、调度逻辑或 Skill 配置接入。
