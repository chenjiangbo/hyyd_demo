

> **最终方案：Tray App 自己截取前台微信/企微窗口；Windows 自带 OCR 识别整张窗口；VLM 低频/触发式识别窗口内区域坐标；本地代码按区域坐标给 OCR 结果分区；再做会话识别、消息块合并、发送方判断和去重。**

这个方案不再依赖 screenpipe。你原文档里“原始证据先保存、按会话分桶、会话内去重、不要直接把 OCR 全文写成正式消息”的设计仍然保留，只是把底层采集从 screenpipe 换成自研 Tray App。

# 1. 新版整体目标

MVP 阶段目标不是订单关联，也不是写正式 `messages` 表，而是验证：

```text
员工正常使用企微 / 微信时，
Tray App 能够自动捕获用户打开过的会话，
并在本地还原出近似的聊天界面：

左侧：识别到的会话列表
右侧：该会话下识别出来的消息块
每条消息可回溯来源截图
```

几个边界：

```text
不 hook 微信 / 企微
不解密本地数据库
不调用微信私有协议
不依赖 screenpipe
不要求员工固定窗口大小
不要求员工不最大化 / 不 resize / 不调整微信内部栏宽
MVP 不做订单关联
MVP 尽量还原所有被打开过的会话
```

原文档里“不 hook、不解密、不调用私有协议”的边界仍然成立。

---

# 2. 总体链路

```text
Tray App
  ├─ 监听前台激活窗口
  ├─ 判断是否 是WXWork.exe / WeChat.exe
  ├─ 截取目标窗口截图，不保存全屏
  ├─ Windows OCR 识别整张窗口，得到 text + bbox
  ├─ 判断是否需要 VLM 重新分区（如果当前没有 vlm 给的分区，或者窗口触发了 resize 或最大化等影响分区坐标的行为，那就需要 VLM 一次，VLM 建议使用 qwen 的 vl 系列）
  ├─ VLM 返回 sidebar/title/chat/input 区域坐标
  ├─ 本地按坐标给 OCR block 分区
  ├─ title 区识别当前会话
  ├─ chat 区提取消息块
  ├─ 根据左右位置判断 self / other / system
  ├─ 会话内去重、消息块去重
  ├─ 写入本地 SQLite
  └─ Tray App 已有界面读取 SQLite 展示
```

这里最关键的分工是：

```text
Windows API：
  负责知道当前是不是微信/企微窗口，以及窗口大小/最大化状态是否变化。

Windows OCR：
  负责识别窗口截图里的文字，并返回文字坐标。

VLM：
  只负责低频识别窗口内几个大区域的坐标。

本地代码：
  负责高频分区、消息合并、去重、存储、展示。
```

# 3. 窗口检测与截图

Tray App 只采当前前台窗口。

判断逻辑：

```text
1. 获取前台窗口 hwnd
2. 获取窗口进程名
3. 如果 process_name 是 WXWork.exe 或 WeChat.exe，进入采集状态
4. 否则不采集
```

窗口大小和位置可以通过 Windows API 获得。`GetWindowRect` 返回指定窗口的边界矩形，坐标是屏幕坐标；`GetWindowPlacement` 可以判断窗口是否最大化、最小化或普通显示状态。([Microsoft Learn][1])

你的判断是对的：**移动窗口位置不用触发 VLM 重新分区**。因为我们截的是“微信窗口图”，VLM 和 OCR 处理的坐标都是相对于这张窗口截图的内部坐标。窗口从屏幕左边拖到右边，只要窗口内部大小没变，区域坐标不变。

需要触发 VLM 的外部变化只有：

```text
窗口宽度变化
窗口高度变化
最大化 / 恢复变化
```

这里我不知道 windows api，是否可以检测到一些窗口的事件，比如窗口发生了 resize，我们就认为需要 vlm 一次，不过我不知道 resize 是不是用户在拖动窗口大小的过程中一直触发，那我们可能需要避免持续vlm

隔多长时间截图一次这个可能也需要仔细斟酌下，3-5秒就可以了，要估算下数据量

# 4. OCR 方案

MVP 采用 Windows 自带 OCR。

原因：

```text
1. 我已经简单测试过，中文微信内容能识别出来。
2. screenpipe 在 Windows 上的 OCR 效果你也觉得可接受。
3. Windows OCR 能返回文字、行、词以及坐标，适合我们后续做分区和消息块合并。
4. 暂时不需要引入 PaddleOCR / Python / ONNX 等复杂依赖。
```

Windows 的 `Windows.Media.Ocr` 命名空间提供 `OcrEngine`、`OcrResult`、`OcrLine`、`OcrWord` 等对象；`OcrWord` 有 `BoundingRect`，可以拿到识别文字在图片中的位置和大小。([Microsoft Learn][2])

OCR 处理方式：

```text
每次截取微信/企微窗口图
=> 对整张窗口图 OCR
=> 保存 OCR lines / words / bbox
=> 后续按 VLM 区域坐标分区
```

注意：**不是先裁 chat 区再 OCR**。现在更稳的方式是：

```text
整张窗口 OCR
+
VLM 给区域
+
OCR block 按坐标分区
```

这样即使区域坐标有轻微偏差，也可以通过后续规则处理。

# 5. 分区方案：VLM 低频/触发式校准

这是新版核心。

## 5.1 VLM 负责什么

VLM 只做一件事：

> 看一张微信/企微窗口截图，返回几个区域坐标。

不要让 VLM 做 OCR，不要让 VLM 判断消息，不要让 VLM 还原聊天。它只返回：

```json
{
  "imageWidth": 1280,
  "imageHeight": 820,
  "regions": {
    "sidebar": {
      "x1": 0,
      "y1": 0,
      "x2": 310,
      "y2": 820
    },
    "title": {
      "x1": 310,
      "y1": 0,
      "x2": 1280,
      "y2": 70
    },
    "chat": {
      "x1": 310,
      "y1": 70,
      "x2": 1280,
      "y2": 650
    },
    "input": {
      "x1": 310,
      "y1": 650,
      "x2": 1280,
      "y2": 820
    }
  },
  "confidence": 0.86
}
```

区域坐标必须是**相对于窗口截图本身**的像素坐标，不是屏幕坐标。

这样窗口移动不会影响 layout。

---

## 5.2 什么时候调用 VLM

按照你刚才的修正，我建议这样定：

```text
1.Tray App 当前没有可用的 VLM layout 时 WXWork.exe / WeChat.exe：
   调用 VLM。


3. Windows API 检测到窗口宽高变化：
   调用 VLM。

4. Windows API 检测到最大化 / 恢复状态变化：
   调用 VLM。

5. 定时重新校准：
   每 5 或 10 分钟调用一次 VLM。
```

其中第 5 点主要解决你说的内部 layout 变化：

```text
用户拖动了左侧联系人栏宽度
用户调整了输入框高度
微信/企微内部 UI 变化
```

这些 Windows API 不一定能知道，所以用定时 VLM 兜底。

我同意你说的：**layout 失效判断先保留设计，但暂时不启用。** 也就是说 MVP 先不做复杂判断，只记录一些指标，实际效果测试后再决定要不要打开。

---

## 5.3 VLM 分区结果如何被本地使用

每张截图 OCR 后，会得到很多 OCR block：

```json
{
  "text": "好的，明天上午十点到",
  "bbox": {
    "x": 625,
    "y": 220,
    "w": 210,
    "h": 24
  }
}
```

本地代码计算中心点：

```text
center_x = x + w / 2
center_y = y + h / 2
```

然后套 VLM 返回的区域：

```text
center 在 sidebar 内 -> sidebar
center 在 title 内   -> title
center 在 chat 内    -> chat
center 在 input 内   -> input
否则                 -> unknown
```

这一步是纯坐标判断，非常稳定，也很好调试。

---

## 5.4 layout 版本

每次 VLM 返回一套区域坐标，都生成一个 `layout_version`。

后续截图帧都关联当前 `layout_version`。

```text
layout_version_id = 12
app = WeChat.exe
window_width = 1280
window_height = 820
show_state = maximized / normal
created_reason = first_open / window_resize / maximize_changed / periodic
regions_json = ...
created_at = ...
```

这样后面排查问题很方便：

```text
某条消息为什么分错区？
看它对应的是哪个 layout_version。
这个 layout 是 VLM 什么时候生成的？
是因为 resize 生成的，还是定时生成的？
```

# 6. 截图与 OCR 频率

你明确说不需要“鼠标滚轮 / 键盘输入 / 点击触发采集”，那就先不用。

MVP 采集规则：

```text
目标窗口在前台：
  每 3 秒截一帧并 OCR

目标窗口不在前台：
  不截、不 OCR

刚切换到目标窗口：
  延迟 500-800ms 截第一帧，避免界面还没刷新完

窗口最小化：
  不截、不 OCR

窗口大小 / 最大化状态变化：
  等 500-800ms 稳定后截一帧，调用 VLM，更新 layout
```

# 7. 会话识别

MVP 要还原所有被打开过的会话，不再只保留规范命名会话。

当前会话主要从 `title` 区域 OCR 得到。

处理逻辑：

```text
1. 取 title 区 OCR 文本
2. 清洗：
   - 去空格
   - 去特殊符号
   - 去“聊天信息”“更多”等按钮文字
3. 得到 conversation_title
4. 生成 thread_key
```

`thread_key` 可以这样：

```text
如果 title 里有手机号：
  thread_key = channel + ":phone:" + phone

否则：
  thread_key = channel + ":title:" + normalized_title_hash
```

MVP 不做订单关联，但仍然可以做 classification：

```text
title 有手机号：
  named_customer

title 命中“泰康 / 寰宇 / 沟通群 / 服务群”等：
  work_group

其他私聊：
  unknown_private

其他群聊：
  unknown_group

识别不到标题：
  unknown_thread
```

这只是分类，不影响展示。所有打开过的会话都可以进入本地还原界面。

你原设计里“会话层 conversation_threads 表示员工和某个人 / 某个群的一条聊天链”的概念仍然保留，只是 MVP 暂时去掉 `matched_order_id`。

# 8. 消息块提取

分区完成后，只从 `chat` 区域里提取消息块。

不要从这些区域提取消息：

```text
sidebar
title
input
unknown
```

尤其是 `input` 区域，不能当消息，因为那可能是员工还没发送的草稿。

## 8.1 OCR line 进入 chat 区

Windows OCR 通常会给 line / word。建议先以 line 为基本单位，而不是 word。

每个 line 有：

```text
text
bbox_left
bbox_top
bbox_right
bbox_bottom
```

过滤规则：

```text
只保留中心点落在 chat 区域内的 OCR line。
```

## 8.2 判断发送方

基于 chat 区左右位置判断：

```text
chat_left
chat_right
chat_width
```

对每个 line / block：

```text
如果 block.right 靠近 chat_right：
  self

如果 block.left 靠近 chat_left：
  other

如果 block.center 靠近中间，且文本像时间 / 系统提示：
  system

否则：
  unknown
```

比起只看中心点，我更建议看左右边界：

```text
右侧消息看 right 是否靠近 chat_right
左侧消息看 left 是否靠近 chat_left
```

原因是长消息会向中间延伸，只看中心点容易误判。

## 8.3 合并多行消息

一条长消息可能被 OCR 拆成多行。

合并规则：

```text
同一个 thread
同一个 frame
同一个 sender_type
纵向距离接近
左右边界接近
中间没有明显时间戳 / 系统提示
```

“接近”不要写死。可以用当前帧 OCR 行高的中位数做基准：

```text
median_line_height = 当前 chat 区 OCR line 高度中位数

如果 next.top - current.bottom < median_line_height * 1.2：
  可能属于同一消息
```

左右边界：

```text
self 消息：
  比较 right 边界是否接近

other 消息：
  比较 left 边界是否接近
```

这比“x 坐标相差多少”更稳。

# 9. 去重设计

你说多次截图、多次 OCR 的去重需要更严谨，这确实是重点。

我建议分 4 层去重。

---

## 9.1 帧级去重

同一窗口停留不动时，每 2 秒会产生大量重复截图。

每帧保存：

```text
image_hash
phash
ocr_text_hash
chat_text_hash
```

判断：

```text
如果当前 frame 的 phash 和上一帧极其相似
并且 chat_text_hash 相同
=> 这帧不进入消息提取，只更新 last_seen_at
```

注意：不要只用图片 hash，因为微信光标闪烁、时间变化、头像状态变化可能导致图片 hash 变化。更稳的是：

```text
图片相似
+
chat 区 OCR 文本相同
```

---

## 9.2 会话级去重

必须先识别当前 thread，再在 thread 内去重。

原文档里强调“不能在全天 500 张截图里全局去重，必须先分会话，再在会话桶内部排序、去重、提取新增文本”，这个原则继续保留。

原因：

```text
不同客户都可能回复“好的”
全局去重会误删不同会话的相同消息
```

所以所有消息块 dedupe 都必须带上：

```text
thread_id
```

---

## 9.3 消息块级去重

对每个提取出来的 message block，生成：

```text
content_normalized
sender_type
content_hash
```

dedupe_key：

```text
thread_id + sender_type + normalized_content_hash
```

如果同一个 thread 最近 N 条里已经存在相同或高度相似内容：

```text
不新增 message_block
只更新 existing_block.last_seen_at
增加 seen_count
追加 source_frame_id
```

相似度判断可以先简单做：

```text
完全相同：直接去重
归一化后相同：直接去重
相似度 > 0.92：认为重复
```

归一化包括：

```text
去掉多余空格
全角半角统一
标点统一
OCR 常见错字可后续再处理
```

---

## 9.4 滚动场景去重

员工滚动聊天记录时，旧消息会重新出现。

这时不要把旧消息当新消息。

所以同一个 thread 下，不应该只看最近 10 条，而是看一个较大的时间窗口：

```text
最近 24 小时 / 最近 500 条 message_blocks
```

如果同样内容、同样 sender、相似位置附近出现过，就不新增。

但有一个问题：客户可能真的多次发“好的”。

所以短文本需要特殊处理。

### 短文本策略

对于：

```text
好的
收到
可以
嗯
谢谢
```

这类短文本，如果完全去重，可能误删真实重复消息。

MVP 可以先这样：

```text
短文本相同且在 2 分钟内重复出现：
  去重，更新 last_seen_at

短文本相同但间隔超过 2 分钟：
  可以新增一条
```

长文本可以用更长窗口去重。

# 10. 本地 SQLite 设计

不用 screenpipe SQLite 后，需要自己的本地存储。

## 10.1 `capture_frames`

```sql
CREATE TABLE capture_frames (
  id INTEGER PRIMARY KEY AUTOINCREMENT,

  channel TEXT NOT NULL,                 -- wxwork / wechat
  process_name TEXT NOT NULL,            -- WXWork.exe / WeChat.exe
  window_title TEXT,

  captured_at TEXT NOT NULL,

  window_left INTEGER,
  window_top INTEGER,
  window_width INTEGER,
  window_height INTEGER,
  window_show_state TEXT,                -- normal / maximized / minimized

  screenshot_path TEXT NOT NULL,          -- 目标窗口截图，不是全屏

  image_hash TEXT,
  phash TEXT,
  ocr_text_hash TEXT,
  chat_text_hash TEXT,

  layout_version_id INTEGER,

  ocr_engine TEXT,                        -- windows_ocr
  ocr_status TEXT,                        -- success / failed
  ocr_text TEXT,
  ocr_blocks_json TEXT,

  frame_status TEXT,                      -- captured / skipped_duplicate / ocr_failed / no_layout

  created_at TEXT NOT NULL
);
```

---

## 10.2 `layout_versions`

```sql
CREATE TABLE layout_versions (

  channel TEXT NOT NULL,
  process_name TEXT NOT NULL,

  window_height INTEGER NOT NULL,
  window_show_state TEXT,

  trigger_reason TEXT NOT NULL,

  sidebar_rect_json TEXT NOT NULL,
  title_rect_json TEXT NOT NULL,
  chat_rect_json TEXT NOT NULL,
  input_rect_json TEXT NOT NULL,

  is_active INTEGER DEFAULT 1,

  created_at TEXT NOT NULL
);
```

---

## 10.3 `conversation_threads`

```sql
CREATE TABLE conversation_threads (
  id INTEGER PRIMARY KEY AUTOINCREMENT,

  channel TEXT NOT NULL,
  thread_key TEXT NOT NULL,

  conversation_title TEXT,
  normalized_title TEXT,

  phone TEXT,
  is_group INTEGER DEFAULT 0,
  classification TEXT,
  -- named_customer / work_group / unknown_private / unknown_group / unknown_thread

  last_seen_at TEXT,

  message_count INTEGER DEFAULT 0,

  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,

  UNIQUE(channel, thread_key)

```

---

## 10.4 `message_blocks`

```sql
CREATE TABLE message_blocks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,

  thread_id INTEGER NOT NULL,

  sender_type TEXT NOT NULL,
  -- self / other / system / unknown

  content TEXT NOT NULL,
  normalized_content TEXT NOT NULL,

  bbox_left INTEGER,
  bbox_top INTEGER,
  bbox_right INTEGER,
  bbox_bottom INTEGER,

  first_seen_at TEXT NOT NULL,
  last_seen_at TEXT NOT NULL,
  seen_count INTEGER DEFAULT 1,

  content_hash TEXT NOT NULL,
  dedupe_key TEXT NOT NULL,

  source_frame_ids TEXT,
  source_screenshot_path TEXT,

  ocr_confidence REAL,
  sender_confidence REAL,

  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,

  FOREIGN KEY(thread_id) REFERENCES conversation_threads(id)
);
```

## 10.5 `ocr_blocks`，可选

如果你想方便调试，建议单独存。

```sql
CREATE TABLE ocr_blocks (
```

如果担心表太大，MVP 可以先只把 blocks 放在 `capture_frames.ocr_blocks_json`。

# 11. 处理流程细化

完整流程如下：

```text
1. Tray App 发现前台窗口是 WXWork.exe / WeChat.exe

2. 判断当前窗口是否可采：
   - 非最小化
   - 窗口宽高正常
   - 窗口可见

3. 每 2 秒截一张目标窗口截图

4. 获取窗口状态：
   - width
   - height
   - show_state

5. 判断是否需要 VLM：
   - 没有 active layout
   - app 类型变化
   - width / height 变化
   - show_state 变化
   - 距离上次 layout 超过 5 或 10 分钟

6. 如需要，调用 VLM：
   - 输入窗口截图
   - 返回 sidebar/title/chat/input 坐标
   - 保存 layout_versions

7. 调 Windows OCR：
   - 对整张窗口图 OCR
   - 保存 OCR text + blocks + bbox

8. 使用当前 active layout 给 OCR block 分区：
   - sidebar
   - title
   - chat
   - input
   - unknown

9. 从 title 区识别当前 conversation_title

10. 获取或创建 conversation_thread

11. 从 chat 区提取 OCR lines

12. 判断 sender_type：
   - self
   - other
   - system
   - unknown

13. 合并多行 OCR 为 message_blocks

14. 做 frame / thread / message_block 去重

15. 写入 SQLite

16. Tray App 已有界面读取 conversation_threads 和 message_blocks 展示
```

# 12. layout 失效检测先怎么处理

你说“判断 layout 是否失效的逻辑可以留着，但暂时不生效”，我同意。

MVP 可以只记录，不触发：

```text
unknown_region_block_ratio
title_region_text_count
chat_region_text_count
input_region_text_count
sidebar_region_text_count
```

先不让它影响主流程。

也就是说：

```text
如果指标异常：
  只写日志
  不自动判定 layout 失效
  不自动重新 VLM
```

等你们跑真实数据后，再决定要不要启用：

```text
连续 N 帧异常 => 触发 VLM
```

这样不会一开始把系统做复杂。

# 13. VLM prompt 要求

VLM prompt 必须极其简单，避免它发挥。

建议任务描述：

```text
你会看到一张 Windows 桌面端微信或企业微信窗口截图。
请只识别窗口内部的四个主要区域，并返回像素坐标：

1. sidebar：左侧联系人/会话列表区域
2. title：右侧顶部当前会话标题区域
3. chat：右侧聊天消息展示区域
4. input：右侧底部消息输入区域

要求：
- 坐标必须相对于输入图片左上角
- 不要识别聊天内容
- 不要输出解释
- 只输出 JSON
```

输出 schema 固定：

```json
{
  "imageWidth": 0,
  "imageHeight": 0,
  "regions": {
    "sidebar": { "x1": 0, "y1": 0, "x2": 0, "y2": 0 },
    "title": { "x1": 0, "y1": 0, "x2": 0, "y2": 0 },
    "chat": { "x1": 0, "y1": 0, "x2": 0, "y2": 0 },
    "input": { "x1": 0, "y1": 0, "x2": 0, "y2": 0 }
  },
  "confidence": 0.0
}
```

后端/本地必须校验 JSON：

```text
字段齐全
坐标不越界
区域宽高合理
chat 在 title 下方
input 在 chat 下方
sidebar 在 chat 左侧
```

VLM 输出不合法时，不更新 layout。

# 14. MVP 验收标准

我建议验收标准改成这些：

```text
1. 只在 WXWork.exe / WeChat.exe 前台时采集。
2. 不保存全屏截图，只保存目标窗口截图。
3. Windows OCR 能输出文本和 bbox。
4. 首次打开微信/企微时，VLM 能返回 sidebar/title/chat/input 区域。
5. 窗口最大化 / 恢复 / resize 后，能触发 VLM 重新分区。
6. 移动窗口位置不会触发 VLM，也不影响分区。
7. 每 5 或 10 分钟能自动重新校准 layout。
8. Tray App 能展示用户打开过的所有会话，而不是只展示规范命名会话。
9. 同一屏长时间停留不会生成大量重复消息。
10. 切换会话后，消息能进入对应 conversation_thread。
11. 每条 message_block 能回溯到来源截图。
12. 关闭微信/企微或切到其他应用时停止采集。
```

# 15. 我对这个方案的最终评价

这版方案是目前最平衡的：

```text
比 screenpipe 好：
  不再受全屏截图和全屏 OCR 干扰。

比纯 OpenCV 好：
  不需要写复杂、脆弱的视觉规则。

比人工校准好：
  员工可以最大化、resize、调整内部栏。

比每帧问 VLM 好：
  成本低，延迟低，稳定性更好。

比纯 OCR 规则好：
  分区这件最难的事交给 VLM 做。
```

我建议最终就定成：

> **Windows API 负责窗口状态；Windows OCR 负责文字和坐标；VLM 负责低频区域坐标；本地规则负责高频分区、消息提取和去重。**

这个方案既能做 MVP，也能作为最终交付方案继续演进，不需要 MVP 后再推翻重做。
