# 变更说明：消息结构化从 sidecar(C#) 移到后端(TS)

> 日期：2026-06-13　范围：capture-sidecar / backend / tray-app 类型
> 一句话：把"路线1 的解释层"（拼行 + 分说话人 + 分组）从员工机上的 C# sidecar，
> 挪到后端 TS。sidecar 只保留 采集 + 去重 + OCR + 客户会话过滤，外加给每个 OCR 词块
> **采样气泡颜色**；结构化算法集中到后端，可热更新、好测试，且**不必上传图片**。

## 一、为什么改（背景）

之前 sidecar 越长越胖：截图→去重→OCR→会话过滤→订单号抽取→**消息结构化**全在 C# 里。
讨论后明确了真正的架构分界线：

- **分界线不是 "sidecar vs tray-app"**——两者都跑在员工机上，**都要逐台部署**才能更新。
- **分界线是 "员工机上 ↔ 后端"**：只有后端能"改一处、一台服务器"热更新，但后端只能处理上传上来的数据。

由此得出该放哪：

| 留在员工机（sidecar，因上传代价/隐私，且本就很少改） | 移到后端（因正在反复迭代、需热更新/测试） |
|---|---|
| 采集 + 去重 + **OCR**（本地免费/离线/不传图） + **客户会话过滤（上传前的隐私闸门）** | **拼行 + 分说话人 + 分组（结构化）**、订单号模糊匹配、LLM 抽取 |

**关键洞察**：判说话人要看气泡颜色 = 要像素，而像素只有 sidecar 有。但"判颜色"只需在本机
**采几个像素样本（几个数字）**，不必把图传上去。所以 sidecar 给每个 OCR 词块附带一个
`colorSample`，后端用它算 HSV 饱和度判 self/other。

**多用户不串**：结构化是**纯函数、无状态**——每帧自带输入、输出仅依赖本帧，不碰任何跨请求/
跨用户的共享内存；落库一律按 `employeeId` 归集。Node 并发请求各自栈隔离，物理上不会混。

## 二、改了什么

### 新增（后端）
- **`packages/backend/src/lib/messageStructure.ts`**：结构化核心，C# `MessageStructurer` 的 TS 移植。
  - `structureMessages({channel,width,height,blocks})` → `{speaker:'self'|'other'|'system', name, text}[]`。
  - 算法同 C# 版：`detectChatXRange`（X 投影找最宽密集列 = 聊天区，排除侧栏/成员面板）、
    `groupLines`（Y 重叠拼行）、行→消息分组（垂直间隔大/左右切换）、`classifySpeaker`
    （把消息内各词块的 `colorSample` 取平均算 HSV 饱和度，≥阈值=self，无色则按位置兜底）、
    system 判定（居中 + 时间/撤回正则）。
  - 阈值走环境变量，与 C# 同名同默认：`HYYD_BUBBLE_SAT`(0.15)、`HYYD_CHAT_COL_GAP`(18)、
    `HYYD_CHAT_COL_MINBLOCKS`(5)、`HYYD_CHAT_TOP_FRAC`(0.08)、`HYYD_CHAT_BOTTOM_FRAC`(0.10)。
- **接口 `POST /api/v1/capture/structure`**（`api.ts` §8.4）：body=`StructInput`，鉴权后调
  `structureMessages`，返回 `{data:{messages}}`。纯函数、无状态。
- **`packages/backend/scripts/verify-structure.ts`**：离线验证脚本（合成一帧带侧栏/成员面板干扰
  + 颜色样本的词块），断言列检测排除干扰、self/other/system 判定正确。`npx tsx` 已跑通。

### 新增/改动（sidecar C#）—— 仅"采样颜色"，**结构化逻辑未动**
- **`Models.cs`**：`OcrBlock` 加可选 `ColorSample`；新增 `record ColorSample(int R,int G,int B)`。
- **`BlockColorSampler.cs`**（新）：`Enrich(bitmap, blocks)` 给每块采气泡填充色（复用原
  `MessageStructurer.SampleFill` 的"跳过文字深色像素取平均"逻辑，由按消息区域采改为按词块区域采）。
- **`CaptureCollector.cs`**：OCR 成功后 `ocr = ocr with { Blocks = BlockColorSampler.Enrich(...) }`，
  使上报帧的 `ocr.blocks[]` 带上 `colorSample`。

### 改动（tray-app 类型）
- **`capture-types.ts`**：`CaptureOcrBlock` 加可选 `colorSample`，让该字段贯穿到（未来的）上传。

## 三、为什么是"安全的增量"
- sidecar 端**纯增量**：`MessageStructurer.Build` 仍在跑、现有 frame 的 `messages[]` 字段不变，
  采集调试页照常工作。颜色采样即便有 bug，最坏是 `colorSample=null`→后端按位置兜底，不影响采集。
- 后端结构化与现有 `POST /api/v1/messages`（订单关联）、`extract-key-info`（LLM）同模式：按
  `employeeId` 归集、纯函数处理，不引入跨用户状态。

## 四、已验证 / 未验证
- ✅ 后端 `tsc` 通过；`verify-structure.ts` 跑通（列检测/颜色判定/system 判定全对）。
- ✅ tray-app web/node `tsc` 通过。
- ⚠️ **C# 未编译/未部署**：`capture-sidecar` 目标框架 `net8.0-windows`，Mac 上无法编译，
  需在 Windows 上 `pnpm sidecar:build:win`（或 deploy:win）验证 `colorSample` 真实采样效果。
  改动是增量+复用成熟逻辑，风险低，但**上线前必须在 Windows 编译跑一次**。
- ⏳ 端到端（sidecar 采色 → 上传 → 后端结构化）**尚未联通**：上传链路本就还没接（见交接文档 B6）。

## 六、给"开发 tray-app 的 AI"的提醒
交接文档 **附录 C** 原来建议"直接消费 sidecar 的 `messages[]`"。架构已调整为**后端结构化**：
- 现状：sidecar 仍吐 `messages[]`（旧路径），但**正确方向是上传"词块+colorSample"让后端结构化**。
- 落库结构化消息时，数据从 `POST /api/v1/capture/structure` 的返回（或 `messages` 接口内部结构化）拿，
  不要再在 tray-app 里写第二份结构化逻辑（那正是要删的重复）。
