# 泰康采集账号归属改造

## 已确认的接口行为

- 同一浏览器配置文件中，登录 B 后旧 A 标签页不刷新，`getInfo` 返回 B；个人池接口即使仍传 A 的旧参数，也返回 B 的订单。
- 采集中途切换 A → B，同一轮可能先取得 A 的挂号个人池，再取得 B 的其他个人池。页面上显示的姓名不能用于订单归属。
- `recommendations`、`getImage` 的切换行为尚未实测；采集器对它们采用身份变化即丢弃任务的保守规则。

## 运行规则

同一 Chrome 配置文件的所有泰康窗口只选一个采集标签页。每轮用实时 `getInfo` 与凭证快照确认账号，整轮列表完成并再次核对身份后才发送后台。后台连接账号、消息账号和员工绑定必须一致；列表和详情上报时都重新检查当前员工绑定。列表得到入库 ACK 后才开始个人池详情；详情及附件完整保存并收到 ACK 后才推进指纹。

泰康订单不会在账号之间转单。假设上线前历史归属已由用户核对，本次改造无需判断订单新旧。个人池新订单按本轮验证通过的账号归属，已有相同归属的订单正常更新。每一轮都会重新读取后台现有归属并比较；若不一致，本轮在 `order_attribution_mismatches` 留一条记录，本单不改写、不抓详情，同批其他订单继续。下一轮遇到同一订单仍重新判断；若继续不一致，再记录下一轮。正常情况下此表为空。`collectionBatchId` 只用于详情批次校验。

旧版可能在附件保存失败前就写入详情指纹；新版只把 `detailJson.captureVersion=2` 的订单纳入后端基线。旧详情会在其所属账号的个人池再次出现时重新采集一次。
每轮详情筛选等待当前账号的后端基线；基线超时则按无缓存处理，重新抓取，避免本地旧指纹造成漏采。

## 发布顺序

1. 发布新版后端并重启；启动时会幂等创建 `order_attribution_mismatches` 表及索引，无需手动执行建表 SQL。随后发布新版 Chrome 扩展并让使用者重新加载。后端拒绝旧版采集协议的列表和详情上报，因此两端需在同一维护窗口切换。
2. 观察入库 ACK 的 `mismatchCount`、详情 ACK、账号切换中止日志和不一致记录。若表中出现数据，定位并修复采集代码或核对现有归属；本次发布不自动改写历史归属。不要把历史 `rawJson.taikangAccount` 单独作为修复旧订单归属的依据，它可能曾由错误的全局连接写入。

每条记录对应一次采集批次中的一笔归属不一致订单；同一批次重复上报只写一条。查询：

```sql
SELECT source_order_no, stored_employee_id, observed_employee_id,
       observed_taikang_account, observed_taikang_user_id,
       batch_id, observed_at
FROM order_attribution_mismatches
ORDER BY observed_at DESC;
```

## 上线前需在泰康测试环境确认

- A、B 单独采集；登录 B 后不刷新旧 A 页；同配置文件新窗口登录 B；列表翻页及详情进行中切换账号。
- `recommendations` 和 `getImage` 的账号切换行为、空图片与请求失败的区别、图片是否分页。
- 后台断线和附件保存失败后能够重试，且未完成详情不会写入成功指纹。

测试记录只保留账号、时间、订单号摘要和结果，不保留令牌、患者资料或图片。
